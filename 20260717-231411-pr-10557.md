## Review Process Notes

### Skill improvements

- When a finding claims a shared test fixture or mock feeds wrong-format data to a production consumer, verify that the test harness actually instantiates that consumer. Harnesses frequently select a mock implementation through an env var or factory switch that short-circuits the real one, so a consumer that looks reachable from the fixture may never run under the test. Confirm the instantiation path before rating such a finding, because a plausible consumer chain traced without it produces a high-confidence false positive.

### Repo context updates

- [repo] In the Playwright e2e specs, `startRancherDesktop` (`e2e/utils/TestUtils.ts`) defaults to `RD_MOCK_BACKEND=1`, and `backend/factory.ts` returns `MockBackend` before the `win32 → WSLBackend` branch. `MockBackend` never spawns `wsl.exe`, and `WSLBackend` — including `registeredDistros`, which decodes `wsl.exe --list --verbose` as UTF-16LE by default — is never constructed. A finding claiming the real WSL backend consumes a spec's mock `wsl.exe` entries with the wrong encoding or arg order is therefore a false positive during these specs. The only in-spec consumers of the mock are `WindowsIntegrationManager` (UTF-8 under `WSL_UTF8=1`) and the `CheckWSLDistros` diagnostic (`--list --quiet`, UTF-8).

S2. **Mock WSL ignores the `WSL_UTF8` environment variable** — `src/go/mock-wsl/mock-wsl.go:130` (suggestion, gap)

```go
		encoding := unicode.UTF8
		if cmd.UTF16LE {
			encoding = unicode.UTF16(unicode.LittleEndian, unicode.IgnoreBOM)
```

The mock WSL binary determines output encoding solely via the static configuration flag `cmd.UTF16LE`. If a future change accidentally drops `WSL_UTF8: '1'` from the environment in production, the test will remain green because the mock still outputs UTF-8, while the actual `wsl.exe` in production would default back to UTF-16LE, leading to a silent regression.

### Design Observations

#### Concerns
- **WSL Command Helper Environment Coupling** `(in-scope)`: Since `execCommand` and `captureCommand` now automatically merge `process.env`, the integration manager is much less prone to environment-stripping bugs. However, other components in the codebase that use `spawnFile` directly (such as other diagnostics checkers or backends) could still fall into this trap. Consider introducing a shared helper utility for executing host commands under WSL that standardizes the merge of `process.env` with `WSL_UTF8: '1'`.

#### Strengths
- **Centralized Environment Merging**: Consolidating `...process.env` in `execCommand` and `captureCommand` within `WindowsIntegrationManager` elegantly fixes the stripped-environment bug across all integration manager commands, eliminating redundant hand-rolled environment spreads at the call sites.
- **Robust Multi-Wait Assertions**: Applying a consistent timeout of `10_000` ms on visibility assertions ensures that slow CI runners have sufficient time to render the list, preventing flaky E2E tests.
