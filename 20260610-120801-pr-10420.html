Design Observations ¶

Concerns ¶

setHasQueuedUpdate is a non-serialized read-modify-write; un-awaited callers can race (future) — pkg/rancher-desktop/main/update/LonghornProvider.ts:198-211 Gemini

setHasQueuedUpdate reads updater-longhorn.json, flips isInstallable, and writes it back, with no serialization. The checking-for-update handler calls it with false and the persistent update-downloaded handler calls it with true, both un-awaited (index.ts:153, index.ts:210); a fast cached-update sequence could interleave the two read-modify-write cycles and persist the wrong flag. This is pre-existing — the function and both callers predate the PR, and the Round-1 S1 fix removed a third concurrent caller from the install path, so this change narrows the race rather than widening it. The outcome is also largely self-healing: the next periodic check re-detects the staged update, and the install-completing case ends with the flag the next boot expects. A promise queue inside setHasQueuedUpdate would close it; out of scope here.

Strengths ¶

Not broadcasting update-state from checking-for-update is deliberate (in-scope) — pkg/rancher-desktop/main/update/index.ts:144-154 Gemini

The handler clears available, downloaded, error, and now progress in memory but does not call window.send. Broadcasting that transient state would set available=false/downloaded=false in the renderer, where updateReady gates the Restart Now button on available && downloaded && !error (UpdateStatus.vue:148-149), hiding the update card on every periodic re-check until the check resolves — the flicker PR #10419 fixed. The cleared progress still reaches the UI on the next resolving event, so a newer offer never shows the previous download's percentage. Gemini flagged the missing broadcast as a regression (I1); re-verified against merge-base 8e06bd961, the handler never broadcast, and the proposed fix would reintroduce the flicker.

finish() centralizes listener teardown (in-scope) — pkg/rancher-desktop/main/update/index.ts:291-296 Claude

The closure removes all three one-shot listeners before resolving, so every terminal path settles the promise once and arms no stale update-downloaded listener for a later quitAndInstall. The test "does not install on a later download once the queued install has settled" locks this in.

Promise-settling covers the no-event outcomes (in-scope) — pkg/rancher-desktop/main/update/index.ts:316-322 Claude

Settling on the checkForUpdates() promise itself — .then(result => !result && finish(false)) for disabled checks and .catch(onError) for a rejected check — handles the two cases that emit no updater event at all. This targets the root cause the commit names, not a symptom.

Persistent-handler ordering preserves the queued-flag write (in-scope) — pkg/rancher-desktop/main/update/index.ts:196 Codex Claude

Both reviewers traced that the persistent update-downloaded handler runs before the install-path one-shot, so dropping setHasQueuedUpdate(true) from the one-shot (Round-1 S1 fix) loses no state. See S1 for the suggestion to document the dependency.

Review Process Notes ¶

Skill improvements ¶

  • When a finding recommends emitting, broadcasting, or persisting intermediate state that the code currently withholds at a reset or in-progress point, evaluate the cost of emitting it before rating the omission a bug. A deliberately-withheld update often prevents downstream churn — UI flicker, redundant writes, observer thrash. Trace the consumer that would receive the new emission and confirm it improves rather than regresses behavior. A handler that mutates state in memory and lets the next terminal event broadcast it is a common, correct pattern, not a missing-broadcast bug, because the consumer re-renders on every state it receives.

Repo context updates ¶

  • [repo] main/update/index.ts: the checking-for-update handler intentionally omits window.send('update-state', updateState). It clears available/downloaded/error/progress in memory so the next resolving event (update-available/update-not-available/error) broadcasts fresh values; broadcasting at the checking-for-update point would set available=false/downloaded=false and hide the Restart Now card in UpdateStatus.vue (gated on updateReady = available && downloaded && !error) on every periodic re-check — the flicker PR #10419 fixed. Do not flag the missing broadcast here as a bug.
  • [repo] main/update/LonghornProvider.ts: setHasQueuedUpdate and hasQueuedUpdate do non-serialized read-modify-write on updater-longhorn.json, and the event handlers call setHasQueuedUpdate un-awaited (false from checking-for-update, true from update-downloaded). This is a known pre-existing latent write race; treat a "concurrent un-awaited write" finding here as pre-existing unless the change under review adds, reorders, or awaits these calls.
