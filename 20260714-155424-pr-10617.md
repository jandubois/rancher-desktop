## Design Observations

### Concerns

- **`unused` sits in the default gate, against a strings-first workflow** (in-scope) [Claude Opus 4.8]. Bare `check` — the PR-CI form — always runs `unused` (report_check.go:110), so it fails when an en-us key lands before the code that references it. This project's stack lands strings ahead of their wiring, exactly the case that trips it (the current review SHA reports 2961 unused keys). `undefined` belongs in the default, since it renders `%key%` at runtime; consider moving `unused` behind `--strict`, where completeness and hygiene already live.

### Strengths

- The gate-vs-lister invariant is real for stale, missing, and drift. `check --strict` flattens the locale with `loadYAMLFlat` and `drift` uses `nodeAllLeaves`, but both route through `flattenNodeWithComments`/`appendKeyPath`, so they produce identical key sets — the two commands report identical drift by construction.
- The `errFindings` / operational split (main.go:20-32) is clean, and `drift` honors it correctly.
- Drift compares decoded scalars, so re-quoting the English never counts as drift (compute.go:11-13) — a subtle correctness property, well-commented.
- Keeping missing and drift behind `--strict` is a sound CI split: PR runs stay structural, release runs enforce completeness.

## Review Process Notes

### Skill improvements

- When a tool documents a dual exit-code or error-taxonomy contract (findings vs. operational, retryable vs. fatal, warning vs. error), enumerate every terminal path across all sibling subcommands and confirm the same underlying condition maps to the same code everywhere. Sibling commands that share a contract routinely draw the boundary differently for an edge case — a missing input file, a malformed config, an unknown argument — and the divergence stays invisible until the paths are compared side by side.

- When a PR adds a CI gate, validator, or check whose inputs are supplied by other changes (sibling PRs in a stack, an integration branch, a later migration), identify the tree the gate is meant to run against and exercise it there before rating findings that it aborts, fails, or cannot run. A gate that is dormant on its own branch, because its inputs are not yet assembled, is expected rather than a defect; run it where the inputs exist before assigning severity.

### Repo context updates

- [repo] The `src/go/i18n-report` `check` and `drift` gates run against the `i18n-workflow-v2` integration tree, not individual stacked PR branches. On a stacked branch the registration surfaces (the `locale` enum in `command-api.yaml`, `...availableLocales` in `settingsValidator.ts`) and the translation files are absent, so `check --locale` aborts on a missing enum and bare `check` reports thousands of unused keys — all expected. Validate i18n-report gate changes by building the tool and running it inside an `i18n-workflow-v2` worktree.

- [repo] `i18n-report` flattens locale files through one shared path: both `loadYAMLFlat` and `nodeAllLeaves` call `flattenNodeWithComments`/`appendKeyPath`, so the flat key→value map and the node-tree leaf set carry identical keys, quoted dotted segments included. `check --strict` (flat map) and `drift` (node tree) therefore report identical drift by construction. A finding claiming the two diverge on dotted-segment keys is a false positive — verify the shared flattener first.

- [repo] UPDATE the existing i18n note reading "the source/merge/remove/validate subcommands and the splitKeyPath/appendKeyPath write path live on the i18n-report-merge branch, not yet on the default branch." These subcommands and the write path are now merged to the default branch (main); only `check` and `drift` remain in flight. Drop the "not yet on the default branch" caveat.


The comment for `parseAPILocaleEnum` states it locates the enum by "walking all schema definitions looking for an 'application' property with a 'locale' child." However, `findLocaleEnum` recursively searches for ANY map containing a `locale` key with an `enum`. Because Go randomizes map iteration order, if `command-api.yaml` ever defines multiple `locale` properties (e.g., across different endpoints or components), `findLocaleEnum` will return one of them non-deterministically. (important, regression)

I2. **Inconsistent error classification for unreadable registration files** — `src/go/i18n-report/report_check.go:150-153`

```go
	apiLocales, err := parseAPILocaleEnum(translationsPath(root, "../specs/command-api.yaml"))

	}
```

The registration checks classify missing files inconsistently. If `command-api.yaml` cannot be read, it returns a standard error, resulting in an operational failure (exit code 2). Conversely, if `settingsValidator.ts` or `settingsValidator.spec.ts` are unreadable, the errors are appended to the `problems` slice and returned as a `findingsError` (exit code 1). Missing source files evaluated in a CI gate should be classified uniformly—either all are structural findings, or all are operational tool failures.

Fix: Catch the error from `parseAPILocaleEnum`, append it to the `problems` slice, and continue, matching the structural finding behavior of the other registration file checks.
