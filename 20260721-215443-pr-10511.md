C2. **Unchecking a group deselects the wrong containers** — `pkg/rancher-desktop/pages/Containers.vue:583` [Claude Opus 4.8, Codex GPT 5.6 Sol, Gemini 3.5 Flash]

```js
        table.update([], containers);
```

`update()` locates each row to remove with `findIndex((r) => r._key === row._key)` (`selection.js:444`). This table declares `key-field="id"` (line 14) and its rows carry no `_key`, so every comparison is `undefined === undefined`, matching index 0. Removing N rows splices the first N entries instead. Select group A, then B, then uncheck B: A leaves the selection and B stays, and `applyTableAction` (`selection.js:515`) runs Stop/Delete against B.

This is **pre-existing, not a regression**: `selection.js`, `key-field="id"`, and the absent `_key` all predate the merge-base, and individual row deselect already hits it. `Images.vue:14` passes `key-field="_key"`, which is why it went unnoticed. This PR makes it the new feature's primary path, so it needs fixing here.

Fix in the shared helper (`get` is already imported):

```diff
-        const index = this.selectedRows.findIndex((r) => r._key === row._key);
+        const index = this.selectedRows.findIndex((r) => get(r, this.keyField) === get(row, this.keyField));
```

## Important Issues

I1. **Indeterminate group state never renders** — `pkg/rancher-desktop/pages/Containers.vue:121-122` [Consolidator]

```
                :value="isGroupSelected(group)"
                :indeterminate="isGroupIndeterminate(group)"
```

`@rancher/components` draws the indeterminate dash only via `.checkbox-container input:checked ~ .checkbox-custom.indeterminate:after`, and its `isChecked` computed is `value === valueWhenTrue`. `isGroupSelected` (all selected) and `isGroupIndeterminate` (some but not all) are mutually exclusive by construction, so `value` is always `false` exactly when `indeterminate` is `true`. The input is never checked, the rule never matches, and the base `:after` stays at `scale(0)` — a partially-selected group renders as a blank box, identical to nothing selected.

Fix: drive `value` from "any selected" so the component's CSS engages. Note this also flips the click semantics on a partial group from select-all to clear-all, which is the conventional behavior.

```diff
-                :value="isGroupSelected(group)"
+                :value="isGroupSelected(group) || isGroupIndeterminate(group)"
```

I2. **`display: flex` stretches the group tab across the table** — `pkg/rancher-desktop/pages/Containers.vue:615` [Claude Opus 4.8]

```scss
      display: flex;
```

SortableTable styles `.group-tab` as a shrink-to-fit tab (`display: inline-block`, `padding: 0 10px`, `min-width`, plus a decorative skewed `:after` pinned at `right: -15px`) in an **unscoped** block at `SortableTable/index.vue:1847-1876`. That compiles to `.sortable-table tbody tr.group-row .group-tab`, specificity (0,3,2). The new scoped rule adds a `[data-v-…]` attribute, reaching (0,4,0), so it wins. `display: flex` makes the box block-level, so the tab background and its skewed tail span the full `colspan` instead of hugging the label.

This is the most likely subject of the still-open alignment comment (see Unresolved Feedback).

Fix:

```diff
-      display: flex;
+      display: inline-flex;
```

I3. **Checking a partially-selected group double-adds its rows** — `pkg/rancher-desktop/pages/Containers.vue:581` [Claude Opus 4.8, Codex GPT 5.6 Sol, Gemini 3.5 Flash]

```js
        table.update(containers, []);
```

`update()` appends unconditionally (`selection.js:451-453`). Check one container's own row checkbox, then click its group checkbox: that container is pushed a second time. `howMuchSelected` then compares an inflated count against `pagedRows.length` and can report ALL while rows remain unselected, the bulk command repeats the id on the CLI, and a later group-uncheck removes only one of the two entries, stranding a row in the selection.

Unlike C2, this instance is new: the group checkbox did not exist before.

Fix:

```diff
-        table.update(containers, []);
+        table.update(containers.filter(c => !this.selectedRows.includes(c)), []);
```

I4. **Group selection covers only the current page** — `pkg/rancher-desktop/pages/Containers.vue:18-19` [Codex GPT 5.6 Sol, Claude Opus 4.8]

```
      :paging="true"
      :rows-per-page="10"
```

`groupedRows` is built from `pagedRows` (`grouping.js:27`), so a compose project with more than 10 containers renders a separate group header per page and `groupContainers(group)` returns only that page's slice. The checkbox reports fully-selected while off-page members are untouched, and Stop/Delete acts on a subset of the project the user believes they selected. Paging to the rest does not help: the `pagedRows` watcher (`selection.js:123-136`) drops every row that leaves the page.

Each page's header covers exactly the rows beneath it, so the display stays honest. But it defeats the PR's stated goal of acting on a whole compose project.

Fix: compare against the filtered set rather than the paged set in that watcher, or state the limitation in the PR description.

## Design Observations

### Concerns

- **Bulk Delete silently skips running containers (in-scope)** [Claude Opus 4.8] — the issue asks to delete containers by compose group, and the superseded implementation used `rm -f`. A bulk action is enabled when *some* selected row supports it (`selection.js:100-105`), then `applyTableAction` filters to only the enabled subset (`selection.js:517-521`). Delete is enabled only for stopped containers (`Containers.vue` `getContainerActions`), so selecting a running compose project either greys Delete out or, for a mixed project, deletes only the already-stopped members with no message. The new e2e suite encodes the workaround: test 2 stops the project before test 3 deletes it. This deserves an explicit decision. Either document "stop first", or surface a count of skipped rows.
- **Selection ownership leaks across the component boundary (in-scope)** [Codex GPT 5.6 Sol] — the page mirrors the child's mutable selection, understands `displayRows` wrappers, and invokes an internal method through `$refs`. `SortableTable` should expose `selected`, `indeterminate`, and `setSelected` as group-slot properties keyed off its configured key field. That would centralize identity and pagination semantics in one place.
- **`selectedRows` aliases the table's internal array (future)** [Claude Opus 4.8] — `onSelectionChange` stores the emitted array by reference, which is the table's own reactive `selectedRows`. Any future mutation in the page would corrupt table state with no error; a `[...rows]` copy makes ownership one-way.

### Strengths

- **Reuses the whole bulk-action machinery (in-scope)** [Codex GPT 5.6 Sol, Claude Opus 4.8] — replacing bespoke per-group buttons with a selection checkbox composes across groups, allows excluding individual containers, and applies generically to compose projects, Kubernetes pod groups, and standalone containers.
- **Zero new user-facing strings (in-scope)** [Claude Opus 4.8] — `1ea648735` correctly removed the six `containers.group.*` keys the first commit added, so `en-us.yaml` is untouched in the net diff.
- **Non-obvious coupling is documented (in-scope)** [Claude Opus 4.8] — `groupContainers` explains *why* the unwrap is needed, exactly the kind of comment that earns its place.
- **Flexbox alignment of the group tab controls (in-scope)** [Gemini 3.5 Flash] — the intent is right even though the chosen `display` value regresses the tab shape (I2).

## Review Process Notes

### Skill improvements

- When a finding turns on whether a third-party component supports a prop or renders a state, read the component's shipped implementation in `node_modules` (its compiled template, computed properties, and CSS) rather than trusting the prop name. A component may accept a prop, document it, and still render nothing for it when its own stylesheet gates the visual on a second condition the caller does not satisfy. Verify the render path, not the prop's existence.
- When a page passes two mutually exclusive booleans to one child component, check whether the component's rendering treats them as independent. Props computed as "all" and "some but not all" can never both be true, so any styling that requires both is dead by construction.
- Before reporting that a test file is merely incomplete, run it. Under ESM a mock that omits a named export the module under test imports fails at link time, so the suite reports zero tests rather than a wrong assertion. The difference between "harmless today" and "CI is red" is one command.

### Repo context updates

- [repo] `pkg/rancher-desktop/utils/testUtils/mockModules.ts` builds each mocked module's named exports by spreading the object it is given. Adding a named import from an already-mocked package (`@rancher/components` especially) requires adding a matching stub to every spec that mocks it, or the suite fails to link with `does not provide an export named 'X'` and runs zero tests. Check this whenever a diff adds an import to a component that has a spec.
- [repo] `SortableTable`'s `update(toAdd, toRemove)` in `components/SortableTable/selection.js` matches rows to remove by a hard-coded `_key` field, ignoring the table's own `key-field` prop. Only `Images.vue` sets `key-field="_key"`; the containers table uses `id`, so every removal comparison degenerates to `undefined === undefined` and splices index 0. Treat any new caller of `update()` from a table not keyed on `_key` as broken on the removal path.
- [repo] `SortableTable` styles live in an unscoped block at the bottom of `components/SortableTable/index.vue`. A consuming page's `scoped` style block gains a `[data-v-…]` attribute and therefore outranks those rules at equal class count, so a one-line override in a page can silently restyle the shared component's layout. Check specificity whenever a page overrides a class the component also styles.
- [repo] `SortableTable` groups and paginates in that order: `groupedRows` is computed from `pagedRows`. Group-level operations therefore see only the current page, and the `pagedRows` watcher drops selections when the page changes, so a selection cannot span pages. Any feature acting on "the whole group" needs to account for this.
- [repo] Bulk actions enable when *any* selected row supports the action, then execute against only the subset where it is enabled (`selection.js`). A bulk Delete over a mixed running/stopped selection therefore deletes part of it and reports nothing. Flag new bulk-action surfaces that do not tell the user what was skipped.
