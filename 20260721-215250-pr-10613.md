## Suggestions

S1. **Temp-directory cleanup removes a tree the process still holds open** — `pkg/rancher-desktop/main/update/__tests__/LonghornProvider.spec.ts:46-48` [Claude Opus 4.8]

```ts
afterAll(() => {
  fs.rmSync(tmpDir, { recursive: true, force: true });
});
```

`logsDir` (line 42) reaches the real logging module through the `paths` mock at
line 53, and `Log`'s constructor calls `reopen()`, which opens a `WriteStream`
on `logs/update.log` and never closes it.

On POSIX the unlink succeeds against the open handle. On Windows the name
lingers until the handle closes, so the enclosing `rmdir` can fail and
`afterAll` throws, turning a passing spec into a failing one for a developer
running `yarn test` locally. CI never sees it, because `yarn test` runs only in
the `ubuntu-latest` job (`.github/workflows/test.yaml:22`) while the
`windows-latest` matrix job lints without running jest. Round 2's S2 fix added
this cleanup, so the risk arrived with the fix. The Windows failure is reasoned
from handle semantics rather than reproduced.

Fix: make the cleanup best-effort instead of fatal.

```diff
 afterAll(() => {
-  fs.rmSync(tmpDir, { recursive: true, force: true });
+  // Logging holds `logs/update.log` open for the life of the process, which
+  // can block the directory removal on Windows.
+  try {
+    fs.rmSync(tmpDir, { recursive: true, force: true });
+  } catch {}
 });
```

S2. **The rejection log names the API even when the responder is what changed** — `pkg/rancher-desktop/main/update/LonghornProvider.ts:212` [Claude Opus 4.8]

```ts
      console.log(`Ignoring update staged from ${ cache.apiURL ?? 'an unrecorded source' }.`);
```

`fromCurrentSources` (line 197) rejects when either recorded source differs, but
the message names only `apiURL`. A run that sets `RD_UPGRADE_RESPONDER_URL`
without `RD_GITHUB_API_URL` writes `apiURL: 'https://api.github.com'`, so a
later official launch logs `Ignoring update staged from https://api.github.com.`
That names the one source which does match, and the responder that actually
differed goes unmentioned. `update.log` is the only record of why a staged
update was dropped. The provenance-less wording added in Round 2 reads
correctly; this is the mixed case.

Fix: report both recorded sources.

```diff
-      console.log(`Ignoring update staged from ${ cache.apiURL ?? 'an unrecorded source' }.`);
+      console.log(`Ignoring update staged from ${ cache.apiURL ?? 'an unrecorded source' }` +
+        ` via ${ cache.upgradeServer || 'the configured responder' }.`);
```

S3. **The responder-gate test cannot distinguish "ignored" from "never configured"** — `pkg/rancher-desktop/main/update/__tests__/index.spec.ts:371` [Claude Opus 4.8]

```ts
    await expect(optionsFromFreshSetup()).resolves.not.toHaveProperty('upgradeServer');
```

The fixture at line 332 is `'{}'`, so the parsed options carry no
`upgradeServer` at all. The assertion proves only that the override was not
added, while the test's name describes a configured server surviving. A real

The gate itself stays covered, because removing the `RD_FORCE_UPDATES_ENABLED`

configured server would keep the test green, and that is the mutation this
fixture cannot catch. The sibling `LonghornProvider.spec.ts` passes a configured
server into `makeProvider` (line 470).

```diff

+    fs.writeFileSync(appUpdateConfigPath,
```

S4. **Three `hasQueuedUpdate` cases sit under a `checkForUpdates` describe** — `pkg/rancher-desktop/main/update/__tests__/LonghornProvider.spec.ts:542` [Claude Opus 4.8]

## Design Observations

### Concerns

- `setHasQueuedUpdate` round-trips the parsed cache
  (`LonghornProvider.ts:248-252`), so `apiURL` and `upgradeServer` survive by
  construction rather than by contract. A future rewrite that composes a fresh
  object would strip them and silently reopen the hole this PR closes, with
  every current test still green. [Claude Opus 4.8] (future)

### Strengths

- Gating both overrides on `RD_FORCE_UPDATES_ENABLED` does more than tidy the
  environment. That flag already suppresses the `update-apply` IPC
  (`index.ts:72`) and the queued-install branch (`index.ts:284`), so a run that
  can redirect a release is structurally a run that cannot install one.
  [Claude Opus 4.8] (in-scope)
- Serving the release from a local server, rather than mocking `net.fetch`, is
  what lets the suite catch the bundling class of failure that unit tests cannot
  see. The tiny checksum-backed asset keeps that honest without a large
  download. [Claude Opus 4.8, Codex GPT 5.6 Sol] (in-scope)
- The provenance guard is applied at both readers of the cache
  (`hasQueuedUpdate` at line 211, `checkForUpdates` at line 434), with a comment
  at line 209 stating why one-sided enforcement would not hold.
  [Claude Opus 4.8, Codex GPT 5.6 Sol] (in-scope)
- Centralizing source identity in `updateSources()` keeps cache writes and both
  readers on identical provenance rules. [Codex GPT 5.6 Sol] (in-scope)
- `delete_pending_update` is called from `factory_reset` rather than only from
  the new suite, so the leak it prevents is closed for every bats file. It
  deletes entries inside `$PATH_CACHE` without removing the directory, which
  keeps `factory-reset.bats`'s `assert_exists "$PATH_CACHE"` intact.
  [Claude Opus 4.8] (in-scope)
- The update server uses Node's own `http` module, with no external dependency
  for the test harness to drift against. [Gemini 3.5 Flash] (in-scope)

## Review Process Notes

### Skill improvements

- Set the per-pass agent deadline from the reasoning effort and the assembled
  prompt length, not from diff size alone. A small diff reviewed at maximum
  effort against a long injected context routinely outruns a deadline chosen by
  byte count, and a watchdog kill costs a full retry. When retrying after a
  timeout, budget the retry above the deadline that just expired rather than
  repeating it.

- When injecting prior-round context, state the declined findings and the
  reasons they were declined, but do not tell agents that a clean review is an
  expected outcome. Naming the expected result raises the reporting threshold
  for every reviewer at once, so a round in which most agents return clean then
  carries less information than it appears to.

- Require each reviewer to mark every claimed verification as executed or
  reasoned, and to name what blocked any execution it could not perform. A
  review that announces a test run and then reports no result is
  indistinguishable from one that ran the tests and found nothing.

- Anchor the polling gate's forbidden-path patterns to the review workdir's
  generated outputs rather than matching `review-*.md` anywhere in a command.
  The substring match denies legitimate reads of context files whose names embed
  the word, such as a repository-overview file passed in during setup.

### Repo context updates

- [repo] Reviewers cannot execute the jest suite from a review worktree, because
  the tree carries no `node_modules`. Running jest anyway fails with
  `Cannot find name 'it'`-style errors that read as broken test files rather
  than a missing dependency. Treat any claimed green jest run from a review
  worktree as unverified.

- [repo] `yarn test` runs only in the `ubuntu-latest` job of
  `.github/workflows/test.yaml`; the `windows-latest` and `macos-latest` matrix
  jobs run lint and license checks without running jest. A test failure mode
  specific to Windows or macOS therefore reaches local developers rather than
  CI, and should be severity-rated on that basis.
