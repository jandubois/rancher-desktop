## Executive Summary

The Files tab is a well-shaped first cut. The `ls`/`cp` split is the right design, `withCpStream` is a good abstraction, and the unit suite is real. But all seven defects below reproduce. The worst truncates a host file on a failed download and tells the user nothing. The rest misreport what is in the container. Previews of files well past the 1 MiB cap error out, listings drop entries, and a preview can show the wrong file.

All four reviewers converged on the >1 MiB preview failure, and three of the four on the `ls` parser. I reproduced every Critical and Important finding below against the review SHA, each with a control case showing where the defect does *not* fire, and the reproducers and their output are inline with the findings.

## Critical Issues

C1. **Failed download replaces the chosen host file with a fragment and reports nothing** — `pkg/rancher-desktop/main/containerFiles.ts:437` [Codex GPT 5.6 Sol, Claude Opus 5, Gemini 3.1 Pro]

```ts
        extract.on('entry', (header, stream, next) => {
          if (!wrote && header.type === 'file') {
            wrote = true;
            const out = fs.createWriteStream(destination);

            out.on('error', reject);
            stream.pipe(out);
            out.on('finish', next);
```

`createWriteStream` truncates the destination the moment the first entry arrives, before the copy is known to have succeeded. When `cp` dies mid-archive, `withCpStream` rejects, and the renderer's only handler is `console.error` (`ContainerFiles.vue:333`), so nothing reaches the UI. The user, who chose an existing file in the save dialog, is left with a truncated fragment. Retrying a download after a failure therefore destroys the good copy from the previous attempt. The directory branch at line 421 opens the destination the same way.

```ts repro
// Real handler; the fake cp delivers a tar header plus half of a 40,000-byte
// body, then exits 1, as if the container were removed mid-copy.
fs.writeFileSync(dest, 'ORIGINAL HOST CONTENT');
showSaveDialog.mockResolvedValue({ canceled: false, filePath: dest });
try {
  outcome = `RESOLVED ${ JSON.stringify(await handler.download({ sender: {} }, 'abc', '/f', false, {})) }`;
} catch (ex) {
  outcome = `REJECTED ${ ex.message }`;
}
console.log(`${ outcome } | now ${ fs.readFileSync(dest).length } bytes`);
```

```text repro-output
PROBE-CLOBBER: REJECTED Unexpected end of data | host file was 21 bytes
  "ORIGINAL HOST CONTENT", now 20000 bytes starting "aaaaaaaaaaaa"

control (same handler, archive delivered in full):
PROBE-FILE-DOWNLOAD: result={"canceled":false,"path":"…/f"} fileExists=true
```

Fix: stream into an adjacent temporary file, `rename` it over the destination only after both the tar stream and the child process finish successfully, and unlink it on failure. Add a `containerFiles.errors.download` key and render it, so a failed download says so.

## Important Issues

I1. **Previewing a large file fails instead of showing the truncated prefix** — `pkg/rancher-desktop/main/containerFiles.ts:344-353` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

```ts

              truncated = true;
              const keep = MAX_PREVIEW_BYTES - (total - chunk.length);

              if (keep > 0) {
                chunks.push(chunk.subarray(0, keep));
              }
```

`stop()` kills the `cp` child, closing its stdout mid-entry, so the entry stream never emits `end` and the resolve at lines 355-371 never runs. `tar-stream` instead raises `Unexpected end of data`, which `extract.on('error', fail)` turns into a rejection, so the renderer shows an error banner and `containerFiles.truncated` is unreachable text. Log files are exactly what this feature is for. The unit test at `containerFiles.spec.ts:254` passes because `makeCpProcess`'s `kill` is a no-op `jest.fn()`, and because its 1 MiB + 4 KiB fixture is small enough that the remainder is already buffered.

```ts repro

for (const size of [1024 * 1024 + 4096, 2 * 1024 * 1024, 8 * 1024 * 1024]) {
  const handler = new ContainerFilesHandler({ runClient: fastProducer(size) });
  try {
    const r = await handler.readFile('abc', '/big.log', {});
    log(`RESOLVED truncated=${ r.truncated } size=${ r.size }`);
  } catch (ex) {
    log(`REJECTED ${ ex.message }`);

}
```

```text repro-output
PROBE-SIZE [1 MiB + 4 KiB (fast)]: RESOLVED truncated=true size=1048576   <- the unit test's size
PROBE-SIZE [2 MiB (fast)]:         REJECTED Unexpected end of data
PROBE-SIZE [8 MiB (fast)]:         REJECTED Unexpected end of data
PROBE-TRUNCATE-KILLED (4 MiB, slow producer, real kill): REJECTED Unexpected end of data
```

I2. **The `ls` parser corrupts device nodes and silently returns an empty directory for some `ls` configurations** — `pkg/rancher-desktop/main/containerFiles.ts:173` [Codex GPT 5.6 Sol, Claude Opus 5, Gemini 3.1 Pro]

```ts
      // perms links uid gid size mon day time name...  => at least 9 tokens.
      if (tokens.length < 9) {
        continue;
      }
```

The parser assumes the size is one field and the timestamp is three. Neither holds universally. Block and character devices print `major, minor` in place of the size, which is two fields, so `/dev` entries take the major number as their size and the timestamp as part of their name. A container whose environment sets `TIME_STYLE=long-iso` or `iso` emits an eight-token line, so every entry is skipped; `listViaExec` then returns an empty listing *successfully*, and `list()` never falls back to `cp`, so the directory renders as empty.

Both shapes verified against real GNU coreutils 9.11 output.

```ts repro
// Lines copied verbatim from `gls -lnA` / `TIME_STYLE=long-iso gls -lnA`.
log(handler.parseLsOutput('drwxr-xr-x 1173 0 0 37536 Aug 12 19:51 man1'));
log(handler.parseLsOutput('drwxr-xr-x 1173 0 0 37536 2026-08-12 19:51 man1'));
log(handler.parseLsOutput('crw-rw-rw- 1 0 0 3, 2 Sep  4 11:56 /dev/null'));
// dispatch: exec succeeds with long-iso output; cp throws if reached.
log(await handler.list('abc', '/usr/share/man', { running: true }));
```

```text repro-output
PROBE-LS-DEFAULT:  [{"name":"man1","type":"directory","size":37536,"modeString":"rwxr-xr-x"}]
PROBE-LS-LONGISO:  []
PROBE-LS (device): [{"name":"11:56 /dev/null","type":"other","size":3,…}]
PROBE-LS-DISPATCH: RESOLVED {"entries":[],"truncated":false}   <- no cp fallback
```

Fix: match the whole line with an anchored regex that makes the `, minor` group optional, and treat "the command succeeded but nothing parsed" as a listing failure so `list()` falls back to `cp`. Pinning `LC_ALL=C` and `TIME_STYLE=long-iso` through `exec env …` narrows the input but does not remove the device-node case.

I3. **A stopped container's root listing silently drops top-level entries once the entry cap is hit** — `pkg/rancher-desktop/main/containerFiles.ts:253` [Claude Opus 5, Codex GPT 5.6 Sol]

```ts

            truncated = true;
            // We have scanned enough; stop the copy and return what we have.
            stop();
```

The main process does mark the result, but `loadChildren` (`ContainerFiles.vue:246`) returns only `result.entries` and drops `truncated`, and no `en-us.yaml` key exists for it, so the tree renders a one-entry root that is indistinguishable from a real one.

## Suggestions

S1. **The directory-download path has no caller** — `pkg/rancher-desktop/components/ContainerFiles.vue:332` [Claude Opus 5, Codex GPT 5.6 Sol]

```ts
    await ipcRenderer.invoke('container-files/download', props.containerId, selectedPath.value, false, ipcOptions());
```

`isDirectory` is hard-coded `false`, and `selectedPath` is only ever set for non-directory nodes, so the `.tar` branch at `containerFiles.ts:419`, the `.tar` default filename at line 403, and the directory test at `containerFiles.spec.ts:369` all cover unreachable code.

Fix: wire a download action onto directory rows ("I forgot to mount that output directory" is the PR's own motivating story, and the tar path already works), or drop the parameter until there is a caller.

S2. **Any terminating signal counts as a successful copy** — `pkg/rancher-desktop/main/containerFiles.ts:495` [Codex GPT 5.6 Sol]

```ts
      proc.on('exit', (code, signal) => {
        if (stoppedEarly || code === 0 || signal) {
          resolve();
```

`stoppedEarly` already identifies the intentional stop, so the extra `|| signal` accepts an external `SIGKILL` (an OOM kill, say) as success. A half-written directory archive is then reported as downloaded.

Fix: resolve only for `stoppedEarly || (code === 0 && signal === null)`, and reject naming the signal otherwise.

S3. **The module docstring says listing does not read file contents; it only avoids keeping them** — `pkg/rancher-desktop/main/containerFiles.ts:11` [Claude Opus 5, Codex GPT 5.6 Sol]

```ts
 *    archive of the path.  We parse only the tar headers, so no file contents
 *    are read while listing.
```

`tar-stream` must drain each entry body to reach the next header (`stream.resume()`, line 296), so every byte still crosses the pipe. Listing a stopped container with a 3 GB layer transfers 3 GB. A reader of this comment will conclude listing is cheap.

Fix: say the bodies are discarded as they stream past, but the archive is still transferred in full, so listing costs time proportional to the subtree's on-disk size.

S4. **Raw Electron IPC wrappers reach the user, and the translated fallbacks never do** — `pkg/rancher-desktop/components/ContainerFiles.vue:257` [Claude Opus 5]


`ipcRenderer.invoke` rejections always include a message, of the form `Error invoking remote method 'container-files/list': …`. The `errors.list` and `errors.read` keys are therefore dead, and what users see is untranslated and leaks the channel name.

## Design Observations

### Concerns

- **The tar stream already holds the whole subtree, and the code throws it away and re-fetches it on every expansion** `(future)` [Claude Opus 5]. `listViaCp` streams `cp <id>:<dir> -` in full but keeps only immediate children, so expanding `/`, then `/usr`, then `/usr/lib` transfers `/usr/lib` three times. Building the full node tree from one stream, bounded by the same cap, and caching it per container for the life of the tab would make the stopped-container path one transfer per session, and would delete the "infer the intermediate directory" branch. The PR description already anticipates revisiting this against the v2 backend.

- **Nothing cancels an abandoned copy** `(in-scope)` [Claude Opus 5]. Switching tabs destroys the component but leaves the `cp` child running; `updateClient` swaps the client without killing outstanding children, where the sibling handlers tear down explicitly (`ContainerStatsHandler.stopAll`, `ContainerExecHandler.killAll`). `runClient` already accepts an `AbortSignal`. Claude rated this Important; I moved it here because I did not reproduce a user-visible failure from it, only the missing teardown.

- **Two divergent `ls -l` parsers now exist in the tree** `(in-scope)` [Claude Opus 5]. `pages/volumes/files/_name.vue:341` already parses `ls` output for the volume browser using an anchored regex over `ls -la --full-time`; this adds a second, positional parser that accepts strictly more input and mangles some of it (I2). One exported helper with one test suite would give the edge cases a single home.

- **Handlers register from the constructor, which only runs once the backend starts** `(future)` [Claude Opus 5]. Until then `container-files/*` rejects with Electron's "No handler registered", and unlike Shell the Files tab is never disabled, so a user reaching it during startup sees that raw message (compounded by S4). The `containerExec` and `containerStats` handlers share the shape, so this is a class issue rather than a regression.

### Strengths

- The dual mechanism is well chosen [Claude Opus 5, Gemini 3.1 Pro]: `ls` for the cheap common case, `cp`/tar as a universal fallback needing nothing inside the image. Reads and downloads always take the tar path, so they behave identically whether or not the container is running.
- `withCpStream` is a good abstraction [Claude Opus 5, Gemini 3.1 Pro]: one place owns the child's lifetime, stderr capture, the "stopped early means success" rule, and the ordering that surfaces a copy failure even when the tar parsed without error, a detail the error tests pin.
- Engine arguments are passed as arrays rather than through a shell, so container paths and names cannot inject commands [Codex GPT 5.6 Sol].
- File contents, names and symlink targets render through `{{ }}` interpolation, never `v-html` [Codex GPT 5.6 Sol, Gemini 3.5 Flash], which matters in this Node-enabled renderer.
- The IPC surface is fully typed and documented per channel in `electron-ipc.d.ts`, and the component imports the result types with `import type` [Claude Opus 5].

3. **Downloads have no e2e coverage and no failure-path coverage.** The unit tests drive `handler.download` directly with a clean archive, so neither the renderer wiring nor the mid-stream failure that costs a host file (C1) is tested.
4. **No test issues two overlapping `list`/`read` calls**, so I4 and the `refresh()` race are invisible to the suite.
5. **The containerd/nerdctl engine is untested.** Both new e2e describes pin `ContainerEngine.MOBY`; `nerdctl cp` reaches stopped containers by mounting the snapshot rather than entering a task namespace, and its archive layout is exactly the input the wrapper heuristic guesses at.

## Review Process Notes

### Skill improvements

- When a test suite exercises a code path that ends in terminating a child process, closing a socket, or cancelling a stream, check what the test double does for that terminating call. A double that records the call without performing it lets the test follow the uninterrupted path, so the suite is green where production is not. Report the gap against the test, and prove the production behaviour with a double that actually severs the stream.
- When a reproducer's output is quoted in a finding, treat it as a claim to verify rather than as evidence. Re-run it, or compare the quoted output against strings the code can emit. A message that appears nowhere in the implementation or its dependencies means the block was written, not executed, and the finding then rests on nothing but the reading behind it.

### Repo context updates

- `[repo]` The Vue jest transform at `pkg/rancher-desktop/utils/testUtils/vue-jest.js` compiles only a plain `<script>` block (`descriptor.script`); it ignores `<script setup>`, so mounting any `<script setup>` SFC under jest fails with `ReferenceError: __default__ is not defined`. Several container components are written that way and consequently have no unit tests at all, only Playwright coverage. When a review needs to reproduce renderer behaviour in one of them, supply a scratch transform built on `compileScript(descriptor, { inlineTemplate: true })` and point jest at it with `--config`; do not report the absence of component tests as an oversight by the change's author without noting this constraint.
- `[repo]` `docker cp` and `nerdctl cp` do not follow symlinks unless `-L/--follow-link` is passed, so a tar streamed from `cp <id>:<path> -` contains a `symlink` entry with no body whenever the final path element is a link. Code that filters tar entries to `type === 'file'` silently produces nothing for such a path. On Debian-derived images `/bin`, `/lib` and `/sbin` are symlinks, so this is a common path.
- `[repo]` The repo has two `ls -l` output parsers. One is in `pages/volumes/files/_name.vue`, an anchored regex over `ls -la --full-time`; the other is in `main/containerFiles.ts`, a positional split over `ls -lnA`. When reviewing either, check the other for the same input class. Device nodes print `major, minor` in place of the size, and `TIME_STYLE=long-iso`/`iso` collapse the timestamp to two fields; both shift the positional offsets.

### Design Observations

**Concerns**

- **The tar stream already contains the whole subtree; the code throws it away and re-fetches it per expansion** *(future)*. `listViaCp` streams `cp <id>:<dir> -` in full but keeps only the immediate children (`containerFiles.ts:279-293`), so expanding `/`, then `/usr`, then `/usr/lib` transfers `/usr/lib` three times, and the root expansion transfers the entire filesystem. Building the *full* node tree from that single stream — bounded by `MAX_LIST_ENTRIES` exactly as today — and caching it per `containerId` for the life of the tab would make the stopped-container path one transfer per session instead of one per click, with strictly less code (the "infer the intermediate directory" branch at lines 289-292 disappears, since deeper entries become real nodes). It also removes the wrapper-segment heuristic's dependence on knowing `dirPath`'s basename. The obvious cost is memory for very large trees, which the existing cap already bounds.

- **Two divergent `ls -l` parsers now live in the tree** *(in-scope)*. `pages/volumes/files/_name.vue:341` already parses `ls` output for the volume browser, using an anchored named-group regex over `ls -la --full-time`; `containerFiles.ts:160` adds a second, positional parser over `ls -lnA` that accepts strictly more input and mangles some of it (I1). They will drift. Extracting one exported `parseLsLongFormat(stdout)` into `pkg/rancher-desktop/utils/` and having both call it — with the volume browser keeping its `--full-time` invocation and the container browser its `-lnA` — costs one small module and gives the device-node and whitespace edge cases a single home with a single test suite.

- **`ContainerFilesHandler` registers IPC handlers from its constructor but is constructed only in `startK8sManager`** *(future)*. `background.ts:611-616` guards re-construction, so this is correct today, but until the backend has started once, `container-files/*` rejects with Electron's "No handler registered" — the Files tab is enabled unconditionally (`ContainerInfo.vue:42-47`, unlike Shell's `:disabled="!isRunning"`), so a user reaching the tab during startup gets that raw message in the error banner. The pre-existing `containerExec`/`containerStats` handlers share the shape, so this is a class issue rather than a regression; registering the handlers at module load and having them fail with a translated "engine not ready" would fix all three.

**Strengths**

- The dual mechanism is well chosen: `ls` for the cheap common case, `cp`/tar as a universal fallback that needs nothing inside the image — and reads and downloads always take the tar path, so they behave identically whether or not the container is running.
- The `withCpStream` helper (`containerFiles.ts:464-518`) is a genuinely good abstraction: one place owns the child's lifetime, stderr capture, the "stopped early means success" rule, and the "surface the copy failure even when the tar parsed cleanly" ordering at line 508 — a detail that is easy to get wrong and that the error-handling tests actually pin.
- The wrapper-segment tolerance in `listViaCp` (lines 265-277) handles `./`-rooted, base-name-rooted and unwrapped archives uniformly instead of special-casing one engine, and the regression tests added in 074c1c0ee document exactly which shape each engine emits.
- The IPC surface is fully typed in `electron-ipc.d.ts` with doc comments on each channel, and the component imports the result types with `import type`, so no main-process code leaks into the renderer bundle.

### Executive Summary

The Files tab cleanly separates renderer and main-process responsibilities and adds useful Moby E2E coverage. However, previews over 1 MiB deterministically fail, interrupted downloads can silently replace host files with partial data, asynchronous reads can display the wrong file, and several listing states are misrepresented. These correctness and accessibility gaps should be addressed before merge.

### Findings

#### Critical Issues

None.

#### Important Issues

I1. **Stopping a large preview makes `tar-stream` reject it** — `pkg/rancher-desktop/main/containerFiles.ts:340-383` (important, gap)

```ts

  truncated = true;
  const keep = MAX_PREVIEW_BYTES - (total - chunk.length);

  if (keep > 0) {
    chunks.push(chunk.subarray(0, keep));
  }
  // Stop pulling more of this file from the container.
  stop();
}
```

The kill at line 352 closes stdout before the current tar entry reaches its declared size. Pinned `tar-stream@3.2.0` consequently emits `Unexpected end of data`; line 383 rejects before the success path at lines 355-369 runs. The failure is loud—the preview displays an error—but every file over 1 MiB misses the advertised truncated preview. The test at `containerFiles.spec.ts:254-265` misses this because its `kill()` is a no-op at line 50.

```js repro

extract.on('entry', (_h, body, next) => {
  body.resume();
  body.on('end', next);
```

```text repro-output

```

Fix: Resolve the capped result and mark the consumer settled before killing/unpiping the process, then ignore only the expected extractor error from that intentional stop. Update the process fake so `kill()` closes stdout and emits a signal.

S1. **Any signal is treated as a successful copy** — `pkg/rancher-desktop/main/containerFiles.ts:492-499` (suggestion, gap)
