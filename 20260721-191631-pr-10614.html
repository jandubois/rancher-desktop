S1. path.extname rejects a valid dotted subpath Codex GPT 5.6 Sol Claude Opus 4.8¶
scripts/lib/build-utils.ts
 * no extension resolution.  Packages that publish an `exports` map resolve
 * their own subpaths, so try the request unchanged as well.  A request that
 * resolves no way at all would fail once packaged, so fail the build instead.
 */
function externalSpecifier(request: string): string {
  const candidates = path.extname(request) ? [request] : [`${ request }.js`, request];

  for (const candidate of candidates) {
    if (canResolve(candidate)) {
      return candidate;
    }

path.extname treats any dotted final segment as an extension, so a request like package/schema.v1 yields the single candidate package/schema.v1 and never tries an existing package/schema.v1.js. Line 53 then throws.

Verified by probe: a subpath whose real file is .cjs or .mjs throws the same way. That failure is loud and lands at build time, so it costs a confusing build break rather than a broken release. No current dependency uses either shape, and chart.js, the only dotted dependency name, resolves correctly as a bare request.

Fix: treat the suffixed candidate as a fallback rather than gating it on extname, so a dotted subpath still gets the .js probe.

Testing Assessment ¶

The new describe('externals') block is real integration coverage: it resolves against actual node_modules rather than mocks, and the negative cases match on the error message. The suite runs (22 tests pass) under the repo's node --experimental-vm-modules invocation.

Untested scenarios, ranked by risk:

  1. Named-export visibility across the externals boundary (S2). The current assertions would pass while the app was broken in the original way.
  2. Resolver edges (S1). No case covers a dotted extensionless subpath or a non-.js extension. Both throw today, so a test would pin the message rather than catch a silent failure.
  3. exports-map redirection. Every passing subpath in the table resolves via ${request}.js, so the "try the request unchanged" branch on line 46 is reached only by the failing cases.
  4. Optional-dependency absence. If posix-node ever fails to install, the externalizes posix-node case fails with a resolution error rather than a diagnosable skip. It ships prebuilt bindings with no install script, so this is remote.

Documentation Assessment ¶

The docstrings on canResolve, externalSpecifier, externalsEntry, and runtimeDependencies explain why rather than what, which is the harder half.

The canResolve docstring (lines 25-29) is accurate, including its claim that the directory import is the residual limitation. A probe confirmed the distinction: a subpath whose real file is .cjs or .mjs throws at build time, while a directory subpath resolves to a specifier Node later rejects with ERR_UNSUPPORTED_DIR_IMPORT. The directory case really is the only shape that ships silently, so the comment names the right one.

No user-facing documentation is affected. Separately, and outside this PR's scope: 1.23.0/1.23.1 users cannot auto-update to the build carrying this fix, so the next patch's release notes still need the manual-install note.

Review Process Notes ¶

Skill improvements

  • Before rating a finding by its blast radius, determine whether the failure it describes is loud or silent, and say which. A guard that rejects a bad input at build time costs a confusing CI break; the same input accepted and shipped costs a broken release. Reviewers routinely describe the second while the code does the first, because a fallback branch reads as permissive until you trigger it. Construct the input the finding names, run the build, and record what happened. Where the failure is loud, the finding is usually a Suggestion, not an Important issue.
  • When a finding claims a module's exports will be invisible across a CommonJS-to-ESM boundary, import the module and check each name the consumers actually use, distinguishing a true named export from a property reachable only through default. Static analysis of the exporting source does not settle it, because the loader's export detection succeeds on some export-assignment shapes and fails on others. Enumerate the consumers' named imports first, then verify that exact list; a finding that names the boundary without naming the consumed symbols has not been checked.

Repo context updates

  • [repo] The main-process webpack externals in scripts/lib/build-utils.ts throw when a dependency subpath resolves no way at all, and .github/workflows/test.yaml runs yarn build before yarn test, so an unresolvable subpath fails CI rather than shipping. The resolution probe runs under tsx, which is more permissive than the ESM loader in the packaged app: a subpath whose real file carries a non-.js extension throws at build time, while a directory-style subpath resolves and ships a specifier Node later rejects with ERR_UNSUPPORTED_DIR_IMPORT. When reviewing changes to this resolution logic, treat the directory case as the only silent-failure shape, and verify a claimed silent failure by triggering it.
  • [repo] The preload bundle resolves no external of any kind. Electron loads resources/preload.js into a sandboxed renderer from outside the asar (sandbox: true in pkg/rancher-desktop/window/index.ts, resources/ shipped via extraResources in packaging/electron-builder.yml), so it reaches neither npm packages nor the app's node_modules. webpackPreloadConfig therefore clears externals outright rather than changing the external type. A suggestion to give the preload a CommonJS external type is wrong for this repo: electron stays external through webpack's electron-preload externalsPresets, independently of externals.
