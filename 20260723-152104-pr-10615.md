## Suggestions

S1. **The `checksInFlight` counter is not incremented for the startup check** — `pkg/rancher-desktop/main/update/index.ts:365` [Codex GPT 5.6 Sol]

```ts
      autoUpdater.checkForUpdates().then((result) => {
```

The counter's comment (`index.ts:68-74`) says it tracks "how many update checks are in flight," and the `error` handler releases the install latch only when it is zero (`index.ts:166`). But only `triggerUpdateCheck` increments it (`index.ts:397`); the cached-startup path in `doInitialUpdateCheck` calls `checkForUpdates()` directly here without counting. It is safe today — the renderer gates install on `updateReady` (`UpdateStatus.vue:167`) and startup cannot offer one until `update-downloaded` — so no install can be pending during this check. But the classifier now rests on an unstated call-site invariant that a future direct caller would silently break.

Fix: extract a counted `runUpdateCheck()` wrapper used at both sites, or rename to `periodicChecksInFlight` and document why startup cannot overlap an install.

S2. **The test `beforeEach` reset silently depends on `checksInFlight === 0`** — `pkg/rancher-desktop/main/update/__tests__/index.spec.ts:132` [Claude Opus 4.8]

```ts
    updater.emit('error', new Error('reset'));
```

The reset emits `error` to clear an `installStarted` latch a prior test may have left set. But the production handler (`index.ts:166`) releases the latch only when `checksInFlight === 0`. Every current test balances the counter — each unsettled `checkForUpdates()` promise is later rejected and flushed — so the reset works today. A future test that leaves a check in flight would make this reset silently no-op, leaking `installStarted` into the next test as an order-dependent flake with no obvious cause.

Fix: make the reset independent of counter balance — reset the module (`jest.resetModules()` + re-import) in `beforeEach`, or at minimum state the precondition in a comment so the dependency is visible.

S3. **The renderer clears `applying` on any error, so a check error can re-enable a dead Restart button** — `pkg/rancher-desktop/components/UpdateStatus.vue:139` [Gemini 3.1 Pro]

```ts
    updateState() {
      // The main process has reported the outcome of the retry.
      this.retrying = false;
      if (this.updateState?.error) {
        // Applying failed. The application is still running and the update is
        // still on disk, so the button has to come back.
        this.applying = false;
      }
```

The watcher treats any `error` as an install failure and re-enables Restart Now. But the main process keeps running checks after Apply, and its `installStarted` latch can stay set — after a cancelled quit (no `error` fires), or the accepted I2 residual (an install failure coinciding with an in-flight check). If a later check then errors, the renderer clears `applying` and re-enables the button, yet `update-apply` is still gated (`index.ts:84`), so the click is silently ignored — a live-looking dead button. Gemini 3.1 Pro rated this Important; Claude, Codex, and Flash treat it as accepted, since every path to a stuck latch is either the pre-existing force-restart-zombie state or the rare residual the in-code comments (`index.ts:169-172`, `391-395`) already document. No data loss; a restart recovers.

Fix: let the main process own the latch — send it in `UpdateState` — rather than have the renderer infer it from `error`.

## Review Process Notes

### Skill improvements

- When a fix's or finding's correctness turns on a third-party dependency's ordering between emitting a callback/event and settling its returned promise (for example "emits `error` before the promise rejects"), verify it against the pinned dependency's own source, not the test's mock. A mock hard-codes whichever ordering the author assumed, so it passes whether or not production honors it; only the dependency's source can confirm the assumption. Read it from the installed package at the pinned version, since a newer upstream may have reordered the two.

### Repo context updates

- [repo] electron-updater's `AppUpdater.checkForUpdates()` (pinned 6.8.9, `out/AppUpdater.js`) emits its `error` event synchronously *before* the returned promise settles: the internal `.catch` runs `this.emit("error", e, …)` and then re-throws. So a main-process `error` handler runs while the check is still "in flight" — code that classifies a failure by whether a check is currently running can rely on that in-flight state being observable during the error. Confirm the ordering still holds after any electron-updater bump.
- [repo] UPDATE the updateState-field-ownership entry: `checking-for-update` clears `error`, `downloaded`, and `progress` but **no longer clears `available`**; `available` is now owned solely by the definitive `update-available` (sets true) and `update-not-available` (sets false) events, so it survives a check that errors before either fires. A finding that assumes `checking-for-update` retracts the card by zeroing `available` is out of date.
