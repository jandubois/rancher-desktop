## Executive Summary

This PR adds runtime i18n: a main-process ICU translator mirroring the renderer store, a shared translation loader, localized validator errors classified through a structured `hasLockedFieldError` flag, and an experimental language picker. The design is coherent and well tested. Two Important gaps remain: one validator caller still regex-parses the now-localized lock message, and the bundled `zh-hans.yaml` makes Chinese a selectable, validator-accepted locale that the command-api enum rejects.

All three reviewers converged on both Important issues (Codex and Claude on each; Gemini added a latent lock-path defect downgraded here to S3). No finding contradicted another. The remaining suggestions are cleanup: a dead import, two parallel `t()` implementations that drift, README references to tooling not on this branch, and dead arguments at ~20 call sites. The escaping-model change (raw output, sinks escape) was audited safe.

## Important Issues

I1. **`checkForLockedVersion` still parses the now-localized lock message** — `pkg/rancher-desktop/backend/backendHelper.ts:176` [Codex GPT 5.5, Claude Opus 4.8]

```ts

        throw new LockedFieldError(`Error in deployment profiles:\n${ errors.join('\n') }`);
```

This caller was missed. `checkForLockedVersion` receives the same `SettingsValidator` and calls `sv.validateSettings()` one line above, so `sv.hasLockedFieldError` is in hand — yet it still matches `/field ".*" is locked/`. Fix:

```diff
-      if (errors.some(err => /field ".*" is locked/.exec(err))) {
+      if (sv.hasLockedFieldError) {
```

I2. **Picker and validator expose a `zh-hans` locale the API enum rejects** — `pkg/rancher-desktop/assets/specs/command-api.yaml:602` [Codex GPT 5.5, Claude Opus 4.8]

```yaml
            locale:
              type: string
              # Keep in sync with the translation files and settingsValidator.ts;
              # run `i18n-report check --locale=all` to catch mismatches.
              enum: [none, en-us]
```

`translationLoader` derives `availableLocales` from every `.yaml` file present, returning `en-us` and `zh-hans`. The picker iterates that list and the validator gates on it (`settingsValidator.ts:104`), so the UI offers 简体中文 and accepts `zh-hans` — yet this hand-maintained enum lists only `[none, en-us]`. The GUI and CLI contract disagree, and a user can persist a locale the schema forbids. `zh-hans.yaml` predates this PR and stayed untouched while `en-us.yaml` was rewritten (+703/−799); `i18n-report validate --locale=zh-hans` reports 2370 errors, so selecting it yields a mostly-English UI, contradicting "no locale ships yet." No gate catches this: `check-api-schema.ts` skips enums, and the registration check is on a separate track.

Fix: pick one source of truth for shippable locales. Either add `zh-hans` to the enum and the registration tests once it is retranslated, or gate the picker and validator to a curated ready-set and move `zh-hans.yaml` out of the bundled tree until then.

S2. **The main and renderer `t()` implementations drift** — `pkg/rancher-desktop/main/i18n.ts:92` [Codex GPT 5.5, Claude Opus 4.8]

```ts
  const stringArgs = args && Object.fromEntries(Object.entries(args)
    .map(([name, value]) => [name, typeof value === 'number' ? value : String(value)]));
```

The two translators consume the same YAML but behave differently. The renderer injects `{ vendor, appName }` into every format call (`store/i18n.js:87`); the main process does not, so a key using `{appName}` renders in the renderer and degrades to the raw pattern in the main process. They also differ on ICU detection (main tests `includes('{') || includes("'")`, the store only `includes('{')`) and on key-path splitting (the renderer's `get()` uses `splitObjectPath`, which handles quoted dotted segments; the main helper splits on every dot). All are latent today, since the main process translates only `validation.*` keys, which use none of these — but the divergences are footguns as main-process menus and titles get wired up.

Fix: extract one shared formatting core consumed by both the store getter and the main-process `t`.

S3. **Root-level lock check re-derives a leading-dot path instead of using `fqname`** — `pkg/rancher-desktop/main/commandServer/settingsValidator.ts:285` [Gemini 3.1 Pro]

```ts

```

`checkProposedSettings` already computed `fqname` for this field, yet re-derives the path here and in the error at line 291. When `prefix` is empty (a root-level leaf such as `version`), the string gains a leading dot; `_.get(lockedSettings, '.version')` reads the path as `['', 'version']` and returns `undefined` (verified), so a lock on a root-level setting is bypassed and the text reads `field ".version" is locked`. This is pre-existing and currently unreachable — the only root-level leaf, `version`, uses `checkUnchanged`, which never reports a change — but the PR edits this exact line, and `fqname` fixes both the lookup and the message for free.

Fix: replace both `${ prefix }.${ k }` occurrences with `fqname`.

## Review Process Notes

### Skill improvements

- **Localizing a machine-read string breaks its parsers.** When a change converts a signal that code elsewhere pattern-matches — an error string, status text, or label — into localized or otherwise user-facing text, search the whole codebase for every consumer that parses or regex-matches that text, not just the files in the diff. Localization silently defeats string-based classification, and the broken consumer usually sits in an untouched file. Flag any parser of a now-localized string and prefer a structured signal (flag, error subclass, status code) over the parse.
- **Runtime-discovered value sets drift from their hand-declared mirrors.** When a set of valid values is discovered at runtime from the filesystem (a glob, directory read, or bundler context) yet also declared by hand elsewhere — an API or schema enum, a validator list, a UI menu — treat the pair as a drift risk. Enumerate every hand-maintained mirror and check it against what discovery actually yields; a stray or stale file on disk can widen the runtime set past the declared contract with no code change in the diff.

### Repo context updates

- [repo] The app's `pkg/rancher-desktop/assets/translations/` directory is the source for `availableLocales` via `utils/translationLoader.ts`, which reads every `*.yaml` file present. Any locale file in that directory becomes selectable in the Preferences picker and accepted by `settingsValidator`'s `checkEnum('none', ...availableLocales)`, independently of the `command-api.yaml` `locale` enum and the Go/rdctl contract generated from it. When reviewing i18n or settings changes, cross-check the on-disk locale files against the command-api enum — the two are maintained separately and drift silently.

# Deep Review — PR #10618: Add runtime i18n with a language picker in Preferences

| | |
|---|---|

## Executive Summary

The PR adds a main-process ICU translator mirroring the renderer store, a shared `translationLoader`, localized `settingsValidator` errors classified via a structured `hasLockedFieldError` flag, and an experimental language picker. The escaping-model change (raw output, sink escapes) is sound, documented, and safe — every HTML sink uses `raw`/`v-clean-html`. Two gaps stand out: one validator caller (`backendHelper.ts`) still regex-parses the now-localized "is locked" message, and the selectable-locale set is derived three inconsistent ways, exposing a stale `zh-hans` the CLI schema rejects.

## Critical Issues

None.

## Important Issues

I1. **`checkForLockedVersion` still parses the now-localized lock message** — `pkg/rancher-desktop/backend/backendHelper.ts:176` (important, gap)

```js
if (errors.some(err => /field ".*" is locked/.exec(err))) {
  throw new LockedFieldError(`Error in deployment profiles:\n${ errors.join('\n') }`);
}
```

This PR's stated design is "callers classify errors via `hasLockedFieldError` instead of parsing text," and it migrated `commandLineOptions.ts:142` to do exactly that. But `checkForLockedVersion` — which receives the same `SettingsValidator` (`sv`) and calls `sv.validateSettings(...)` at line 173 — was missed. The lock message is now `t('validation.fieldLocked', …)` (settingsValidator.ts:290). It matches this regex only while it resolves to English via fallback; the moment a shipped locale translates `validation.fieldLocked` (the explicit goal of the follow-up PRs), this branch stops firing and a locked deployment-profile version is misreported as a generic error. This reintroduces the exact fragility the PR set out to remove.

Fix:
```diff
-    if (errors.some(err => /field ".*" is locked/.exec(err))) {
+    if (sv.hasLockedFieldError) {
```

I2. **Selectable-locale set is derived three inconsistent ways; the picker exposes a stale, unshipped `zh-hans`** — `pkg/rancher-desktop/assets/specs/command-api.yaml:602` (important, gap)

```yaml
              enum: [none, en-us]
```

The picker (`store/i18n.js` `availableLocales`, fed by `translationLoader`) and the validator (`settingsValidator.ts:104`, `checkEnum('none', ...availableLocales)`) both derive their locale set from the `.yaml` files on disk — `en-us` **and** `zh-hans`. So the GUI offers "简体中文" and the validator accepts `zh-hans`, but this hand-maintained enum lists only `[none, en-us]`, and the PR states "no locale ships yet." `zh-hans.yaml` was not touched by this PR while `en-us.yaml` was rewritten (+703/−799), so it is badly out of sync — selecting it yields a mostly-English-fallback UI. The result: GUI and CLI/API contract disagree on valid values, and users can persist a locale the schema forbids. No gate in this PR catches it (`check-api-schema.ts` explicitly skips enums; the `i18n-report` registration check is on a separate track).

Fix: pick one source of truth for "shippable" locales. Either add `zh-hans` to the enum once it is retranslated, or gate the picker/validator to a curated ready-set and remove/relocate `zh-hans.yaml` from the bundled tree until then.

## Suggestions

S1. **Dead `t` import in the main entry point** — `background.ts:34` (suggestion, gap)

```ts
import { initMainI18n, t } from '@pkg/main/i18n';
```

`t` is never called in `background.ts` (only `initMainI18n` is). This is a dead import that `@typescript-eslint/no-unused-vars` will flag — confirm it is not already failing lint on this SHA.

Fix: `import { initMainI18n } from '@pkg/main/i18n';`

S2. **The main and renderer ICU engines diverge in ways that will surprise a shared corpus** — `pkg/rancher-desktop/main/i18n.ts:62-105` (suggestion, gap)

The two `t()` implementations differ: the store auto-injects `{ vendor, appName }` into every format call (`store/i18n.js:88`), the main process does not — so a key using `{appName}` renders correctly in the renderer but degrades to the raw pattern in the main process (latent today: no `validation.*` key uses them). They also differ on the ICU-detection heuristic (main tests `includes('{') || includes("'")`, store only `includes('{')`), and on cache lifecycle (store clears `intlCache` on switch, main relies on the locale-prefixed key). Since both consume the *same* YAML, these divergences are footguns as main-process menus/titles get wired up. Consider sharing one formatting core.

S3. **README documents files and a directory that do not exist** — `pkg/rancher-desktop/assets/translations/README.md:11,23` (suggestion, gap)

The Files table lists `zh-hans.yaml | Simplified Chinese translation` and `de.yaml | German translation`, but there is no `de.yaml` in the tree; the German examples throughout are illustrative only. Line 23 states "The `meta/` subdirectory holds per-locale metadata" — no `meta/` directory exists yet. Align the doc with the tree (drop `de.yaml`, or mark both as illustrative/planned).

S4. **The `t` global-property contract dropped its third parameter, orphaning ~43 call sites** — `pkg/rancher-desktop/plugins/i18n.js:30-32` (suggestion, gap)

The new global `t(key, args)` silently ignores the old `raw` third argument, yet ~43 call sites still pass `t(key, args, true)` (e.g. `Nav.vue:23`, `SnapshotCard.vue:84`). Behavior is preserved because raw is now the default and none of the surveyed HTML sinks relied on the old escaped default — but the dead arguments mislead readers into thinking the flag still does something. Sweep them in a follow-up (the `i18n-report` tooling can locate them).

## Design Observations

**Concerns**

- **Unused locale-change callback machinery** (`main/i18n.ts:17,113-123,144-160`) — `onLocaleChange`/`localeChangeCallbacks` has no caller anywhere in `pkg/`. The README's "Callback lifecycle" note frames it as future infrastructure (tray show/hide), but shipping an exported registration API plus its dispatch loop with zero consumers is speculative. Consider landing it with its first consumer. *(future)*
- **Two parallel ICU translators** — see S2. A single shared `translate(map, locale, key, args)` core consumed by both the store getter and the main-process `t` would eliminate the divergence class rather than documenting each instance. *(future)*
- **`none` repurposed; the `%key%` debug mode is gone** — the old store treated `selected === 'none'` as "render every string as `%key%`" (a coverage-audit aid), toggled by the now-deleted `toggleNone`. The new code maps `none → en-us` everywhere, so that debug mode is silently removed. No external caller used `toggleNone`/`selectedLocaleLabel`/`previous`, so removal is safe, but note the lost capability. *(in-scope)*

**Strengths**

- The shared `translationLoader` unifies webpack/jest/tsx loading and its `recursive: false, /\.yaml$/` filter fixes the old "any file under `translations/` becomes a locale" footgun (README.md now lives safely in that tree).
- The escaping model (raw output, sink escapes; `v-clean-html` for interpolated external data) is coherent, documented, and well tested — and the audit confirms the sole `v-t` directive usage is plain text and no 2-arg `t()` reaches an unsanitized HTML sink.
- `hasLockedFieldError` is the right structured-classification replacement for regex-sniffing localized text (its absence at one call site is I1, not a knock on the approach).
