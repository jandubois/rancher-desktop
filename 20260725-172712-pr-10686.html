Executive Summary ¶

The PR ignores the undici status-0 RangeError that Electron's net.fetch throws from its own 'response' listener, a real defect no call-site try/catch can reach. But registering any uncaughtException listener makes Electron's built-in handler bail out, so the "A JavaScript error occurred in the main process" dialog disappears for every exception, including the one in the issue this PR cites. Suppressing the throw also leaves the originating fetch promise pending forever.

All four reviewers flagged the global side effect; three misdiagnosed its mechanism as a lost process exit. Findings below use the corrected mechanism, verified by probe.

Design Observations ¶

Concerns ¶

  • A global exception filter is the wrong layer for a per-call-site failure (in-scope) Claude Opus 5 Codex GPT 5.6 Sol. One library call cannot settle its promise, and the compensation is a process-wide switch in background.ts that knows nothing about which request failed. A shared netFetch() wrapper in @pkg/utils/ that always attaches an AbortSignal.timeout would give every caller a rejection it can handle, and would shrink the global handler's job to "don't show a dialog for this one known-benign escape."
  • The workaround has no upstream anchor (in-scope) Gemini 3.1 Pro Codex GPT 5.6 Sol. The real bug belongs to Electron: net.fetch should reject its promise instead of throwing out of its own event listener. A GitHub search turned up no matching electron/electron issue, so filing one and linking it from the comment would give this code a removal condition. Without that, it stays forever.
  • Both rethrow-style fixes proposed by reviewers are worse than the current code (in-scope) [orchestrator]. Removing the listener and throwing from inside the handler kills the process: Node treats it as an internal handler failure and exits 7 (measured on v22.14.0). Removing the listener and rethrowing in a queueMicrotask does restore the dialog, but it also disarms the status-0 workaround permanently, since the listener is gone for the rest of the session. Calling showErrorDialog directly (C1) avoids both.

Strengths ¶

  • The filter checks the error type and the distinctive undici message, so it does not swallow every RangeError Codex GPT 5.6 Sol Claude Opus 5.
  • The ignored error still reaches background.log, preserving evidence of the network failure Codex GPT 5.6 Sol Claude Opus 5.
  • The handler mirrors the adjacent unhandledRejection handler at lines 136-142, so it reads consistently with the file Claude Opus 5.

Testing Assessment ¶

CI is green at this SHA: lint on macOS and Windows, test, both e2e-tests runs, and packaging for all four platforms. No test accompanies the change, and background.ts has no unit spec, so nothing exercises either branch of the new handler.

Untested scenarios, highest risk first:

  1. An unrelated main-process exception still reaches the user. Nothing asserts that a deliberate throw produces any user-visible signal. C1 shipped precisely because this is unverified.
  2. The status-0 path itself. No test drives net.fetch to a status-0 response, so neither the handler nor the resulting hang (I1) is exercised. main/update/__tests__/LonghornProvider.spec.ts mocks net.fetch with resolved values only, which is why the hang is invisible to the suite.
  3. The message match (S1). Nothing fails when the undici wording changes; the filter degrades silently on the next Electron bump.
  4. Startup with a queued update while offline. This is the path where an unsettled fetch blocks startup at background.ts:311.

The predicate extraction in S1 is the cheapest coverage available; the rest need e2e or a fake net module.

Review Process Notes ¶

Skill improvements ¶

  • [ ] When a finding's mechanism depends on a runtime default (process exit on uncaught exception, signal handling, crash reporting, default dialogs), verify it in the runtime the product ships, not in whatever interpreter the worktree offers. Embedded runtimes routinely register their own handlers at startup and change the default before any application code runs, so a probe in the bare interpreter measures a different program.
  • [ ] Probe the fix you propose, not only the defect you found. A fix that changes global error handling, teardown, or listener registration can be worse than the code it replaces, and the cost of running it once is small compared to a reviewer acting on it.

Repo context updates ¶

  • [ ] Electron's main process shows its "A JavaScript error occurred in the main process" dialog only while the app registers no uncaughtException listener of its own; the built-in handler returns early once process.listenerCount('uncaughtException') > 1. Any change adding such a listener therefore removes the crash dialog for every main-process error, whatever the listener itself does. Flag it unless the new handler re-shows the dialog for the cases it does not handle. The built-in handler only shows the dialog; it never exits, so a listener does not change whether the process survives.
  • [ ] Electron.net.fetch builds its Response inside the ClientRequest 'response' listener, outside the promise chain, and rejects only from the sibling 'error' listener. A response the Response constructor rejects (status 0 from a dropped connection) therefore leaves the promise pending forever, and only an AbortSignal on the request can settle it. When reviewing a main-process net.fetch call, check for a timeout signal; a call without one can hang its caller for the life of the process.
