## Executive Summary

This PR fixes a real startup hang. The queued-install path in `doInitialUpdateCheck` settled its promise only on `update-downloaded`, so a launch-time check that failed (offline, or the release was pulled) left `setupUpdate(enabled, true)` pending and blocked startup. The production fix is correct: it settles on every terminal outcome, removes its listeners on exit, and falls through to schedule periodic checks. One defect blocks merge — the new regression test references an undefined `timersMock` and cannot run.

Two of the three reviewers completed; Codex hung twice and was dropped (see retro). Claude and Gemini independently flagged the broken `timersMock` test (C1) — the single merge-blocking issue, verified by reading the file and confirming `timersMock` is defined nowhere. Gemini additionally raised a "newer-version download blocks startup" concern, which is **pre-existing**, not introduced here (the merge-base settled the same promise only on `update-downloaded`); it appears below as a design observation, not a regression.

## Design Observations

### Concerns

**The queued-install path blocks startup while a superseding newer release downloads** — `pkg/rancher-desktop/main/update/index.ts:285-322` [Gemini 3.1 Pro] (future)

The promise settles only on `update-downloaded` or an error. When the server offers a version newer than the cached one, `electron-updater` discards the cached file and downloads the new release, so a slow link blocks startup for the full download before the backend starts. This is **pre-existing**: the merge-base settled the same promise only on `update-downloaded`, so the PR neither introduced nor worsened it. Hooking `download-progress` to resolve `false` and finish the download in the background would continue startup, but that changes the install-on-launch contract and belongs in a separate change. (Gemini rated this Critical and labeled it a regression; verified against the merge-base, it is neither.)

### Strengths

**Centralized listener teardown covers every terminal outcome** [Claude Opus 4.8] (in-scope)

The `finish()` closure removes all three one-shot listeners before resolving, so each terminal outcome — error event, `update-not-available`, `update-downloaded`, a falsy `checkForUpdates()` result, and a rejected `checkForUpdates()` promise — settles the promise once and leaves no stale `quitAndInstall` armed for a later periodic check.

**Fall-through keeps the periodic loop alive** [Claude Opus 4.8] (in-scope)

Falling through to `triggerUpdateCheck()` after a failed queued install keeps the update loop running, so the session can pick up an update later in the same run instead of waiting for the next launch.

## Review Process Notes

### Skill improvements

- **Arm a watchdog for external agents, not just the in-process path.** When launching an external review agent as a background Bash call, start a Monitor watchdog (`sleep <deadline> && echo TIMEOUT`) alongside it, mirroring the in-process subagent path. The Bash `timeout` parameter does not reliably kill a `run_in_background` task, so a hung agent CLI can run far past its deadline with no output and no completion notification, leaving the orchestrator waiting indefinitely. When the watchdog fires, stop the task and apply the retry budget. Without an explicit deadline, a single stuck CLI silently stalls the whole review.

### Repo context updates

- **[repo]** `main/update/index.ts`: `setupUpdate(enabled, true)` is awaited before the backend starts, so any promise in `doInitialUpdateCheck` that fails to settle hangs app startup. When reviewing this path, enumerate every terminal outcome of `autoUpdater.checkForUpdates()` — error event, `update-not-available`, `update-downloaded`, and a falsy or rejected return — and confirm each one settles the promise. Note also that `stagedVersion` is in-memory (reset each process) while `hasQueuedUpdate()` reads persistent on-disk state, so on a fresh launch a cached update is not recognized as "downloaded" until `autoDownload` re-fetches it.

### [Gemini 3.1 Pro] — Pass 1

### Executive Summary

This PR correctly ensures that a queued install check resolves its blocking promise when the update is no longer available or the check fails, preventing a startup hang. However, the fix is incomplete: if a newer update is available, `electron-updater` will discard the cached file and begin a background download, which still hangs the startup because the `download-progress` event is not handled. ### Findings

#### Critical Issues

C1. **Startup hangs indefinitely when a cached update is superseded by a new release during launch** — `pkg/rancher-desktop/main/update/index.ts:285-322`

`doInitialUpdateCheck` awaits a Promise that settles only on `error`, `update-not-available`, or `update-downloaded`. This path executes when a cached update is queued (`hasQueuedUpdate() === true`), so the user expects a quick install on launch. However, if a *newer* version is available on the server, `electron-updater` discards the cached file and begins downloading the new release. Because `download-progress` is not hooked, the Promise blocks app startup while the new version downloads. On a slow connection, this hangs the application indefinitely before the backend can start.

Fix: Hook the `download-progress` event to resolve the Promise with `false` and continue startup, letting the new update download in the background.

```diff
       const finish = (installing: boolean) => {
         autoUpdater.removeListener('error', onError);
         autoUpdater.removeListener('update-not-available', onNotAvailable);
         autoUpdater.removeListener('update-downloaded', onDownloaded);
+        autoUpdater.removeListener('download-progress', onDownloadProgress);
         resolve(installing);
       };
       const onError = (e: Error) => {
         console.error('Updater got error', e);
         finish(false);
       };
       const onNotAvailable = () => {
         console.log('Cached update is no longer offered; continuing startup.');
         finish(false);
       };
+      const onDownloadProgress = () => {
+        console.log('Newer update is downloading; continuing startup.');
+        finish(false);
+      };
       const onDownloaded = () => {
         console.log('Update download complete; restarting app');
         setHasQueuedUpdate(true);
         autoUpdater.quitAndInstall(true, true);
         finish(true);
       };
 
       autoUpdater.once('error', onError);
       autoUpdater.once('update-not-available', onNotAvailable);
       autoUpdater.once('update-downloaded', onDownloaded);
+      autoUpdater.once('download-progress', onDownloadProgress);
```

C2. **New test fails with ReferenceError on undefined variable** — `pkg/rancher-desktop/main/update/__tests__/index.spec.ts:263`

```typescript
    expect(timersMock.setTimeout).toHaveBeenCalled();
```

The test added to verify that a failed queued install schedules periodic checks uses an undefined variable `timersMock`. Because `timersMock` is never declared in the file or the test environment, this line throws a `ReferenceError`, breaking the test suite. 

Fix: Use Jest's timer count assertion instead, matching the pattern used in the subsequent test.

```diff
-    expect(timersMock.setTimeout).toHaveBeenCalled();
+    expect(jest.getTimerCount()).toBeGreaterThan(0);
```
