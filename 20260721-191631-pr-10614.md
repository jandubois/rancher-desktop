## Suggestions

S1. **`path.extname` rejects a valid dotted subpath** — `scripts/lib/build-utils.ts:46` [Codex GPT 5.6 Sol, Claude Opus 4.8]

```ts
  const candidates = path.extname(request) ? [request] : [`${ request }.js`, request];
```

`path.extname` treats any dotted final segment as an extension, so a request
like `package/schema.v1` yields the single candidate `package/schema.v1` and
never tries an existing `package/schema.v1.js`. Line 53 then throws.

Verified by probe: a subpath whose real file is `.cjs` or `.mjs` throws the
same way. That failure is loud and lands at build time, so it costs a
confusing build break rather than a broken release. No current dependency
uses either shape, and `chart.js`, the only dotted dependency name, resolves
correctly as a bare request.

Fix: treat the suffixed candidate as a fallback rather than gating it on
`extname`, so a dotted subpath still gets the `.js` probe.

S2. **No test asserts named-export visibility across the externals boundary** — `scripts/lib/__tests__/build-utils.spec.ts:34` [Claude Opus 4.8]

```ts
    ])('externalizes %s', async(request, expected) => {
      await expect(classify(buildUtils.webpackConfig, request)).resolves.toBe(expected);
    });
```

The table asserts specifier strings. The bug this PR fixes had a correct
specifier and invisible exports: `fs-extra` builds its exports in a loop, so
`readFile` reaches the namespace only through `default`, which is why
`(0, o.readFile)` was undefined.

The consolidator confirmed the current graph is safe. Every name
`kubeconfig.ts` imports from `@kubernetes/client-node/dist/config_types`
(`ActionOnInvalid`, `exportContext`, `exportUser`, `newContexts`, `newUsers`)
is a true named export, as is `MacUpdater`. A test importing each externalized
specifier and asserting the names it consumes would pin the deeper shape.

S3. **Dead `?? ''` fallback** — `scripts/lib/build-utils.ts:77` [Claude Opus 4.8]

```ts
    return callback(null, `module-import ${ externalSpecifier(request ?? '') }`);
```

Line 77 cannot see an undefined `request`. The regex on line 71 requires at
least one character, so an undefined request produces no `packageName` and
returns at line 74. The fallback suggests an empty request reaches
`externalSpecifier`, which never happens.

Fix: destructure with a default (`{ request = '' }`) and drop both `??`
operators.

S4. **The callback type forecloses webpack's error channel** — `scripts/lib/build-utils.ts:70` [Claude Opus 4.8]

```ts
  return ({ request }: { request?: string }, callback: (error?: null, result?: string) => void) => {
```

Typing the first parameter as `null` rules out webpack's documented
`callback(err)` path, which is why line 53 throws instead.

The throw works. Driving a bad specifier through a real `webpack()` run
surfaces it as a compilation error with `err` null and `stats.hasErrors()`
true, and `buildJavaScript` (line 406) rejects on exactly that. So this is a
contract-clarity nit, not a defect: widening the type to `Error | null` would
let the code use the channel webpack documents.

## Review Process Notes

**Skill improvements**

- Before rating a finding by its blast radius, determine whether the failure it
  describes is loud or silent, and say which. A guard that rejects a bad input
  at build time costs a confusing CI break; the same input accepted and shipped
  costs a broken release. Reviewers routinely describe the second while the
  code does the first, because a fallback branch reads as permissive until you
  trigger it. Construct the input the finding names, run the build, and record
  what happened. Where the failure is loud, the finding is usually a
  Suggestion, not an Important issue.

- When a finding claims a module's exports will be invisible across a
  CommonJS-to-ESM boundary, import the module and check each name the consumers
  actually use, distinguishing a true named export from a property reachable
  only through `default`. Static analysis of the exporting source does not
  settle it, because the loader's export detection succeeds on some
  export-assignment shapes and fails on others. Enumerate the consumers' named
  imports first, then verify that exact list; a finding that names the boundary
  without naming the consumed symbols has not been checked.

**Repo context updates**

- `[repo]` The main-process webpack externals in `scripts/lib/build-utils.ts`
  throw when a dependency subpath resolves no way at all, and
  `.github/workflows/test.yaml` runs `yarn build` before `yarn test`, so an
  unresolvable subpath fails CI rather than shipping. The resolution probe runs
  under tsx, which is more permissive than the ESM loader in the packaged app:
  a subpath whose real file carries a non-`.js` extension throws at build time,
  while a directory-style subpath resolves and ships a specifier Node later
  rejects with `ERR_UNSUPPORTED_DIR_IMPORT`. When reviewing changes to this
  resolution logic, treat the directory case as the only silent-failure shape,
  and verify a claimed silent failure by triggering it.

- `[repo]` The preload bundle resolves no external of any kind. Electron loads
  `resources/preload.js` into a sandboxed renderer from outside the asar
  (`sandbox: true` in `pkg/rancher-desktop/window/index.ts`, `resources/`
  shipped via `extraResources` in `packaging/electron-builder.yml`), so it
  reaches neither npm packages nor the app's `node_modules`. `webpackPreloadConfig`
  therefore clears `externals` outright rather than changing the external type.
  A suggestion to give the preload a CommonJS external type is wrong for this
  repo: `electron` stays external through webpack's `electron-preload`
  `externalsPresets`, independently of `externals`.

### Important Issues

**I1. Subpath externalization moves untested CJS modules onto Node's ESM interop path — `scripts/lib/build-utils.ts:286` (important, regression)**

```ts
        externals:   [externalsEntry(this.runtimeDependencies)],
```

Before this commit, a string external matched only the bare package name, so `@kubernetes/client-node/dist/config_types` was **bundled** and webpack performed the CJS interop itself. Line 286 now externalizes it as `module-import`, so Node must discover its named exports through `cjs-module-lexer` — the exact mechanism that made `fs-extra`'s `readFile` undefined. Two main-process files take *value* imports from it: `pkg/rancher-desktop/backend/kubeconfig.ts:10-17` (`ActionOnInvalid`, `exportContext`, `exportUser`, `newContexts`, `newUsers`) and `pkg/rancher-desktop/backend/k3sHelper.ts:13`. `canResolve` (line 33) proves the file exists; it says nothing about export visibility. The commit message records runtime verification only for the macOS updater download. This is distinct from the declined Windows/Linux item — this path loads on every platform, on every Kubernetes start.

Fix: before merge, start Kubernetes once on a packaged build. That is the only path that loads `config_types`; a failure there is a hard startup break, not a degraded feature.

### Suggestions

**S1. `externalSpecifier` throws where webpack's contract is `callback(error)` — `scripts/lib/build-utils.ts:53` (suggestion, regression)**

```ts
  throw new Error(`Cannot resolve external "${ request }"; Node will not resolve it at runtime either.`);
```

The callback type at line 70 is declared `(error?: null, result?: string) => void`, which forecloses webpack's documented `callback(err, result, type)` error path and forces the throw at line 53. A synchronous throw out of an externals function relies on webpack's internal queue catching it rather than on the documented contract; the path is exercised only by the unit test calling the handler directly (spec line 47), never by a real `yarn build`. The spec's `classify` helper discards the error argument entirely (`_error` at spec line 17), so it cannot tell `callback(err)` from "not external."

Fix:

```diff
-  return ({ request }: { request?: string }, callback: (error?: null, result?: string) => void) => {
+  return ({ request }: { request?: string }, callback: (error?: Error | null, result?: string) => void) => {
```

and have `externalSpecifier` return `string | undefined`, with `externalsEntry` calling `callback(new Error(...))`.

**S2. `canResolve` is never validated against Node's own ESM resolver — `scripts/lib/build-utils.ts:33` (suggestion, gap)**

```ts
    return fs.statSync(fileURLToPath(import.meta.resolve(specifier))).isFile();
```

Line 33 runs under three different resolvers and none of them is the one that matters. The build runs under tsx (`scripts/ts-wrapper.js`); the unit test runs under jest-resolve; the packaged app runs under Node/Electron's ESM loader. The first two are strictly more permissive. The docstring at lines 25-29 names only the directory-import case, but tsx's extensionless resolution covers other extensions too: a subpath whose real file is `.cjs`, `.mjs`, or `.json` fails the `${request}.js` candidate at line 46, then resolves bare under tsx, and ships a specifier Node rejects. The inverse also bites — `path.extname` at line 46 treats any dot in the last segment as an extension, so a subpath like `foo/bar.min` never gets the `.js` candidate.

Fix: reject a resolution that is the specifier plus an appended extension — that is the loader's guessing, not an `exports` redirect:

```diff
-    return fs.statSync(fileURLToPath(import.meta.resolve(specifier))).isFile();
+    const resolved = fileURLToPath(import.meta.resolve(specifier));
+
+    // tsx resolves extensionless specifiers that Node's ESM loader rejects; an
+    // `exports` map redirect lands somewhere else entirely, so it still passes.
+    if (path.extname(resolved) && resolved.endsWith(path.extname(resolved)) &&
+        resolved.slice(0, -path.extname(resolved).length).endsWith(specifier.replaceAll('/', path.sep))) {
+      return false;
+    }
+
+    return fs.statSync(resolved).isFile();
```

**S3. Dead `?? ''` fallback — `scripts/lib/build-utils.ts:77` (suggestion, regression)**

```ts
    return callback(null, `module-import ${ externalSpecifier(request ?? '') }`);
```

Line 77 cannot be reached with `request` undefined: the regex at line 71 needs at least one character, so an undefined request yields no `packageName` and returns at line 74. The fallback misleads a reader into thinking an empty request reaches `externalSpecifier`.

Fix:

```diff
-  return ({ request }: { request?: string }, callback: (error?: null, result?: string) => void) => {
-    const packageName = /^(?:@[^/]+\/)?[^/]+/.exec(request ?? '')?.[0];
+  return ({ request = '' }: { request?: string }, callback: (error?: null, result?: string) => void) => {
+    const packageName = /^(?:@[^/]+\/)?[^/]+/.exec(request)?.[0];
 
     if (!packageName || !Object.hasOwn(dependencies, packageName)) {
       return callback();
     }
 
-    return callback(null, `module-import ${ externalSpecifier(request ?? '') }`);
+    return callback(null, `module-import ${ externalSpecifier(request) }`);
```
