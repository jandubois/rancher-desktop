Design Observations ¶

Concerns ¶

  • Staged-update state is split across two stores (future) Claude — The persistent truth for a staged update is the on-disk LonghornCache (isInstallable + release.tag, read by hasQueuedUpdate()), while index.ts now also tracks staged identity in a process-local stagedVersion. The two diverge across the lifecycle: after a restart, stagedVersion is undefined even when a valid update sits on disk, so the first post-restart update-available reports downloaded=false until update-downloaded re-fires from cache (a brief flicker, not a re-download — electron-updater serves the cached file when its sha512 matches). Seeding stagedVersion from cache.release.tag in getUpdater, or reading the cache directly in update-available instead of keeping a parallel copy, would centralize the truth and remove the window.
  • setHasQueuedUpdate is an unsynchronized read-modify-write (future) Claude — checking-for-update writes false and the new matching path in update-available writes true, both un-awaited, to the same cache file with no locking. Today the network round-trip between the two events orders them, but as more events touch the cache the race surface grows. A single-writer helper or serialized queue would foreclose the class.

Strengths ¶

  • Replacing the state === State.UPDATE_PENDING proxy with explicit version tracking removes the exact fragile inference that caused the bug — the cached-update path (no download-progress, so state never reaches UPDATE_PENDING) is now handled directly. Claude Codex
  • Re-arming autoDownload only when info.version !== stagedVersion fixes a real latent bug where a long-running instance advertised newer releases but never downloaded them, and safely delegates stale-file cleanup to electron-updater. Claude Gemini
  • Clearing updateState.error in checking-for-update without immediately broadcasting avoids a status-message flicker while still restoring the button when the next check succeeds. Gemini
  • First-ever test coverage for the state machine, driving the real handlers through a faithful event-emitting fake rather than asserting on mocked return values. Claude

Review Process Notes ¶

Skill improvements

  • Add a correctness pattern: Promise settled by a single event listener. When a function returns a Promise (or awaits one) that calls resolve/reject from inside only one event-handler callback, enumerate every other terminal event the underlying emitter or source can produce — error events, "not-found"/"unavailable"/"no-op" events, and rejection of the call that kicks off the work — and confirm each path settles the Promise. An await on a Promise that can stay pending blocks its caller indefinitely, and a try/catch around the await cannot rescue a Promise that never rejects (it simply never settles). Flag when the success listener resolves but the failure listeners only set a flag, and when the triggering call's rejection is neither awaited nor .catch()ed.

Repo context updates

  • [repo] The auto-update state machine in pkg/rancher-desktop/main/update/index.ts has three pieces of state that can diverge: the in-memory state enum (drives the triggerUpdateCheck skip-while-downloading guard), the in-memory stagedVersion/updateState, and the on-disk LonghornCache (isInstallable + release.tag, accessed via hasQueuedUpdate()/setHasQueuedUpdate() in LonghornProvider.ts). The renderer consumer components/UpdateStatus.vue reads updateState.{available,downloaded,error,info,progress}; note progress is set in the download-progress handler and never cleared. background.ts:296 awaits setupUpdate(cfg.application.updater.enabled, true) before startBackend() (line 320), so anything that blocks setupUpdate blocks the whole backend bring-up. When reviewing update-logic changes, trace all three state stores and this startup ordering.
  • [repo] electron-updater (6.8.x) caches exactly one pending update in <cacheDir>/pending, keyed by sha512 (DownloadedUpdateHelper.getValidCachedUpdateFile). On a checkForUpdates, if the offered update's sha512 differs from the cached update-info.json, it calls cleanCacheDirForPendingUpdate() (deletes the staged file) and forces a fresh download; if the sha512 matches, it serves the cache and emits update-downloaded with no preceding download-progress. Verify claims about "stale cached file" or "re-download" against this sha512-keyed behavior rather than assuming filename-based caching.
