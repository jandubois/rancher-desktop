## Executive Summary

The `DOWNLOADING` → `CHECKED` transition correctly unwedges the updater, and its regression test drives a real timer through the scheduler. The staged-update half is incomplete: `checking-for-update` clears `available` before an error arrives, and only `downloaded` is restored, so the renderer receives `{available: false, downloaded: true}` and still hides Restart Now. That is the symptom the author reproduced in issue 7516.

Three of four reviewers found that gap independently. Two probe tests run against the PR's own harness confirmed it, plus a second symptom: a failed Retry hides the whole card.

## Important Issues

I1. **A failed check still hides a staged update; `available` is never restored** — `pkg/rancher-desktop/main/update/index.ts:158` [Claude Opus 4.8, Codex GPT 5.6 Sol, Gemini 3.1 Pro]

```ts
    updateState.downloaded = !!stagedVersion && updateState.info?.version === stagedVersion;
    window.send('update-state', updateState);
```

The card is gated on `available`, not `downloaded` (`UpdateStatus.vue:159`). Every check begins with `checking-for-update`, which sets `updateState.available = false` and sends nothing. When that check then errors, the handler restores `downloaded` but leaves `available` false, so the whole card unmounts.

Two probe tests against the PR's own harness confirm both symptoms. A staged update followed by a failed re-check yields `{available: false, downloaded: true}`, hiding Restart Now. A failed download followed by a Retry whose check also fails yields `available: false`, so the card the user just acted on disappears with no message and no way to try again. The card returns on the next successful check, within 10 minutes via the `catch` arm at `index.ts:384`, so the damage is temporary.

Fix: restore `available` when the staged update survives.

```diff
     updateState.downloaded = !!stagedVersion && updateState.info?.version === stagedVersion;
+    if (updateState.downloaded) {
+      // A check that failed did not retract the offer it made last time.
+      updateState.available = true;
+    }
```

I2. **`updateStatus.errorChecking` is now unreachable, so a failed check shows nothing** — `pkg/rancher-desktop/components/UpdateStatus.vue:174` [Claude Opus 4.8, Gemini 3.1 Pro]

```ts
      if (!this.updateState?.info) {
        return this.updateState?.error ? this.t('updateStatus.errorChecking') : '';
      }
```

`statusMessage` is evaluated only inside the card, which requires `available`. One place sets `available = true` (`index.ts:177-178`), and it always sets `info` alongside it. So `available` implies `info`, and this branch cannot render. `errorChecking` has exactly one reference in the tree, this line, so the string and its eight translations are now dead.

The reachable half of that state (`available === false` with an error) renders no card at all, so a check that fails outright stays silent. That is the case issue 7516's title names. The pre-existing test at `__tests__/UpdateStatus.spec.ts:67-79` pins `available: true` with no `info`, a state the main process cannot produce, so it will not catch the loss.

Fix: render the card on `error` alone so a check failure gets a message and a Retry button, or drop the branch, the key from all nine locales, and the test.

I3. **An install error leaves the apply button permanently disabled** — `pkg/rancher-desktop/components/UpdateStatus.vue:135-139` [Codex GPT 5.6 Sol]

```ts
  watch: {
    updateState() {
      // The main process has reported the outcome of the retry.
      this.retrying = false;
    },
  },
```

`applyUpdate()` sets `applying = true` (line 238) and nothing clears it. An install attempt can dispatch an updater error (`MSIUpdater.ts:95` calls `dispatchError` directly), which reaches the renderer through the same handler. Because `updateReady` now deliberately stays true after an error, the button stays rendered but disabled, reading "Applying update..." until the app restarts, while the body text claims the update is available and no error appears anywhere.

At the merge-base this stayed invisible: the error forced `downloaded = false`, so the button unmounted and `errorChecking` displayed. This PR introduces the dead end.

Fix: reset `applying` in the same watcher when the new state carries an `error`.

## Suggestions

S1. **In-memory `downloaded` now disagrees with the on-disk queued flag** — `pkg/rancher-desktop/main/update/index.ts:170` [Claude Opus 4.8]

### Concerns

- **Scope versus issue 7516** `(in-scope)` [Claude Opus 4.8, Codex GPT 5.6 Sol]. The thread converged on a persistent "Check Now" button beside the auto-update checkbox, available regardless of state. This predates the PR, but the change now depends on `state` accurately describing the download, so splitting the enum's dual role (startup progress versus download progress) would remove the need for the new reset entirely.

Routing updater events through one transition helper that emits a coherent renderer snapshot would centralize the invariant.

## Review Process Notes

### Skill improvements

- When a finding claims a UI element disappears, is disabled, or otherwise becomes unreachable, trace how it comes back before assigning severity. A state that a scheduled retry, a timer, or the next successful poll restores is a temporary defect; one that persists until the process restarts is a dead end. Reviewers routinely report the first as permanent, which inflates severity by a full level.
- When an agent reports a concrete run result (a test count, a green suite, a built binary), reproduce it before repeating it, and use the project's own documented test command rather than invoking the runner directly. Test harnesses frequently require flags that the package script supplies, so a direct invocation can fail for reasons that have nothing to do with the code under review, and reporting that failure as a defect is worse than reporting nothing.

### Repo context updates

- [repo] The `updateState` object that `main/update/index.ts` broadcasts to the renderer is mutated by several handlers in sequence, and only some of them call `window.send`. `checking-for-update` clears `available`, `downloaded`, and `progress` without sending, so the next handler that does send inherits those cleared fields. When reviewing a change to any single updater event handler, trace which earlier handler last mutated each field of `updateState` and whether it sent; a fix that repairs one field in the `error` handler can leave a sibling field cleared by `checking-for-update`, and the renderer gates on the sibling.
- [repo] `pkg/rancher-desktop/components/UpdateStatus.vue` renders its card on `updateState.available`, not on `downloaded` or `error`. Any main-process change intended to keep part of the update UI visible has to keep `available` true as well, or the whole card unmounts and the change has no visible effect.
- [repo] Jest suites in this repo must run through `yarn test:unit:jest`, which sets `NODE_OPTIONS=--experimental-vm-modules`. Invoking `yarn jest` or `npx jest` directly fails with "Cannot use import statement outside a module" or an internal paths-module error, neither of which indicates a problem with the code under review.

### Design Observations

**Concerns**

- **`state` is clobbered right after the initial check, defeating the `DOWNLOADING` guard at startup** *(future)*. `setupUpdate` assigns `state = State.CHECKED` at line 280 after `doInitialUpdateCheck()` returns. `checkForUpdates()` resolves once the download has *started*, not finished, so a `download-progress` event that set `state = State.DOWNLOADING` (line 207) during the initial check is immediately overwritten, and the next timer tick starts a check while the download is still running. Pre-existing (not introduced here), but this PR now depends on `state` being an accurate description of the download, so it is worth either dropping the assignment when `state === State.DOWNLOADING` or replacing the enum's dual role (startup progress vs. download progress) with a separate `downloading` flag. The three-value split would also remove the need for the new reset at lines 150-155.

- **Scope vs. issue #7516** *(in-scope decision)*. The issue thread converged on a "Check Now" button beside the "Check for updates automatically" checkbox, available regardless of state. This PR instead adds a Retry button inside the update card, shown only when a download failed. That is a defensible narrower fix for the reported symptom, but with `Closes #7516` the broader agreed feature — and the check-failure case in I2 — is closed unimplemented. Consider `Refs #7516` and keeping the issue open for the Check Now button.
