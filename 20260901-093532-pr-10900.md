## Design Observations

### Concerns

- **`resolveTag` probes only the newest release** `(future)` [Claude Opus 5]. `latestVersion` reduces to the maximum version, so `resolveTag` gets one version and two tags. Epinio published `v0.1.4` and `v0.1.5` with no image under either form; I confirmed both return 404 today. Had the daily run fired between those releases and `v0.1.6`, the bump would have failed every day until an image appeared. Falling back to the newest version the registry actually serves would fix it, but that re-opens what @mook-as objected to in #8647, so any fallback should log which version it skipped.
- **The card label and the pinned tag diverge exactly where it matters** `(future)` [Claude Opus 5]. A `v` prefix reaches the manifest only when the publisher has no unprefixed image, which is precisely when the string on the card is a tag the registry does not serve. Nothing in the app consumes the label, but `command-api.yaml:563` documents `application.extensions.installed` as taking a tag, so an admin copying a version off the card into a deployment profile gets a reference that 404s.
- **Extension bump PRs still carry an empty body** [Claude Opus 5]. `getBody()` returns `''` for anything that is not a `GitHubDependency`, and `Extension` extends `VersionedDependency` directly. Pre-existing and out of scope, but the PR title will now say `0.1.6` while the diff pins whatever `resolveTag` chose, and a body is where that belongs.

### Strengths

- `imageTagExists` fails closed on any status that is neither success nor 404, with the reason stated in a comment (`registry.ts:81-82`) [Claude Opus 5, Codex GPT 5.6 Sol]. That is the right default for a tool that writes pins, and it is the property most likely to be simplified away later.
- The rationale for skipping `docker manifest inspect` (`registry.ts:4-5`) is accurate [Claude Opus 5]. I ran it against a public ghcr.io image and got `denied: denied`.
- `MarketplaceCard.spec.ts:35-37` asserts on `versionedExtension`, not just the label [Codex GPT 5.6 Sol, Claude Opus 5]. It pins the half that must not change, which is the harder half to remember.
- Each of the four commits carries its own test, and the commit bodies state facts I could check. I confirmed the shared-digest claim in `1407d8fc7` and the open-webui tag history in `66d43fd7c` against the live registry.

## Review Process Notes

### Skill improvements

- [ ] A review session launched inside a git worktree cannot write to the reviews directory in the main checkout, and cannot run the multi-statement shell forms the setup steps use. Before assembling any context, check whether the session is worktree-isolated. When it is, run every helper as a single command with fully-qualified paths rather than assigning shell variables, and settle where the report will be written before spending agent time, since the deliverable's home lies outside the isolation boundary.

- [ ] Shell state does not persist between tool calls, so a step that imports variables by `eval`-ing a helper's output leaves every later step referring to unset names. Have the helper's output read once and substitute the values literally into each later command.

- [ ] Confirming that a reviewer's environment *could* have produced a run result is not enough to repeat it. Compare the reported numbers against the suite's own output: an agent with a working toolchain can still report a per-suite breakdown that does not match what the runner prints. When the totals disagree, label every execution claim from that agent unverified, whatever its environment allowed.

### Repo context updates

- [ ] `.gitignore` lists `/node_modules/` with a trailing slash, which matches directories only. An agent that symlinks the main checkout's `node_modules` into its worktree leaves an untracked entry visible in `git status`, while one that copies or installs a real directory leaves none. Read a clean `git status` in a review worktree as evidence about the agent's method, not as proof it modified nothing.

- [ ] `getExtensions(true)` filters the extension catalog to entries carrying a `github_repo`, and that filtered list is what the dependency manager consumes. Extensions without one never reach `latestVersion`, so its `reduce` over an empty array cannot throw for them. Do not file that as a defect.

- [ ] Docker Hub answers 401, not 404, for a repository that does not exist, even after a successful anonymous token exchange. Code that classifies registry responses by status will report a renamed, deleted, or private repository as an authentication failure. Check that distinction whenever a change reads registry status codes.

**I1. `imageTagExists` — the module's actual contract — has no test** — `scripts/lib/__tests__/registry.spec.ts:1-31` (important, gap)

Fix — I ran this against the unmodified tree; 3 passed:

```ts
/** @jest-environment node */
import { jest } from '@jest/globals';

import { imageTagExists } from '../registry';

let responses: Response[] = [];
const calls: string[] = [];

beforeEach(() => {
  calls.length = 0;
  responses = [];
  globalThis.fetch = jest.fn((input: any) => {
    calls.push(String(input));

    return Promise.resolve(responses.shift() ?? new Response('', { status: 500 }));
```

## Design Observations

### Concerns

**`resolveTag` probes only the single newest release** *(future)*. `latestVersion` (`dependencies.ts:534-542`) reduces to the maximum version, so `resolveTag` gets one candidate version and two candidate tags. This is not hypothetical for the catalog as it stands: epinio published releases `v0.1.4` and `v0.1.5` on 2026-08-20, and I confirmed against Docker Hub that **neither has an image under either form** (both return 404; `v0.1.6` and `0.1.6` share `sha256:b9812aeb…`). Had the daily run fired between those releases, the extension's bump would have failed every day until `v0.1.6` landed. Falling back to the newest version the registry actually serves would fix that, but it also re-opens exactly what @mook-as objected to in #8647 — a silent pin to an older release. If the fallback is added, it should log loudly which version it skipped and why, so the divergence stays visible without going red.

**One dead image still blocks every extension bump** *(future)*. `updateManifest` calls `generateExtensionMarketplaceData()` (`extension-data.ts:95`), which `docker pull`s all 14 catalog images (`extension-data.ts:100-109, 147-148`), so a single deleted upstream tag fails *every* extension's bump — now reported as N separate failures rather than one aborted run. The PR description names this, and the `try`/`catch` contains the blast radius, but the root cause survives. `imageTagExists` now makes a cheap pre-check possible: probe all 14 refs before regenerating and skip regeneration with a clear message when one is gone. I probed all 14 in a single pass in about two seconds; all currently resolve.

**The card label and the pinned tag diverge exactly where it matters most** *(future)*. `resolveTag` prefers the unprefixed form (`extension-data.ts:75`), so a `v` prefix reaches the manifest **only** when the publisher has no unprefixed image — which is precisely the case where the string the card shows (`0.0.8`) is a tag the registry does not serve. Nothing in the app consumes the label, but `application.extensions.installed` is documented as taking a tag (`pkg/rancher-desktop/assets/specs/command-api.yaml:563`, `x-rd-usage: installed extensions and their tag`), so an admin reading a version off the card into a deployment profile would get a reference that 404s. Worth a line in the deployment-profile docs rather than a code change.

**Extension bump PRs still carry an empty body**. `getBody()` returns `''` for anything that is not a `GitHubDependency` (`rddepman.ts:107-110`), and `Extension` extends `VersionedDependency` directly — which is why #10889 has no body. Pre-existing, and out of scope here, but the PR title will now say `0.1.6` while the diff pins whatever `resolveTag` chose; a body would be the natural place to record that.

##### S1. Lack of timeout on registry authentication fetch calls `(suggestion, gap)` — `scripts/lib/registry.ts:43-43`

##### S2. Regex-based authentication challenge parser is sensitive to parameter quoting `(suggestion, gap)` — `scripts/lib/registry.ts:22-23`

```typescript
export function parseAuthChallenge(header: string): Record<string, string> {
  return Object.fromEntries(Array.from(header.matchAll(/(\w+)="([^"]*)"/g), m => [m[1], m[2]]));
}
```

The regex `/(\w+)="([^"]*)"/g` expects parameter values to be double-quoted. While Docker Hub and GHCR use quoted parameters, standard OCI registries or proxy servers could theoretically omit quotes for simple tokens (e.g. `service=ghcr.io`). If unquoted parameters are returned, the parser will fail to extract them, breaking the token exchange.

Fix: Update the regex to support optional surrounding quotes for parameter values.

```diff
 export function parseAuthChallenge(header: string): Record<string, string> {
-  return Object.fromEntries(Array.from(header.matchAll(/(\w+)="([^"]*)"/g), m => [m[1], m[2]]));
+  return Object.fromEntries(Array.from(header.matchAll(/(\w+)=(?:"([^"]*)"|([^,\s]*))/g), m => [m[1], m[2] || m[3]]));
 }
```
