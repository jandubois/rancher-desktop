## Important Issues

I1. **Blog-feed parsing logic ships untested** — `pkg/rancher-desktop/components/__tests__/BlogFeed.spec.ts:9` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro, Gemini 3.5 Flash]

```ts
    ipcRenderer: { invoke: () => new Promise(() => {}) },
```

The spec mocks `invoke` to a never-resolving promise, so `mounted` never calls `parseFeed`. Both tests set `entries` directly or assert the empty state — covering the render loop but not `parseFeed`, `firstParagraph`, or `formatDate` (`BlogFeed.vue:20-54`): XML parsing, the `content:encoded`→`description` fallback, whitespace collapse, and date parsing. These are the parts most likely to break against a real feed.

Fix: feed a small RSS XML string through `parseFeed` and assert the extracted `title`/`link`/`summary`/`date`, including a `content:encoded` body and an invalid `pubDate` to exercise the raw-string fallback at `BlogFeed.vue:47`.

I2. **Feed links reach `href` without scheme validation** — `pkg/rancher-desktop/components/BlogFeed.vue:73` [Codex GPT 5.5]

```vue
          <a
            :href="entry.link"
            class="blog-entry-title"
          >{{ entry.title }}</a>
```

`entry.link` is the RSS `<link>` text (`BlogFeed.vue:30`), bound raw into two anchors (`:73`, `:80`). The main window runs `nodeIntegration: true` and `contextIsolation: false` (`window/index.ts:128`), so a `javascript:` link would execute with Node access. Claude read the links as safe because `will-navigate` (`window/index.ts:79`) sends external URLs to `shell.openExternal` — but that guard covers http/https navigations, not a `javascript:` href, which runs inline without navigating. Exploiting it needs a compromised feed or MITM against first-party HTTPS, so this is defense-in-depth, not a live hole — but cheap to close.

Fix: allowlist `http:`/`https:` while parsing and drop other schemes.

```diff
-        link:    item.querySelector('link')?.textContent ?? '',
+        link:    this.safeLink(item.querySelector('link')?.textContent ?? ''),
```

## Suggestions

S1. **New user-facing strings bypass i18n** — `pkg/rancher-desktop/components/BlogFeed.vue:64` [Codex GPT 5.5, Claude Opus 4.8]

```vue
    <h3>From the blog</h3>
```

"From the blog" (`:64`), "Read more" (`:82`), and the checkbox label "Check for updates automatically" (`AutoUpdateCheckbox.vue:60`) are literal English, while the app ships `zh-hans` and the page header routes through `this.t('general.title')` (`General.vue:46`). Fix: add keys under `general.*` to `en-us.yaml` and `zh-hans.yaml` and render them through `t()`. If deferred, make it a conscious call given the page's mix.

S2. **New components drift from the Composition-API convention** — `pkg/rancher-desktop/components/AutoUpdateCheckbox.vue:12` [Gemini 3.1 Pro, Gemini 3.5 Flash]

```js
export default {
  name:       'auto-update-checkbox',
```

`AutoUpdateCheckbox.vue` and `BlogFeed.vue` use the Options API in a plain `<script>` block. The repo convention (per `deep-review-context.md`, citing `ContainerLogs.vue`/`ContainerShell.vue`) is `<script lang="ts" setup>` with `defineOptions({ name })`. Neither new component declares props, so only the `defineOptions`/setup part applies. This is stylistic, and much existing code predates the convention — flagged because the context asks to.

Fix: convert both to `<script lang="ts" setup>` with `defineOptions`.

S3. **`get-blog-feed` fetch has no timeout** — `background.ts:808` [Claude Opus 4.8, Gemini 3.5 Flash]

```ts
  const response = await Electron.net.fetch(blogFeedURL);
```

If `docs.rancherdesktop.io` stalls mid-response, the handler promise and the renderer's `invoke` (`BlogFeed.vue:13`) stay pending for the page's lifetime. Impact is low — `mounted` does not await it, so the section just never appears — but each General visit can leak a pending promise with no diagnostic.

Fix:

```diff
-  const response = await Electron.net.fetch(blogFeedURL);
+  const response = await Electron.net.fetch(blogFeedURL, { signal: AbortSignal.timeout(10_000) });
```

S4. **Description fallback can render raw HTML tags** — `pkg/rancher-desktop/components/BlogFeed.vue:39` [Gemini 3.5 Flash]

```js
      const text = body.querySelector('p')?.textContent || item.querySelector('description')?.textContent || '';
```

When `content:encoded` is empty, `firstParagraph` falls back to the item's `description` via `textContent`. A `description` carrying escaped HTML (e.g. `&lt;p&gt;…`) decodes to a string with literal `<p>` tags, which the escaped `{{ entry.summary }}` then shows verbatim. The `content:encoded` path already strips tags by parsing to a document; the fallback does not. The feed's items carry `content:encoded` today, so this path is rarely hit.

Fix: parse the `description` fallback through `DOMParser` too and take its `textContent`.

S5. **Pre-existing: `settings-read` listener never removed** — `pkg/rancher-desktop/pages/General.vue:55` [Claude Opus 4.8, Gemini 3.1 Pro, Gemini 3.5 Flash]

```js
    ipcRenderer.on('settings-read', (event, settings) => {
      this.$data.settings = settings;
    });
```

The inline arrow handler is never unregistered in `beforeUnmount` (`:61-64`), so each General mount appends a listener to the global `ipcRenderer` and pins the old component instance. This predates the PR (present at merge-base `60d6526`), so it is not a regression — but the PR edits this exact `mounted` block, making it a natural cleanup.

Fix: register `this.onSettingsUpdate` for `settings-read` and add the matching `off()` in `beforeUnmount`, mirroring `settings-update`.

## Review Process Notes

### Skill improvements

- When a finding credits an existing guard — a sanitizer, a navigation interceptor, an allowlist, an escaping layer — as neutralizing untrusted input, verify the guard covers the specific input class the finding involves (URL schemes, encodings, nested markup, boundary values), not just the common path. A guard that handles the normal case can still leave a narrow bypass, and a reviewer who trusts it wholesale will miss it. Recognise the pattern when a review says "safe because X handles it" without naming which inputs X actually rejects.

### Repo context updates

- [repo] The main application `BrowserWindow` runs with `nodeIntegration: true` and `contextIsolation: false` (`pkg/rancher-desktop/window/index.ts`), so any renderer component that displays remote or untrusted data (feeds, API responses, file contents) runs in a full-Node context — rate an unvalidated `href`, `v-html`, or injected script higher than in a sandboxed renderer. The `will-navigate`/`setWindowOpenHandler` guard in the same file sends http/https URLs to `shell.openExternal` but fires only on navigation, so it does not neutralize a `javascript:`/`data:` href that runs inline on click; do not treat it as sufficient sanitization for untrusted links.
- [repo] Page title-line action components resolve by name through a dynamic import in `pkg/rancher-desktop/components/TheTitle.vue` (`import('@pkg/components/${action}.vue')`), driven by `page/setHeader({ action: 'ComponentName' })`. The component needs no global registration — only a matching filename — and `setHeader` resets `action` on every navigation, so it never leaks to other pages. A finding that an `action`-slot component is "never registered" is a false positive.

##### I1. DOM XML namespaced element lookup in `BlogFeed.vue` uses prefix instead of namespace URI `(important, regression)`

```javascript

```

The lookup at `pkg/rancher-desktop/components/BlogFeed.vue:37` queries thenamespaced element `<content:encoded>` by its prefix-qualified literal string. While some parser modes accept this, standard-compliant XML DOM engines require namespace-aware lookups to retrieve namespaced elements. ```diff
