## Design Observations

### Concerns

- **The confirmation will be a three-way duplication once Images moves over** `(future)` [Claude Opus 5]. Round 1 recorded moving `components/Images.vue`'s dialog to this shape as a follow-up. Extracting the S2 helper first turns that follow-up into a call-site change, and gives the images dialog `normalizeAccessKeys` and the macOS strip at the same time.
- **A store refresh while the dialog is open can clear the selection** `(future)` [Claude Opus 5]. `selection.js`'s `pagedRows` watcher drops any selected row not identity-present in the new rows, and `Volumes.vue:141` rebuilds every row object on each store refresh. `e2e/volumes.e2e.spec.ts:175` asserts the checkboxes survive a cancelled bulk delete and then re-clicks without re-selecting. A cancel emits no docker event, so the window is small, but this is the shape that produces a rare red e2e rather than a reproducible failure.
- **A bulk action that skips ineligible rows still says nothing about them** `(future)` [Claude Opus 5]. Carried from Rounds 1 and 2 unchanged. The dialog names the rows it will delete, so it is accurate; closing it means a tenth translation key, and Stop, Start and Restart would still skip silently.

### Strengths

- Both pages capture the target list before prompting and reuse it for the confirmation and the execution, so the count and the action cannot drift apart. [Codex GPT 5.6 Sol, Claude Opus 5]
- `applyTableAction` filters the selection down to rows where the action is enabled before the dialog is built, so a mixed running and stopped selection names exactly the containers that will go. [Claude Opus 5]
- Placing labels by named index keeps `buttons`, `defaultId` and `cancelId` synchronized against reordering. [Codex GPT 5.6 Sol, Gemini 3.1 Pro]
- Confirmation reaches every delete route: `execCommand` has one caller for `rm` and one for `volume rm`, both behind `confirmDelete`. [Claude Opus 5, Codex GPT 5.6 Sol]

## Review Process Notes

### Skill improvements

- When a prior round proposed a repo-context rule that has not yet been processed into the context file, re-derive the rule before injecting it as an established fact. A rule written from one instance often over-generalises, and the next round will apply it to code the original never covered. Verify it against the compiler, linter or runtime that would enforce it, and inject the corrected form.

- Before dispatching agents, name in the prompt every category of state-changing command the host machine cannot afford, rather than relying on a general prohibition against commands that change state outside the worktree. A general rule leaves each agent to decide what counts, and the categories that matter are specific to the machine the review runs on.

### Repo context updates

- `[repo]` CORRECTION to the rule proposed in the previous round about untyped `jest.fn()`. Only `mockResolvedValue` and `mockRejectedValue` fail. With no type argument, `jest.fn()` from `@jest/globals` infers its return as `unknown`, and the resolved-value setters constrain their parameter to `never`, so any argument is rejected. `mockReturnValue` takes the return type directly, and every value is assignable to `unknown`, so it compiles. A live example sits in the default branch at `components/__tests__/StatusBar.spec.ts:18`, which would be falsely flagged by the broader rule. Flag an untyped `jest.fn()` only where a resolved or rejected value is chained onto it.

- `[repo]` In jest specs under `pkg/rancher-desktop/**/__tests__/`, a mock shared across tests in one file needs an explicit `beforeEach` reset. `jest.config.js` sets none of `resetMocks`, `clearMocks` or `restoreMocks`, and `toHaveBeenCalledWith` matches any recorded call, so without a reset a later test can pass on an earlier test's call. Flag a spec that shares a module-level mock across more than one test without resetting it.

- `[repo]` Access keys in the Chinese, Japanese and Korean locale files are written with half-width parentheses after the label, as in `削除(&D)`, and have been since those locales were added, around 26 per file, all under `mainMenu:`. The full-width parentheses those files also use are prose punctuation and never mark an access key. The macOS strip reaches only dialogs that pass `normalizeAccessKeys`; menu accelerators are Electron's own.

- `[repo]` The bulk action bar passes the click event to `applyTableAction`, and `SortableTable` treats the platform's alternate modifier (Command on macOS, Control elsewhere) as a request to run the per-row action instead of the bulk one. Any bulk action that opens a dialog therefore opens one dialog per selected row under that modifier. Check this whenever a row action gains a confirmation or any other user prompt.
