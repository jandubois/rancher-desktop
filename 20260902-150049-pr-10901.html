Design Observations ¶

Concerns ¶

  • The partial path is the only one nothing verifies automatically (in-scope) Claude Opus 5 Codex GPT 5.6 Sol. Round 2 adds the test that covers it, and S2 is why it does not run by default. The awk program remains reachable only through a full VM start; a fixture-driven check (an index.json, a stub docker on PATH, and an assertion that the filtered output parses) runs in milliseconds and is what both the consolidator and two agents built by hand to review this PR.
  • Records from earlier sessions outlive the fix (future) [Claude Opus 5, Codex GPT 5.6 Sol, Consolidator]. Raised in Round 1, and both agents raised it again, Claude at Important. The change stops creating records and removes none, so an upgrading user keeps the warnings for the images their pods inspect. Claude proposed docker image rm "moby-dangling@$digest"; that does not work. On the live VM docker image inspect 'moby-dangling@sha256:d986…' answers No such image, because the CLI normalises a bare name to docker.io/library/… and the record's literal name is not a valid reference. docker images -a and --filter dangling=true do not list them either. Any cleanup would have to go through containerd's moby namespace, which is a larger change than this PR. Release notes saying the fix is preventive would cost nothing.
  • The dangling warning is emitted on inspect, not on load (in-scope) [Consolidator]. On the live VM all 60 warnings fall in a 50-second window right after the k3s start, none in the 14.5 hours since, and neither docker images nor docker image inspect produces one. So assert_no_dangling_records depends on a workload having inspected the affected image. It holds for the seven images pods use, which is where the regression would appear; a record on an image nothing runs would go unseen. Given that no CLI lists these records at all, asserting on the log is the only check available.

Review Process Notes ¶

Skill improvements ¶

  • When a finding's severity turns on a resource limit (memory, disk, a quota), measure it on the target platform before rating it. A path that "could exhaust" a filesystem is a Suggestion or nothing when the filesystem has two orders of magnitude of headroom, and the measurement is usually one command. State the measured figure in the finding so the next round inherits a number.
  • When a finding proposes matching a third-party tool's human-readable error text to classify a failure, weigh the new failure mode against the old one. Text matching turns a rare silent degradation into a hard failure the day upstream rewords the message, and in start-up paths that trades a cosmetic defect for an unbootable service.
