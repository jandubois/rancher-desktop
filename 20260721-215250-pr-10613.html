Design Observations ¶

Concerns ¶

  • setHasQueuedUpdate round-trips the parsed cache (LonghornProvider.ts:248-252), so apiURL and upgradeServer survive by construction rather than by contract. A future rewrite that composes a fresh object would strip them and silently reopen the hole this PR closes, with every current test still green. Claude Opus 4.8 (future)

Strengths ¶

  • Gating both overrides on RD_FORCE_UPDATES_ENABLED does more than tidy the environment. That flag already suppresses the update-apply IPC (index.ts:72) and the queued-install branch (index.ts:284), so a run that can redirect a release is structurally a run that cannot install one. Claude Opus 4.8 (in-scope)
  • Serving the release from a local server, rather than mocking net.fetch, is what lets the suite catch the bundling class of failure that unit tests cannot see. The tiny checksum-backed asset keeps that honest without a large download. Claude Opus 4.8 Codex GPT 5.6 Sol (in-scope)
  • The provenance guard is applied at both readers of the cache (hasQueuedUpdate at line 211, checkForUpdates at line 434), with a comment at line 209 stating why one-sided enforcement would not hold. Claude Opus 4.8 Codex GPT 5.6 Sol (in-scope)
  • Centralizing source identity in updateSources() keeps cache writes and both readers on identical provenance rules. Codex GPT 5.6 Sol (in-scope)
  • delete_pending_update is called from factory_reset rather than only from the new suite, so the leak it prevents is closed for every bats file. It deletes entries inside $PATH_CACHE without removing the directory, which keeps factory-reset.bats's assert_exists "$PATH_CACHE" intact. Claude Opus 4.8 (in-scope)
  • The update server uses Node's own http module, with no external dependency for the test harness to drift against. Gemini 3.5 Flash (in-scope)

Testing Assessment ¶

No reviewer could execute the jest suite: the review worktrees carry no node_modules. Codex and Claude both stated this limitation; the assessments below rest on reading, plus the checks Codex could run (ShellCheck, shfmt, Node syntax checking, live responder/release/asset probes against the mock server, and macOS LaunchServices environment propagation).

Untested scenarios, highest risk first:

  1. setHasQueuedUpdate preserving provenance. See the Design Concern above. A one-line assertion that the fields survive a setHasQueuedUpdate(true) would pin the contract.
  2. getUpdater with RD_FORCE_UPDATES_ENABLED set and no responder override, confirming a configured server passes through untouched. S3's fixture change covers this.
  3. The Linux AppImage and Win32 download paths, skipped by design (upgrade.bats:22-27). The win32 arm of assetName() is consequently never exercised.
  4. Whether the update server was reached at all. The request trace is written to $PATH_LOGS/update-server.txt but never asserted. Failure stays attributable, because a missed override fails at Found version v9.9.9, so the trace is correctly diagnostic rather than an assertion.

Acknowledged Limitations ¶

  • Provenance records the overrides, not the configuration actually used (LonghornProvider.ts:188-193). Confirmed accurate this round: updateSources() never reads this.configuration.upgradeServer, so a fork's cache is indistinguishable from an official one. Reaching it requires a second build writing the same cache path.
  • Caches predating the provenance fields are discarded (LonghornProvider.ts:135-140). Every existing installation pays one extra Upgrade Responder query and forgoes one launch's install-on-startup the first time it runs this build, then self-heals within the same session. Both halves are covered by the tests at lines 603 and 617.
  • macOS installs nothing after the download (upgrade.bats:86-87). The Squirrel.Mac rejection is expected and leaves an error in update.log that no assertion covers.
  • The suite runs on macOS only (upgrade.bats:22-27), with per-platform reasons recorded for Linux (AppImage-only downloads) and Windows (bats runs in WSL).

Review Process Notes ¶

Skill improvements ¶

  • Set the per-pass agent deadline from the reasoning effort and the assembled prompt length, not from diff size alone. A small diff reviewed at maximum effort against a long injected context routinely outruns a deadline chosen by byte count, and a watchdog kill costs a full retry. When retrying after a timeout, budget the retry above the deadline that just expired rather than repeating it.
  • When injecting prior-round context, state the declined findings and the reasons they were declined, but do not tell agents that a clean review is an expected outcome. Naming the expected result raises the reporting threshold for every reviewer at once, so a round in which most agents return clean then carries less information than it appears to.
  • Require each reviewer to mark every claimed verification as executed or reasoned, and to name what blocked any execution it could not perform. A review that announces a test run and then reports no result is indistinguishable from one that ran the tests and found nothing.
  • Anchor the polling gate's forbidden-path patterns to the review workdir's generated outputs rather than matching review-*.md anywhere in a command. The substring match denies legitimate reads of context files whose names embed the word, such as a repository-overview file passed in during setup.

Repo context updates ¶

  • [repo] Reviewers cannot execute the jest suite from a review worktree, because the tree carries no node_modules. Running jest anyway fails with Cannot find name 'it'-style errors that read as broken test files rather than a missing dependency. Treat any claimed green jest run from a review worktree as unverified.
  • [repo] yarn test runs only in the ubuntu-latest job of .github/workflows/test.yaml; the windows-latest and macos-latest matrix jobs run lint and license checks without running jest. A test failure mode specific to Windows or macOS therefore reaches local developers rather than CI, and should be severity-rated on that basis.
