## Suggestions

S1. **Nothing tells the user a compose project is split across pages** — `pkg/rancher-desktop/pages/Containers.vue:142` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro] (round 2 I4, downgraded)

```
              <span v-if="!!collapsed[group.ref]"> ({{ group.rows.length }})</span>
```

`groupedRows` groups `pagedRows` (`grouping.js:27`) and `Containers.vue:19` pins the page at 10 rows, so a 12-container project gets a group header on each page covering that page's slice. Page-scoped selection is the table's own model, so the scope itself is consistent. The gap is disclosure. The table's paging line reads "1 - 10 of 12 Items", but a group's total appears nowhere, and this count shows the page slice and only while collapsed. The new `aria-label` meanwhile promises "Select all containers in project X", which S2 will make reachable and which is false for a split project.

```ts repro
// Save as pkg/rancher-desktop/pages/__tests__/probe-group-paging.spec.ts; run:
//   BROWSERSLIST_IGNORE_OLD_DATA=1 node --experimental-vm-modules \
//     node_modules/jest/bin/jest.js --testPathPatterns probe-group-paging
/** @jest-environment node */
import grouping from '@pkg/components/SortableTable/grouping.js';
import selection from '@pkg/components/SortableTable/selection.js';

const groupedRows = (grouping as any).computed.groupedRows;
const watcher = (selection as any).watch.pagedRows;

/** Containers.vue passes group-by="projectGroup" and :rows-per-page="10". */
const PAGE = 10;

function project(name: string, n: number) {
  return Array.from({ length: n }, (_, i) => ({ id: `${ name }-${ i }`, projectGroup: name }));
}

function groupFor(rows: any[]) {
  return groupedRows.call({ groupBy: 'projectGroup', pagedRows: rows })[0];
}

function tableCtx(over: any) {
  return {
    keyField: 'id', selectedRows: [], pagedRows: [],
    updateInput: () => {}, $emit: () => {}, $nextTick: (cb: () => void) => cb(), ...over,
  };
}

it('group checkbox scope vs. the page', () => {
  const big = project('demo', 12);
  const small = project('tiny', 4);

  const page1 = groupFor(big.slice(0, PAGE));
  const page2 = groupFor(big.slice(PAGE));

  console.log(`12-container project: page 1 header "${ page1.ref }" covers ${ page1.rows.length } rows,`,
    `page 2 header "${ page2.ref }" covers ${ page2.rows.length }`);

  // The user ticks the group header on page 1, then pages over.
  const ctx = tableCtx({ selectedRows: [...page1.rows], pagedRows: big.slice(PAGE) });

  watcher.call(ctx);
  console.log(`  after ticking the group on page 1 and paging over: ${ ctx.selectedRows.length } still selected`);

  // Counter-case: a project that fits on one page, through a rows recompute
  // that rebuilds every wrapper (what Images.vue and Volumes.vue do).
  const one = groupFor(small);
  const rebuilt = small.map((r) => ({ ...r }));
  const ctx2 = tableCtx({ selectedRows: [...one.rows], pagedRows: rebuilt });

  watcher.call(ctx2);
  console.log(`4-container project: header covers ${ one.rows.length } rows;`,
    `after a full wrapper rebuild ${ ctx2.selectedRows.length } still selected,`,
    `re-bound to the current instances: ${ ctx2.selectedRows[0] === rebuilt[0] }`);
});
```

S2. **The new `aria-label` never reaches the element with `role="checkbox"`** — `pkg/rancher-desktop/pages/Containers.vue:123` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.5 Flash] (round 2 S3, still open)

```
              :aria-label="t('containers.manage.table.group.selectAll', { group: group.ref })"
```

`Checkbox` declares no `aria-label` prop and does not set `inheritAttrs: false`, so the attribute falls through to the component root, `<div class="checkbox-outer-container">`. The focusable element is an inner `<span role="checkbox">` whose `aria-label` binds to the component's own `label` prop, unset here. An ancestor's `aria-label` does not name a descendant, so the control is still announced unnamed and `d3b3a6b68`'s claim that "the checkbox has an accessible name" does not hold.

S4. **`Images.vue`'s `_key` embeds the array index, so the re-bind drops its selection** — `pkg/rancher-desktop/components/Images.vue:206` [Codex GPT 5.6 Sol]

```js
            _key: `${ index }-${ image.imageID }-${ this.imageTag(image.tag) }`,
```

Images is one of the two tables `043bc3dac` exists for, and the one whose keys are not stable. `keyedImages` numbers rows by position in `this.images`, so pulling or deleting any earlier image renumbers every later one; the watcher then finds no entry for a selected row's old key and drops it. Nothing is mis-targeted. But the selection the fix is meant to preserve still disappears on Images whenever the list changes ahead of it. Filtering is safe, since `keyedImages` is numbered before `filteredImages` runs.

```ts repro
// Save as pkg/rancher-desktop/pages/__tests__/probe-image-key.spec.ts; run:
//   BROWSERSLIST_IGNORE_OLD_DATA=1 node --experimental-vm-modules \
//     node_modules/jest/bin/jest.js --testPathPatterns probe-image-key
/** @jest-environment node */
import selection from '@pkg/components/SortableTable/selection.js';

const watcher = (selection as any).watch.pagedRows;

/** Images.vue:206 — `_key: `${ index }-${ image.imageID }-${ this.imageTag(image.tag) }`` */
const keyed = (images: string[]) =>
  images.map((id, index) => ({ _key: `${ index }-sha256:${ id }-latest`, imageID: id }));

function rebind(before: string[], after: string[], pick: string) {
  const rows = keyed(before);
  const ctx = {
    keyField: '_key', pagedRows: keyed(after),
    selectedRows: [rows.find(r => r.imageID === pick)],
    updateInput: () => {}, $emit: () => {}, $nextTick: (cb: () => void) => cb(),
  };

  watcher.call(ctx);

  return ctx.selectedRows.length;
}

it('Images.vue _key survives a list change only when no earlier image moves', () => {
  const all = ['alpine', 'busybox', 'nginx'];

  console.log('tick nginx, then delete alpine (an EARLIER image):',
    rebind(all, ['busybox', 'nginx'], 'nginx'), 'row(s) still selected');
  console.log('tick alpine, then delete nginx (a LATER image)  :',
    rebind(all, ['alpine', 'busybox'], 'alpine'), 'row(s) still selected');
  console.log('tick nginx, rows merely rebuilt, same order     :',
    rebind(all, all, 'nginx'), 'row(s) still selected');
});
```

```text repro-output
$ BROWSERSLIST_IGNORE_OLD_DATA=1 node --experimental-vm-modules node_modules/jest/bin/jest.js --testPathPatterns probe-image-key
```

S6. **`prevNode` is not re-bound, so the shift-click anchor still goes stale** — `pkg/rancher-desktop/components/SortableTable/selection.js:158` [Claude Opus 5]


The watcher rebinds `selectedRows` but leaves `this.prevNode` pointing at a discarded object. ## Design Observations

### Concerns

- **Clicking a partly selected group clears it rather than completing it (in-scope)** [Claude Opus 5, Gemini 3.1 Pro] — `Checkbox.clicked()` emits `!value`, and `Containers.vue:124` now makes `value` true in the mixed state, so the click deselects. Both agents called this a regression against the tri-state convention. Round 2 asked for it, though, and it matches the app's own select-all: `THead.vue:118` drives that control with `isAll = howMuchSelected !== NONE`, which clears from partial in exactly the same way. Codex made the same comparison independently. Gemini's proposed revert costs the rendering. I confirmed `:value="isGroupSelected(group)"` leaves `input.checked` false, which is round 2's blank-box bug, because the CSS draws the dash only under `input:checked`. If Jan wants mixed → all, Claude's patch, `@update:value="setGroupSelected(group, !isGroupSelected(group))"`, keeps the dash as well.
- **Bulk Delete over a mixed group silently deletes a subset (future)** [Codex GPT 5.6 Sol, Claude Opus 5] — `selection.js:106` enables an action when *any* selected row supports it, and `applyTableAction` (line 554) then filters to the enabled subset. Delete is enabled only for stopped containers, so one click on a mixed compose project deletes its stopped members and leaves the rest, with no message. Pre-existing and untouched, but the group checkbox is what makes it easy to hit; the new e2e suite encodes the workaround by stopping the project before deleting it. `actions.js:56` already computes the actionable count for its hover tooltip.
- **`_rowCache` still cannot be removed, contrary to round 2's expectation (in-scope)** [Gemini 3.1 Pro, Claude Opus 5, Gemini 3.5 Flash] — round 2 predicted the re-bind would let `Containers.vue:269`'s cache go. The watcher reassigns `selectedRows` synchronously but emits `selection` on `$nextTick`, so the page's own copy lags one tick. With stable row objects the `changed` short-circuit skips both, and the lag never appears; drop the cache and the group checkbox renders unchecked for one frame on every docker event.
- **The page reaches into the table mixin's internals (in-scope)** [Claude Opus 5] — `setGroupSelected` calls `this.$refs.sortableTableRef.update(...)` (`Containers.vue:612`), and `update()`'s `(toAdd, toRemove)` contract is exactly what this round changed. A narrow public API (`selectRows`/`deselectRows`, or a callback in the `group-row` slot scope beside `fullColspan`) would let the mixin move without breaking pages.

### Strengths

- **The fix is in `selection.js`, not in the page (in-scope)** [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.5 Flash] — the root cause is the identity-keyed `:value="selectedRows.includes(row.row)"` at `index.vue:1327`, so Images and Volumes get the fix too. Volumes has no `@selection` handler and depends on the table's internal selection, which is what made round 2's C1 destructive there.
- **The `changed` short-circuit keeps the watcher inert for stable-identity tables (in-scope)** [Claude Opus 5] — `selection.js:151` costs one Map build per event on Containers and emits nothing, which is what keeps the observation above from becoming a visible flicker.
- **`actions.js` fixes a `TypeError` along the way (in-scope)** [Claude Opus 5] — the old `else` branch dereferenced `selectedRowsText.style` on the path where that variable is null, reachable whenever the layout pass runs before `v-if` mounts the label, and its value `'none;'` was invalid CSS besides.
- **The new unit tests pin the fixes, not the mocks (in-scope)** [Claude Opus 5] — both new specs drive the real mixin functions with a hand-built `this`; the mutation check under Testing Assessment confirms they fail against round 2's `selection.js`.

Untested scenarios, highest risk first:

1. **A compose project larger than one page** (S1). No unit or e2e fixture creates more than two containers in a group.
2. **The group checkbox's click in any state but "nothing selected."** The new unit tests call `setGroupSelected` directly and stub `Checkbox` with `{ template: '<div />' }`, so they never exercise the `:value`/`@update:value` pair, the one the round changed and the one the disagreement above is about.
3. **The re-bind against a table that really rebuilds rows**, the case `043bc3dac` exists for. Nothing mounts `Images.vue` or `Volumes.vue`, recomputes `rows`, and asserts the checkboxes stay ticked; S4 is what that test would have caught.
4. **`$nextTick` ordering.** `selection.spec.ts:18` stubs `$nextTick` as a synchronous call, so the spec cannot see the one-tick window in which the page's `selectedRows` copy is stale.
5. **Bulk stop/delete under containerd.** The new e2e block pins Moby; grouping derives from labels for both engines, but containerd routes through a different subscriber and a namespace-scoped `listContainers`.
6. **Bulk actions after they move into the overflow dropdown** (S9).

## Review Process Notes

### Skill improvements

- When a change adds an attribute to a component (an accessible name, a test hook, a data attribute) instead of to a plain element, read the component's template to find its root element and whether it sets `inheritAttrs: false`, before accepting the fix. A fall-through attribute is applied to the root, which is usually a wrapper, while the element with the role, the focus, or the handler is nested inside it. Such a change reads as correct in the diff and does nothing at runtime.
- When a fix identifies records by a key field so a selection or a cache is still valid after a refresh, enumerate every consumer's definition of that key and check it is stable across exactly the updates the fix is meant to cover. A key built from an array index, a render counter, a position or a timestamp is unique but not stable, so the fix silently no-ops for that consumer, often the very one that motivated it.
- When a change adds a user-visible string for a control that renders once per member of a shared category, enumerate the other values that category takes before accepting the wording. A string written for the motivating case is frequently false for its siblings, and the error is expensive to correct once the key has reached translators.
- Before accepting a proposed revert of an expression a prior round changed, apply the patch and re-run the check that motivated the original change. A patch that restores the earlier expression restores the earlier defect, and when both changes are within a few lines of each other, the reviewer proposing it has usually read only one of them.

### Repo context updates

- [repo] `@rancher/components`' `Checkbox` renders `<div class="checkbox-outer-container">` as its root and does not set `inheritAttrs: false`, so every fall-through attribute (`aria-label`, `data-testid`, `class`) is applied to that wrapper div. The focusable element is an inner `<span role="checkbox">` whose `aria-label` binds only to the component's `label` prop. An accessible name must be passed as `:label`, hidden with a scoped rule if no visible text is wanted, never as `aria-label`.
- [repo] `components/Images.vue` builds each row's `_key` as `${index}-${imageID}-${tag}`, numbering rows by position in the unfiltered image list, so an image's key changes whenever an image ahead of it is added or removed. Any `SortableTable` behaviour that matches rows by `keyField` across a refresh therefore no-ops silently on Images; `pages/Containers.vue` (`id`) and `pages/Volumes.vue` (`Name`) have stable keys. Filtering alone is safe, since keys are assigned before filtering.
- [repo] `store/container-engine.ts` gives every container a `projectGroup`: the `com.docker.compose.project` label when present, `<namespace>/<pod>` for containers with Kubernetes pod labels, and the literal `Standalone Containers` otherwise. Any UI text attached to a container group must read correctly for all three; wording that assumes a compose project is wrong for two of them.
- [repo] UPDATE the entry stating that `SortableTable`'s `update(toAdd, toRemove)` matches removals against a hard-coded `_key` and pushes additions without deduplicating. Both halves change once the containers group-selection work lands. Removal compares `get(r, this.keyField)`, and additions are filtered against the already-selected keys. The `_key` trap it warns about is real history but no longer describes the code; the entry should instead say that `update()` is key-based on both paths, so a table whose `keyField` is absent or non-unique collapses its whole selection to one row.

## Design Observations

### Concerns

- **Bulk Delete over a mixed group silently deletes a subset (future).** `selection.js:99-107` enables a bulk action when *any* selected row supports it, and `applyTableAction` (line 554) then filters to the enabled subset. The group checkbox makes this far easier to hit: one click selects a whole compose project of mixed running/stopped containers, Delete is enabled, and only the stopped ones go — with no message. Pre-existing and untouched by the diff, but the new affordance is what will surface it. A cheap improvement: have `applyTableAction` compare `executableSelection.length` against `selectedRows.length` and surface the difference (the `actionTooltip` in `actions.js:56-71` already computes exactly that number for hover).
- **The page reaches into the table's mixin to change selection (in-scope).** `setGroupSelected` calls `this.$refs.sortableTableRef.update(...)` (`Containers.vue:609-615`). `update()` is an internal method of the selection mixin with a `(toAdd, toRemove)` contract that this round just changed. A narrow public API on `SortableTable` — `selectRows(rows)` / `deselectRows(rows)`, or a `select` callback passed into the `group-row` slot scope alongside `fullColspan` — would let the mixin's internals move without breaking pages.
- **`clearSelection()` splices the array it is iterating (future).** `selection.js:566` passes `this.selectedRows` as `toRemove`, and `update()`'s `forEach` at line 472 walks that same array while line 476 splices it, so it would drop every other row. Still no caller anywhere in the repo (grepped), and the watcher's reassignment does not change it. Worth `this.update([], this.selectedRows.slice())` while the file is open.

### Strengths

- The re-bind was put in `selection.js` rather than worked around in `Containers.vue`, so Images and Volumes get the fix too — the right layer for a bug whose root cause is the identity-keyed `:value="selectedRows.includes(row.row)"` at `index.vue:1327`.
- The `changed` short-circuit at `selection.js:151-156` keeps the watcher a no-op for tables with stable row objects, so the common Containers path costs one Map build per event and emits nothing spurious.
- `actions.js:104-110` quietly fixes a real `TypeError` — the old `else` branch dereferenced `selectedRowsText.style` on the path where that variable is falsy — and drops the invalid `'none;'` value.

1. **SortableTable Selection API**: `selection.js` and its methods (`update`, `updateInput`) lack clear JSDoc comments detailing the contract of key-based vs. object-identity-based tracking.
2. **Containers Row Caching Constraint**: While `_rowCache` is correctly kept out of `data()` to prevent unnecessary reactivity tracking, a small comment explaining why it is placed in `created()` instead of `data()` would prevent future developers from accidentally refactoring it into reactive data.

### Acknowledged Limitations

- **SortableTable Page Selection Clearing**: As discussed, when the user navigates across pages, `selectedRows` is re-bound to the new page's rows, meaning any selection on the previous page is dropped. This is an acknowledged design limitation of `SortableTable`.
- **Bulk Actions Over Mixed States**: Clicking bulk Delete on a selection with running containers silently skips them (since bulk action filters are best-effort). This is a pre-existing limitation of bulk-action filtering.
