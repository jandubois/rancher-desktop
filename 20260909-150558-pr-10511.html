Design Observations ¶

Concerns ¶

  • Clicking a partly selected group clears it rather than completing it (in-scope) Claude Opus 5 Gemini 3.1 Pro — Checkbox.clicked() emits !value, and Containers.vue:124 now makes value true in the mixed state, so the click deselects. Both agents called this a regression against the tri-state convention. Round 2 asked for it, though, and it matches the app's own select-all: THead.vue:118 drives that control with isAll = howMuchSelected !== NONE, which clears from partial in exactly the same way. Codex made the same comparison independently. Gemini's proposed revert costs the rendering. I confirmed :value="isGroupSelected(group)" leaves input.checked false, which is round 2's blank-box bug, because the CSS draws the dash only under input:checked. If Jan wants mixed → all, Claude's patch, @update:value="setGroupSelected(group, !isGroupSelected(group))", keeps the dash as well.
  • Bulk Delete over a mixed group silently deletes a subset (future) Codex GPT 5.6 Sol Claude Opus 5 — selection.js:106 enables an action when any selected row supports it, and applyTableAction (line 554) then filters to the enabled subset. Delete is enabled only for stopped containers, so one click on a mixed compose project deletes its stopped members and leaves the rest, with no message. Pre-existing and untouched, but the group checkbox is what makes it easy to hit; the new e2e suite encodes the workaround by stopping the project before deleting it. actions.js:56 already computes the actionable count for its hover tooltip.
  • _rowCache still cannot be removed, contrary to round 2's expectation (in-scope) Gemini 3.1 Pro Claude Opus 5 Gemini 3.5 Flash — round 2 predicted the re-bind would let Containers.vue:269's cache go. The watcher reassigns selectedRows synchronously but emits selection on $nextTick, so the page's own copy lags one tick. With stable row objects the changed short-circuit skips both, and the lag never appears; drop the cache and the group checkbox renders unchecked for one frame on every docker event.
  • The page reaches into the table mixin's internals (in-scope) Claude Opus 5 — setGroupSelected calls this.$refs.sortableTableRef.update(...) (Containers.vue:612), and update()'s (toAdd, toRemove) contract is exactly what this round changed. A narrow public API (selectRows/deselectRows, or a callback in the group-row slot scope beside fullColspan) would let the mixin move without breaking pages.

Strengths ¶

  • The fix is in selection.js, not in the page (in-scope) Claude Opus 5 Codex GPT 5.6 Sol Gemini 3.5 Flash — the root cause is the identity-keyed :value="selectedRows.includes(row.row)" at index.vue:1327, so Images and Volumes get the fix too. Volumes has no @selection handler and depends on the table's internal selection, which is what made round 2's C1 destructive there.
  • The changed short-circuit keeps the watcher inert for stable-identity tables (in-scope) Claude Opus 5 — selection.js:151 costs one Map build per event on Containers and emits nothing, which is what keeps the observation above from becoming a visible flicker.
  • actions.js fixes a TypeError along the way (in-scope) Claude Opus 5 — the old else branch dereferenced selectedRowsText.style on the path where that variable is null, reachable whenever the layout pass runs before v-if mounts the label, and its value 'none;' was invalid CSS besides.
  • The new unit tests pin the fixes, not the mocks (in-scope) Claude Opus 5 — both new specs drive the real mixin functions with a hand-built this; the mutation check under Testing Assessment confirms they fail against round 2's selection.js.

Review Process Notes ¶

Skill improvements ¶

  • When a change adds an attribute to a component (an accessible name, a test hook, a data attribute) instead of to a plain element, read the component's template to find its root element and whether it sets inheritAttrs: false, before accepting the fix. A fall-through attribute is applied to the root, which is usually a wrapper, while the element with the role, the focus, or the handler is nested inside it. Such a change reads as correct in the diff and does nothing at runtime.
  • When a fix identifies records by a key field so a selection or a cache is still valid after a refresh, enumerate every consumer's definition of that key and check it is stable across exactly the updates the fix is meant to cover. A key built from an array index, a render counter, a position or a timestamp is unique but not stable, so the fix silently no-ops for that consumer, often the very one that motivated it.
  • When a change adds a user-visible string for a control that renders once per member of a shared category, enumerate the other values that category takes before accepting the wording. A string written for the motivating case is frequently false for its siblings, and the error is expensive to correct once the key has reached translators.
  • Before accepting a proposed revert of an expression a prior round changed, apply the patch and re-run the check that motivated the original change. A patch that restores the earlier expression restores the earlier defect, and when both changes are within a few lines of each other, the reviewer proposing it has usually read only one of them.

Repo context updates ¶

  • [repo] @rancher/components' Checkbox renders <div class="checkbox-outer-container"> as its root and does not set inheritAttrs: false, so every fall-through attribute (aria-label, data-testid, class) is applied to that wrapper div. The focusable element is an inner <span role="checkbox"> whose aria-label binds only to the component's label prop. An accessible name must be passed as :label, hidden with a scoped rule if no visible text is wanted, never as aria-label.
  • [repo] components/Images.vue builds each row's _key as ${index}-${imageID}-${tag}, numbering rows by position in the unfiltered image list, so an image's key changes whenever an image ahead of it is added or removed. Any SortableTable behaviour that matches rows by keyField across a refresh therefore no-ops silently on Images; pages/Containers.vue (id) and pages/Volumes.vue (Name) have stable keys. Filtering alone is safe, since keys are assigned before filtering.
  • [repo] store/container-engine.ts gives every container a projectGroup: the com.docker.compose.project label when present, <namespace>/<pod> for containers with Kubernetes pod labels, and the literal Standalone Containers otherwise. Any UI text attached to a container group must read correctly for all three; wording that assumes a compose project is wrong for two of them.
  • [repo] UPDATE the entry stating that SortableTable's update(toAdd, toRemove) matches removals against a hard-coded _key and pushes additions without deduplicating. Both halves change once the containers group-selection work lands. Removal compares get(r, this.keyField), and additions are filtered against the already-selected keys. The _key trap it warns about is real history but no longer describes the code; the entry should instead say that update() is key-based on both paths, so a table whose keyField is absent or non-unique collapses its whole selection to one row.
