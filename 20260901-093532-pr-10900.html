Design Observations ¶

Concerns ¶

  • resolveTag probes only the newest release (future) Claude Opus 5. latestVersion reduces to the maximum version, so resolveTag gets one version and two tags. Epinio published v0.1.4 and v0.1.5 with no image under either form; I confirmed both return 404 today. Had the daily run fired between those releases and v0.1.6, the bump would have failed every day until an image appeared. Falling back to the newest version the registry actually serves would fix it, but that re-opens what @mook-as objected to in #8647, so any fallback should log which version it skipped.
  • The card label and the pinned tag diverge exactly where it matters (future) Claude Opus 5. A v prefix reaches the manifest only when the publisher has no unprefixed image, which is precisely when the string on the card is a tag the registry does not serve. Nothing in the app consumes the label, but command-api.yaml:563 documents application.extensions.installed as taking a tag, so an admin copying a version off the card into a deployment profile gets a reference that 404s.
  • Extension bump PRs still carry an empty body Claude Opus 5. getBody() returns '' for anything that is not a GitHubDependency, and Extension extends VersionedDependency directly. Pre-existing and out of scope, but the PR title will now say 0.1.6 while the diff pins whatever resolveTag chose, and a body is where that belongs.

Strengths ¶

  • imageTagExists fails closed on any status that is neither success nor 404, with the reason stated in a comment (registry.ts:81-82) Claude Opus 5 Codex GPT 5.6 Sol. That is the right default for a tool that writes pins, and it is the property most likely to be simplified away later.
  • The rationale for skipping docker manifest inspect (registry.ts:4-5) is accurate Claude Opus 5. I ran it against a public ghcr.io image and got denied: denied.
  • MarketplaceCard.spec.ts:35-37 asserts on versionedExtension, not just the label Codex GPT 5.6 Sol Claude Opus 5. It pins the half that must not change, which is the harder half to remember. Outcome: the spec was removed. Three of its four tests exercised a one-line display regex, and versionedExtension never reads displayVersion, so the invariant is held by the comment at the site instead. Seven of 52 components have specs; a presentational one is not the house pattern.
  • Each of the four commits carries its own test, and the commit bodies state facts I could check. I confirmed the shared-digest claim in 1407d8fc7 and the open-webui tag history in 66d43fd7c against the live registry.

Ranked by risk, what it does not cover:

Review Process Notes ¶

Skill improvements ¶

  • [ ] A review session launched inside a git worktree cannot write to the reviews directory in the main checkout, and cannot run the multi-statement shell forms the setup steps use. Before assembling any context, check whether the session is worktree-isolated. When it is, run every helper as a single command with fully-qualified paths rather than assigning shell variables, and settle where the report will be written before spending agent time, since the deliverable's home lies outside the isolation boundary.
  • [ ] Shell state does not persist between tool calls, so a step that imports variables by eval-ing a helper's output leaves every later step referring to unset names. Have the helper's output read once and substitute the values literally into each later command.
  • [ ] Confirming that a reviewer's environment could have produced a run result is not enough to repeat it. Compare the reported numbers against the suite's own output: an agent with a working toolchain can still report a per-suite breakdown that does not match what the runner prints. When the totals disagree, label every execution claim from that agent unverified, whatever its environment allowed.

Repo context updates ¶

  • [ ] .gitignore lists /node_modules/ with a trailing slash, which matches directories only. An agent that symlinks the main checkout's node_modules into its worktree leaves an untracked entry visible in git status, while one that copies or installs a real directory leaves none. Read a clean git status in a review worktree as evidence about the agent's method, not as proof it modified nothing.
  • [ ] getExtensions(true) filters the extension catalog to entries carrying a github_repo, and that filtered list is what the dependency manager consumes. Extensions without one never reach latestVersion, so its reduce over an empty array cannot throw for them. Do not file that as a defect.
  • [ ] Docker Hub answers 401, not 404, for a repository that does not exist, even after a successful anonymous token exchange. Code that classifies registry responses by status will report a renamed, deleted, or private repository as an authentication failure. Check that distinction whenever a change reads registry status codes.
