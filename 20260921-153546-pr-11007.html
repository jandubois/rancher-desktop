Executive Summary ¶

The PR fixes four causes of broken multi-select on the Containers table, and all four work. But re-pointing the selection by key after a refresh assumes a key always names the same row, and the Images key includes the list position. When a pull or delete shifts the list, the selection can jump to the same image under another name, and bulk Delete targets that tag. No test catches an undone deselect fix or a refresh that keeps stale rows.

Design Observations ¶

Concerns ¶

  • The selection is compared two ways (future) Claude Opus 5. update() and the range anchor match rows by key, while toggle(), isSelected, onRowContext(), groupIdx() and the row checkbox match by identity. Only the pagedRows watcher keeps the two consistent, which is what I3's mutation breaks. Storing a set of selected keys and deriving selectedRows from pagedRows would remove the re-pointing step, at the cost of touching every selection method, and it needs I1's stable key first.
  • The identity fallback compares a Vue proxy with a raw row (future) Claude Opus 5. For a row without the key field, isSameRow() falls back to ===, but selectedRows hands its callbacks reactive proxies while pagedRows can hold a page's raw objects. Claude's probe (not re-run here) fed key-less rows from a parent computed and got 6 selected rows out of 3 after select-all twice; toRaw() on both sides fixed it. No table has key-less rows, and nodeForRow() cannot click one.
  • A click on an element inside a link counts as a plain cell click (future, pre-existing) Claude Opus 5. nodeForEvent() checks only e.target.tagName, so a click on an icon inside a link (pkg/rancher-desktop/components/DiagnosticsBody.vue:195, pkg/rancher-desktop/pages/extensions/installed.vue:228) follows the link and selects the row. Both tables set :table-actions="false", so nobody sees that selection. tgt.closest('a, button, .btn') would cover nested content.
  • clearSelection() removes only every other row (future, pre-existing) Claude Opus 5. It passes the live selectedRows array to update() as toRemove, and update() splices that array while iterating it. Nothing calls it.
  • The JSDoc import in Containers.vue does not resolve (future, pre-existing) Claude Opus 5. Line 149 imports Container from '@pk/store/containers', but the alias is @pkg and the type is in store/container-engine.ts. The new {RowItem} annotations depend on it; only editors read them.

Strengths ¶

  • Real events in the spec (in-scope) Claude Opus 5. Lowercasing the tag selectors lets the spec mount the real SortableTable and dispatch real mouse events, which is how the link and anchor bugs became testable at all.
  • Anchor lookup by key (in-scope) Claude Opus 5. onRowClick() finds the range anchor by key at click time, so the anchor needs no re-pointing of its own.
  • One row-equivalence helper (in-scope) Codex GPT 5.6 Sol Gemini 3.5 Flash. isSameRow() serves removal, deduplication, the refresh and the anchor lookup.
  • Fresh row objects after a refresh (in-scope) Codex GPT 5.6 Sol. Re-pointing hands bulk actions the rebuilt rows, so their availableActions reflect the current container state.
  • No duplicate rows from select-all (in-scope) Claude Opus 5. The duplicate check in update() also stops select-all from adding rows twice; at the merge-base, select-all twice gave 6 rows out of 3 (Claude's probe).

Acknowledged Limitations ¶

  • Do not re-suggest ${ image.imageID }-${ this.imageTag(image.tag) } as the Images row key (Gemini 3.1 Pro's fix for I1). It is the 2021 key that 406ad0143 extended with the list index. Retagged images share it, and with it applied, a plain click on registry.example.com/app selected app:1.0 in I1's probe.
  • Do not re-suggest skipping updateInput() for rows that are in both toAdd and toRemove (Gemini 3.5 Flash's suggestion). The saving is one page of rows per refresh. A plain click calls update([node], content), so the clicked row is in both lists, and the patch would never give it row-selected (reasoned from the code, not run).

Review Process Notes ¶

Skill improvements ¶

  • When a change starts using an existing field as an identity across refreshes, reloads or re-renders, read every producer of that field, not only the consumer under review. A field that only had to be unique within one snapshot may be built from list position, iteration order or a counter, and after the data shifts it names a different entity. Flag a producer like that as a wrong-target bug when the identity drives an action, not as a missed match.
  • When a test claims that a rebuild or refresh preserves object references, check how it compares. A value-equality assertion (toEqual, deepEqual) against fixtures built deep-equal to the originals passes whether the code re-points references or keeps stale ones. Ask for an identity assertion, or for an action whose result depends on identity.
