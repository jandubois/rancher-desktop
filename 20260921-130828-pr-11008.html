Executive Summary ¶

The PR adds a rows-per-page selector to SortableTable's paging footer, backed by the existing ROWS_PER_PAGE preference, and lets Containers and Volumes follow it. The selector, its visibility rules and the translations work, and the new spec, lint, typecheck and i18n gate pass. But the app forgets the choice on every restart. Renderer pages load from app://, where Chromium stores no cookies, so the commit message's persistence claim is false. CI has not run yet.

Design Observations ¶

Concerns ¶

  • Where renderer preferences persist (in-scope). per-page is the first preference anything in Rancher Desktop writes, and both channels of the dashboard-derived prefs store are dead here. asUserPreference saves through a management module that entry/store.ts never registers, and asCookie writes cookies that app:// drops (I1). Whatever I1's fix picks sets the pattern for the next preference. localStorage is the smallest channel that works; the settings file is the choice if rdctl or deployment profiles should see the value. Claude Opus 5
  • i18n's R_LOCALE fallback cannot work (future). store/i18n.js:190-191 calls the cookie "a fallback for a window opened without" the locale URL parameter, but the I1 probe shows app:// never keeps a cookie, so such a window starts in the default locale. The cookie database under ~/Library/Application Support/rancher-desktop/electron/ on the reviewer's machine has no rows at all. I1's localStorage option would fix this too. Claude Opus 5

Review Process Notes ¶

Skill improvements ¶

  • When a change relies on a storage or transport mechanism (cookies, localStorage, IPC, a file location) to deliver a behavior its description promises, verify the mechanism in the runtime the product ships, meaning the real origin, scheme, process and sandbox, rather than in the test environment. Test doubles and browser emulators accept writes the shipped runtime refuses, so a green unit test proves nothing about the promise.

Repo context updates ¶

  • [repo] The renderer loads from app:// (app://./index.html packaged, app:///index.html in dev), and Chromium stores no cookies for that scheme, even within one session. Anything the dashboard-derived code writes through $cookies, such as the prefs store's asCookie or i18n's R_LOCALE, is dropped; localStorage does persist there. Flag any change that relies on $cookies or asCookie to remember a value.
  • [repo] The prefs store's asUserPreference channel saves through a management Vuex module that entry/store.ts does not register, so it does nothing in Rancher Desktop; a preference that must persist needs another channel.
