## Executive Summary

The PR adds an `i18n-report validate` subcommand and a hand-written ICU MessageFormat parser mirroring intl-messageformat 11, gating each translation on placeholder, plural/select, tag, href/`data-*`, `@override`, and `@source` parity. The parser is faithful: it parses the entire en-us corpus and already caught a latent runtime crash in zh-hans. Two regex checks misfire on the shipping corpus — literal angle-bracket prose reads as HTML tags, and repeated href attributes collapse to the last.

All three reviewers converged on the attribute-collapse bug (I1); Claude and Codex also caught the tag-prose bug (I2). Both were confirmed by running `validate --locale=zh-hans` against the live corpus. Gemini raised plural-branch rigidity as Critical; the tool produced zero branch-parity errors on the current locales, so this review reframes it as an in-scope design decision (see Design Observations) with one live manifestation. One Gemini finding — a claimed search-and-replace corruption of `@override`/`@source` strings — did not survive verification and was dropped as a false positive.

## Important Issues

I1. **Repeated href/attribute values collapse to the last** — `report_validate.go:403-414` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]

```go
result := make(map[string]string)
for _, m := range matches {
    if m[2] != "" {
        result[m[1]] = m[2] // keyed by attr name; last href wins
    } else {
        result[m[1]] = m[3]
    }
}
```

`extractDataAttrs` keys attributes by name, so a value with two `<a href=...>` links keeps only the last. Two shipping strings carry two different links each: `needHelp` (`en-us.yaml:4905`, slack + github) and `istio…tip` (`en-us.yaml:1738`). A translation that changes the *first* target passes validation, defeating the stated guarantee that a translation must not change link targets (`report_validate.go:234-236`); the same collapse hides a reordered pair. The pattern `data-\w+` also misses hyphenated names such as `data-test-id`.

Fix: collect every occurrence per name and compare as sorted multisets.

```go
result := map[string][]string{}
for _, m := range matches {
    val := m[2]; if val == "" { val = m[3] }
    result[m[1]] = append(result[m[1]], val)
}
```

I2. **`tagRe` reads literal angle-bracket prose as HTML tags** — `report_validate.go:232` [Claude Opus 4.8, Codex GPT 5.5]

```go
var tagRe = regexp.MustCompile(`</?(\w+)[^>]*/?>`)
```

The regex counts every `<word…>` run as a tag, but the corpus uses angle brackets for literal prose. Running `validate --locale=zh-hans` today emits false errors on real keys: `detailText.binary` (`<Binary Data: {n, number} bytes>`, `en-us.yaml:1433`) and `advancedSettings.descriptions.ingress-ip-domain` (`<ingress-name>`, `<ip address of ingress controller>`, `en-us.yaml:4688`). Each yields a spurious missing/unexpected tag error that would block a correct translation once `@source` is populated. The corpus holds only eight real HTML tag names (a, b, br, code, li, p, pre, span).

Fix: match a known-tag allowlist so literal tokens are ignored.

```go
var tagRe = regexp.MustCompile(`(?i)</?(a|b|br|code|li|p|pre|span|ul)\b[^>]*/?>`)
```

## Suggestions

S1. **Duplicate ICU constructs of the same variable+keyword overwrite each other** — `report_validate.go:318-324` [Codex GPT 5.5, Gemini 3.1 Pro]

```go
enByKey := make(map[string]icuConstruct)
for _, c := range en {
    enByKey[c.Variable+","+c.Keyword] = c
}
```

`compareConstructs` keys constructs by `variable,keyword`, so a message with two `{count, plural, ...}` blocks keeps only the last; a missing branch in the earlier block goes unreported. No current corpus string trips this, so the risk is latent. Fix: group into `map[string][]icuConstruct` and compare positionally, or consume matched constructs from the slices.

S2. **`checkICU` re-parses each value three times** — `report_validate.go:163-164, 192-199, 297-304` [Claude Opus 4.8]

`checkICU` parses en and locale for the syntax check, then `checkPlaceholders` and `checkICUStructure` each parse both again — six `parseICU` calls per key. Parse once and pass `[]icuNode` down: performance is irrelevant for a CLI, but a single parse keeps the three call sites from drifting.

S3. **The locale file is read three times per run** — `report_validate.go:62,67,72` [Claude Opus 4.8]

`validateLocale` loads the locale through `loadYAMLFlat`, `loadYAMLDocument`, and `loadSources` — three reads and parses of one file. A single `yaml.Node` parse yields the flat values, the `@source` comments, and the override placement together.

S4. **`skipArgStyle` ignores apostrophe quoting** — `icu.go:289-304` [Gemini 3.1 Pro]

`skipArgStyle` counts braces to find a typed argument's closing brace but, unlike `parseText`, does not skip apostrophe-quoted regions. A style with a quoted literal brace (e.g. `{n, number, '{'}`) would miscount depth. No corpus string exercises this and simple number/date styles rarely contain braces, so the gap is theoretical; align it with `parseText`'s quote handling if typed styles grow.

## Design Observations

### Concerns

- **Exact ICU structural parity may reject valid locale-specific plurals** (in-scope) [Gemini 3.1 Pro] — `checkICUStructure` requires a translation's plural/select constructs and branch labels to match English exactly. Exact parity is right for `select` (gender, boolean), but `plural` uses locale-specific CLDR categories: Chinese needs only `other`, Polish needs `few`/`many`. On the current en + zh-hans locales the tool reports zero branch mismatches because zh-hans mirrors English's branches. It does already flag one case: `sortableTable.paging.generic`, where the Chinese dropped the nested `{count, plural}` (Chinese does not inflect) and validate reports `missing {count, plural, ...} construct`. The sibling `resource` key kept the structure, so today the drop reads as an inconsistency worth surfacing — but adding a `few`/`many` language would turn exact parity into blocked correct translations. Decide whether plural structure should be exact or relaxed to exact-match labels (`=N`) plus `other`. Gemini rated this Critical; the live impact is a single construct, hence the reframe.

- **Tag and attribute checks bypass the parser they ship beside** (future) [Codex GPT 5.5, Claude Opus 4.8] — Placeholder and plural/select checks use the intl-messageformat-mirroring parser, but the tag and attribute checks use a separate regex tokenizer. That tokenizer cannot tell HTML from literal prose (I2), ignores ICU apostrophe quoting (a `'<b>'` literal counts as a `<b>` tag), and collapses repeats (I1). Routing tag detection through the ICU grammar, which already models `<tag>…</tag>` rich text, would fold three defects into one path. The I2 allowlist is the cheap step; the parser-integrated model is the direction.

- **`@source` errors bury the structural findings** (future) [Claude Opus 4.8] — On zh-hans today, validate prints 2373 errors, 2348 of them `[source]`; the 16 placeholder, 7 tag, and 2 ICU findings — including the runtime crash — are lost in the noise. A `--check=<category>` filter or per-category counts would surface the high-value findings during locale migration.

### Strengths

- **The parser faithfully mirrors intl-messageformat** (in-scope) [Claude Opus 4.8, Gemini 3.1 Pro] — apostrophe quoting, `''` collapse, and `#`-scoping (significant only inside the nearest plural/selectordinal, literal inside a nested `select`) all match formatjs.
- **The gate already earns its keep** (in-scope) [Claude Opus 4.8] — it flagged `workload.validation.containerImage` in zh-hans (`容器{{name}`, a doubled brace) that would crash intl-messageformat at runtime.
- **`TestParseICURealCorpus` pins the parser to the whole en-us corpus** (in-scope) [Codex GPT 5.5, Claude Opus 4.8] — a strong guard on the fidelity claim.
- **Co-located `@source` keeps provenance on the key** (in-scope) [Codex GPT 5.5] — no parallel metadata file to drift.

## Review Process Notes

### Skill improvements

- When a change adds a regex that extracts or classifies a token type (HTML tags, placeholders, identifiers, attributes) from free-form text, run it against the project's real data before trusting it. Two failure modes stay hidden until real data hits them: the pattern over-matches literal text shaped like the token, and a result map keyed by token name silently drops duplicate occurrences. Flag both.
- When a change adds a check that enforces exact structural parity between a source artifact and a derived one, verify the derived form is allowed to match exactly. Derived forms often diverge legitimately along their varying dimension — locale (CLDR plural categories differ by language), platform, or version — so an exact-parity check rejects valid variants. Flag parity checks that assume the derived form must structurally mirror the source.

### Repo context updates

- [repo] Rancher Desktop's translation corpus (`pkg/rancher-desktop/assets/translations`) uses angle brackets for literal display text (`<Binary Data: N bytes>`, `<ingress-name>`), not only HTML. Real HTML tag names in the corpus are limited to a, b, br, code, li, p, pre, span. A tool that treats every `<word>` as an HTML tag produces false positives.
- [repo] The app ships two locales, en-us and zh-hans; zh-hans mirrors English's ICU plural branch structure (keeping never-selected branches) rather than using native CLDR categories. Exact plural-structure parity passes on the current corpus but would block correct translations once a `few`/`many` language is added.
- [repo] The `i18n-report validate` subcommand depends on `@source` snapshots that `i18n-report source` writes onto each translated key; running validate on a locale not yet processed by `source` floods the output with `[source]` errors.

### Executive Summary

The new `validate` command is well-scoped and has useful coverage, but the current checker has several gate-quality problems: it can reject valid translation text as HTML, miss changed link targets when a string has multiple links, and lose ICU construct occurrences when the same variable/keyword appears more than once.

#### Important Issues

I1. **Non-HTML angle text is treated as tags** — `src/go/i18n-report/report_validate.go:231-232` (important, regression)

```go
// tagRe matches HTML-like tags: <tag>, </tag>, <tag/>, <tag attr="...">.
var tagRe = regexp.MustCompile(`</?(\w+)[^>]*/?>`)
```

`tagRe` at line 232 treats any `<word...>` as an HTML tag, so existing non-HTML display text is reported as broken. For example, `detailText.binary` in `en-us.yaml:1433` is `'<Binary Data: {n, number} bytes>'`, and the valid translation at `zh-hans.yaml:932` becomes a missing `<Binary>` tag.
```diff
- var tagRe = regexp.MustCompile(`</?(\w+)[^>]*/?>`)
+ var tagRe = regexp.MustCompile(`(?i)</?(a|b|br|code|li|p|pre|span|ul)\b[^>]*>`)
```

```go
result := make(map[string]string)
```

### [Gemini 3.1 Pro]

### Executive Summary

This PR introduces an ICU MessageFormat parser and structural validator to ensure translation files match the English source. While the parser effectively mirrors the runtime's lenient behavior, the validation rules enforce exact structural parity on locale-specific plural branches, which will break translations for languages with different pluralization rules. Additionally, logic errors in duplicate handling cause the validator to silently skip checks for duplicate HTML attributes and repeated constructs. Finally, a global search-and-replace operation corrupted strings and comments throughout the PR.

### Findings

#### Critical Issues

**C1. `compareBranchLabels` forces locale-specific plural branches to match English** — `src/go/i18n-report/report_validate.go:368-386`

```go
	for _, b := range locale.Branches {
		if !enBranches[b] {
			errors = append(errors, validationError{
				Key:     key,
				Check:   catICU,
				Message: fmt.Sprintf("unexpected branch %q in {%s, %s, ...}", b, locale.Variable, locale.Keyword),
			})
		}
	}
```

This logic asserts that the branches in a translated `plural` construct exactly match those in the English source. While correct for `select`, this breaks `plural` constructs. ICU MessageFormat `plural` relies on CLDR plural categories (`zero`, `one`, `two`, `few`, `many`, `other`) which are intrinsically locale-specific. English uses `one` and `other`, whereas Chinese only uses `other`, and Polish requires `one`, `few`, `many`, and `other`. 

By enforcing exact branch parity, this gate will actively reject correct translations for languages requiring `few`/`many`, and will force translators of languages like Chinese to maintain dead `one` branches, effectively halting the localization pipeline.

**Fix:** For `plural` and `selectordinal` constructs, skip the branch parity check, or only enforce that exact-match branches (e.g., `=0`, `=1`) and the fallback `other` branch are preserved. Exact parity should only apply to `select`.

**I2. `compareConstructs` overwrites identically keyed constructs, dropping structural checks** — `src/go/i18n-report/report_validate.go:339-345`


`compareConstructs` places `icuConstruct` records into a map keyed by `Variable+","+Keyword`. If the English source contains multiple identical constructs (e.g., two `{count, plural, ...}` blocks) in the same string, the map overwrites earlier occurrences. As a result, the validator drops the branch and nested-construct checks for all but the last occurrence, silently accepting a translation that omits or mangles the earlier constructs.

`skipArgStyle` consumes characters for typed ICU arguments (e.g., `{when, date, ...}`) by counting nested braces. However, it does not respect apostrophe quoting (unlike `parseText`). ### Design Observations

#### Concerns
* **Pluralization rigidity (in-scope):** Validating ICU `plural` constructs against English restricts translators to English's structural paradigms. This forces translation pipelines to emit bad or ungrammatical formats for languages that differ widely. Relying on placeholder parity (which you already do correctly) and valid parsing without enforcing branch symmetry creates a much more robust mechanism.

#### Strengths
* **Lenient Quote Handling:** Mirroring the lenient apostrophe logic from `intl-messageformat` ensures the gate evaluates exactly what the runtime formats, eliminating false-positive errors on tricky quoting rules. 
* **Self-Closing Tag Tracking:** `tagRe` accurately identifies and standardizes tags regardless of their closing format (`<tag>`, `<tag/>`, etc.), avoiding fragility around XHTML syntax styles.
