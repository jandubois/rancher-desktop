## Pinned dependencies

### Custom manifest: `pkg/rancher-desktop/assets/dependencies.yaml`

This is the repo's largest dependency surface and its strongest one. 24 dependencies — Lima, QEMU, Electron, helm, the Docker CLI, buildx, compose, the credential helpers, trivy, steve, spin, cert-manager — each pair a concrete `version` with an `assets:` list, and every asset carries its resolved `url` and a `checksum: sha256:<64 hex>`. `scripts/lib/dependencies.ts:105` rejects any checksum that is not exactly `sha256:` plus 64 hex characters, and `scripts/lib/download.ts:117` hashes the downloaded bytes and throws when they differ from the manifest. The cache-hit path re-hashes the file on disk rather than trusting its existence, and the codesign path keeps the verified bytes at `.unsigned` so the digest still means something after signing.

`mobyOpenAPISpec` goes further: `scripts/lib/dependencies.ts:220` requires its `commit` to be a full 40-character SHA, so a regenerate cannot bake a branch name into the download URL.

Three entries carry `assets: []` because another mechanism fetches them. Two of those mechanisms are sound, one is not — see Open issues.

- `golangci-lint` (2.12.2) — `scripts/lint-go.ts:180` runs `go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v<version>` with the version read from the manifest. The Go module proxy and checksum database verify the bytes. Pinned.
- `check-spelling` (0.0.26) and `spinKubePlugin` (0.4.0) — both fetch by mutable ref. See Open issues.

## Open issues

### Critical — code fetched from a moving ref and executed

- `scripts/windows-setup.ps1:49` — `Invoke-WebRequest -Uri 'https://get.scoop.sh' | Invoke-Expression` pipes an unpinned remote script straight into the PowerShell interpreter. This is `curl | bash` (wiki §3.5). Pin the URL to a release SHA, download to disk, verify a stored digest, then run it.

- `scripts/windows-setup.ps1:74` — the loop fetches four `.ps1` files from `https://raw.githubusercontent.com/rancher-sandbox/rancher-desktop/main/scripts/windows/$file` and line 80 executes `sudo-install-wsl.ps1` with administrator rights. The ref is `main`, so anyone who can push to `main` controls what runs as admin on a developer's machine. All four files already exist in this repo at `scripts/windows/`; the download serves no purpose. Copy them from the local checkout and delete the fetch.

- `scripts/windows/install-wsl.ps1:39` — downloads `wsl_update_x64.msi` and hands it to `msiexec /i` on the next line with no digest check. TLS is the only thing authenticating an MSI that installs as SYSTEM. Store the sha256 and verify with `Get-FileHash` before `msiexec` runs.

- `resources/setup-spin:41` — when the tagged template tarball fails to download, the script silently falls back to `https://github.com/spinframework/${repo}/archive/refs/heads/main.tar.gz` and installs whatever is on that third-party branch. This script ships in `resources/` and runs on end-user machines. A transient 404 on the pinned tag is enough to trigger it. Drop the fallback and fail loudly.

- `resources/setup-spin:53` — `install_plugin` builds a manifest URL under `spin-plugins/raw/refs/heads/main/manifests/` and passes it to `spin plugins install --url`, which installs the binary the manifest names. The version in the filename is pinned from `dependencies.yaml` (`spinKubePlugin`), but the manifest itself is read from a moving branch, and neither the manifest nor the binary it points to is verified. This also runs on end-user machines. Pin the manifest URL to a commit SHA.

## Retro: dependency types not explicitly covered

### R1. The `assets:`/`checksum:` manifest schema is invisible to the scanner (misclassification)

**What was seen.** `pkg/rancher-desktop/assets/dependencies.yaml` declares 24 dependencies and 108 downloadable assets, each with a `version` and a `sha256`. `inventory.json` reports `custom_manifests: []`. The single largest — and best-pinned — dependency surface in the repo produced no inventory entry at all: not pinned, not open, absent.

**Why current rules missed it.** Phase 1's custom-manifest detector keys on "YAML pairing deps with `version:` keys AND literal `checksums:` blocks." `main` uses that shape:

```yaml
lima:
  version: 2.1.2.rd1
  checksums:
    lima.macos-15.amd64.tar.gz: sha256:bd95...
```

This branch (`rddepman-asset-metadata`, commit `bf27d8700`) replaces it with a per-asset list:

```yaml
lima:
  version: 2.1.2.rd1
  assets:
    - platform: darwin
      arch: amd64
      url: https://github.com/.../lima.macos-15.amd64.tar.gz
      checksum: sha256:bd95...
```

The key is now singular `checksum:` inside an `assets:` sequence, and the detector's `checksums:`-block requirement no longer matches. The schema is strictly better — it records the resolved URL next to the digest — but the scanner reads it as an ordinary YAML file.

**Proposed change.** Extend the custom-manifest detector to accept either shape: a `checksums:` mapping block (current rule) **or** an `assets:` sequence whose items carry a `checksum:` scalar matching `^sha256:[0-9a-f]{64}$`. Both reduce to the same judgment — "entry pairs a concrete version with stored digests" — so the Phase 2 rules need no change once the entry exists. A digest-carrying key can be singular or plural; keying on the plural alone is brittle across schema revisions.

### R2. `git clone` + `exec` of the cloned script is classified "read-only consumer" (misclassification)

**What was seen.** The digest labels `scripts/spelling.sh:66` as `_(read-only consumer)_`. Line 129 of that same file is `exec "$script"`, where `$script` is `$checkout/unknown-words.sh` — the cloned tree's entry point. The clone is the opposite of read-only: its contents replace the current process.

**Why current rules missed it.** `git_clones_in_scripts[].executes_cloned_code` looks for execution of the clone path, but `spelling.sh` executes through two levels of indirection: `find_script()` builds `$script` from a local `$checkout` variable, echoes it to stdout, and the caller assigns it with `script=$(find_script)` before `exec "$script"`. Neither the clone destination nor the executed variable share a name.

**Proposed change.** When a script's clone destination flows into any variable that is later the target of `exec`, `source`, `.`, `bash`, `sh`, or a bare `"$var"` command position, set `executes_cloned_code: true`. A cheaper approximation that catches this case: if the file contains a clone *and* an `exec`/`source` of any variable, set the flag and let Phase 2 judge. False positives here cost one Read; a false negative downgrades a code-execution finding to a documentation finding.

### R3. `<tool> install --url <URL>` is not a recognized archive-install shape (new detection)

**What was seen.** `resources/setup-spin:59` — `"$spin" plugins install --yes --url "${url}"`, where `$url` points into `spin-plugins/raw/refs/heads/main/manifests/`. The tool fetches the manifest, then fetches and installs the binary the manifest names. Nothing is verified, the ref is a moving branch, and this ships to end users. The scan flagged the sibling `--tar` calls at lines 39 and 42 but not this one.

**Why current rules missed it.** The tool-mediated archive-install detector matches `--(tar|archive|file|from)\b`. `--url` is not in the set, so a plugin installer that takes a URL flag reads as an ordinary command.

**Proposed change.** Add `url` to the flag alternation: `--(tar|archive|file|from|url)\b`. The value is a remote URL either way, and the Phase 2 rule already says to default an unknown tool to open-issue. While there, note that this detector is the right place to catch the "manifest URL points to a binary" indirection — the fetched thing is not the artifact, it names the artifact — but the flag fix alone surfaces the site for judgment, which is enough.
