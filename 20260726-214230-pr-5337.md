## Executive Summary

The PR adds a tray Restart item and an `rdctl restart` subcommand. Both target crash recovery, and both fail at it: `rdctl restart` swallows the unreachable-server error, skips its own force-kill, and exits 0 without restarting anything, while the tray path waits on a graceful backend shutdown that a hung backend never completes. The CLI also registers none of `rdctl start`'s settings flags, the one change the PR's reviewer asked for.

Four reviewers ran one pass each. Each of the two deepest findings came from a single agent, and no agent found both. The PR is closed, so the findings below describe what a revival would have to fix rather than a merge blocker.

## Important Issues

I1. **`rdctl restart` reports success without restarting a hung app** — `src/go/rdctl/cmd/shutdown.go:80-83` [Gemini 3.5 Flash]

```go
		urlError := new(url.Error)
		if errors.As(err, &urlError) {
			return []byte("Rancher Desktop is currently not running (or can't be shutdown via this command)."), nil
		}
```

When the app is hung, its HTTP command server stops answering and the shutdown request fails with a `url.Error`. This branch turns that into a nil error and returns before `shutdown.FinishShutdown` at `shutdown.go:86`, so nothing reaps lima, qemu, or the app process. `restart.go:41-48` then prints the message and calls `doStartOrSetCommand`, which launches a second instance. The hung process still owns the single-instance lock, so the new one exits 201 at `background.ts:60-62` and `rdctl restart` exits 0.

So the command prints "Rancher Desktop is currently not running", does nothing, and claims success, in exactly the case the PR was written for.

Fix: on the unreachable-server path, run `shutdown.FinishShutdown` before starting. Better, give `doShutdown` a signal for "server unreachable" instead of having `restart` re-derive it from the message text.

I2. **Tray restart waits on the shutdown a hung backend never finishes** — `pkg/rancher-desktop/main/tray.ts:97-100` [Codex GPT 5.6 Sol]

```ts
      click() {
        Electron.app.relaunch();
        Electron.app.quit();
      }
```

`app.quit()` enters the `before-quit` handler, which calls `event.preventDefault()` at `background.ts:462` and reaches its final `Electron.app.quit()` only after `await k8smanager?.stop()` settles.

That stop has no deadline. `wsl.ts:1616-1641` awaits a chain of `stopService` calls and a `wsl --terminate` inside `progressTracker.action()`, none of them capped. If one hangs, the process never exits and the armed relaunch never fires, so the button does nothing and the app is now half stopped.

Fix: give the tray path the same force-kill fallback the CLI has. Bound the graceful period, then kill and relaunch, or route the tray item through the same stop-then-start sequence `rdctl` drives.

I3. **`rdctl restart` accepts none of `rdctl start`'s settings flags** — `src/go/rdctl/cmd/restart.go:52-57` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
func init() {
	rootCmd.AddCommand(restartCmd)
	restartCmd.Flags().BoolVar(&commonShutdownSettings.Verbose, "verbose", false, "be verbose")
	restartCmd.Flags().StringVarP(&applicationPath, "path", "p", "", "path to main executable")
	restartCmd.Flags().BoolVarP(&noModalDialogs, "no-modal-dialogs", "", false, "avoid displaying dialog boxes")
}
```

`start.go:52` and `set.go:43` both call `options.UpdateCommonStartAndSetCommands(cmd)`; `restart` does not. So `rdctl restart --container-engine moby` fails with `unknown flag`, and inside `doStartCommand` the generated `GetCommandLineArgsForStartCommand` tests `flags.Changed(name)`, which returns false for every unregistered flag. The relaunch therefore always passes zero settings arguments.

This is the change @ericpromislow requested in his CHANGES_REQUESTED review, and it is one line.

Fix: call `options.UpdateCommonStartAndSetCommands(restartCmd)` in `init()`.

I4. **Restart routes through the start-or-set path built for an already-running app** — `src/go/rdctl/cmd/restart.go:48` [Claude Opus 5, Gemini 3.5 Flash]

```go
		return doStartOrSetCommand(cmd)
```

`doStartOrSetCommand` exists to make `rdctl start` behave like `rdctl set` when the app is already up, which is the opposite of the state `restart` has just created. Whenever the app survives shutdown, `getListSettings()` succeeds and `doSetCommand` runs, failing with `restart command: no settings to change were given` (`set.go:52`), a message naming a command the user did not run. `start.go:72-79` then discards that error and starts a duplicate instance anyway, which exits 201 on the single-instance lock while `rdctl` reports success. Passing `--path` in the same state yields the `start`-oriented error at `start.go:69`.

Gemini 3.5 Flash reported this as an early exit with the `set` error; the fallthrough at `start.go:78-79` refutes that reading.

Fix: call `doStartCommand(cmd)` directly.

I5. **The armed relaunch outlives a cancelled quit** — `pkg/rancher-desktop/main/tray.ts:98` [Claude Opus 5]

```ts
        Electron.app.relaunch();
```

Electron arms the relaunch at call time and fires it when the process exits, whatever happens to the quit in between. A quit can be cancelled: with unsaved preferences open, the close handler at `pkg/rancher-desktop/window/preferences.ts:121-123` calls `event.preventDefault()` when the user picks Cancel.

The ordering makes it worse. RD's `before-quit` handler stops the backend first and only then re-issues the quit that reaches the window, so by the time the dialog appears the VM is already down. The app keeps running with the backend stopped and a relaunch armed, and the user's next deliberate Quit restarts it instead of exiting.

Fix: arm the relaunch from the `gone === true` branch of `before-quit` behind a flag the tray sets, once the quit is committed.

## Suggestions

S1. **Repeated clicks arm repeated relaunches** — `pkg/rancher-desktop/main/tray.ts:97-100` [Gemini 3.1 Pro, Gemini 3.5 Flash]

The menu stays live for the seconds the backend takes to stop, and Electron documents that calling `relaunch()` more than once starts one instance per call. Both Gemini reviewers predicted lock contention and port conflicts from the extra instances. The single-instance lock at `background.ts:60-62` prevents that: every duplicate exits 201, leaving exactly one survivor. What remains is wasted process spawns and a confusing exit code in the logs.

Fix: latch the click handler, which I5 already requires.

S2. **Neither half of the feature has a test** — `src/go/rdctl/cmd/restart.go` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

`src/go/rdctl/cmd/` has no `*_test.go` files, so the repo's convention for a new subcommand is integration coverage. `e2e/rdctl.e2e.spec.ts:927` and `:946` loop the bad-argument and unknown-flag matrices over `['set', 'list-settings', 'shutdown']` and omit `restart`; adding it there is nearly free and would have caught I3. A BATS case around `bats/tests/helpers/vm.bash`, which already drives `rdctl shutdown` and `rdctl start`, covers the round trip.

S3. **Flag registration is copy-pasted and binds shared package globals** — `src/go/rdctl/cmd/restart.go:54-56` [Claude Opus 5]

```go
	restartCmd.Flags().BoolVar(&commonShutdownSettings.Verbose, "verbose", false, "be verbose")
	restartCmd.Flags().StringVarP(&applicationPath, "path", "p", "", "path to main executable")
	restartCmd.Flags().BoolVarP(&noModalDialogs, "no-modal-dialogs", "", false, "avoid displaying dialog boxes")
```

The last two lines duplicate `start.go:53-54` verbatim and bind the same package-level variables, so a rename or default change has to be made twice. `restart` also mutates the shared `commonShutdownSettings` at run time (`restart.go:39`), which `shutdown.go:65-66` and `factoryReset.go:65` also bind.

Fix: extract an `addLaunchFlags(cmd *cobra.Command)` helper in `start.go` and call it from both `init()` functions.

S4. **`Long` restates `Short`, and the command's real behaviour is written down nowhere** — `src/go/rdctl/cmd/restart.go:29-31` [Claude Opus 5]

```go
	Use:   "restart",
	Short: "Restart the running Rancher Desktop application",
	Long:  `Restart the running Rancher Desktop application.`,
```

`Long` adds a period. What a user needs to know is missing: waiting is unconditional (line 39 forces it, and there is no `--wait` opt-out as `shutdown` has), the app gets force-killed if it does not exit in time, and until I3 is fixed the relaunch uses default settings. `src/go/rdctl/README.md` lists no subcommands, so `--help` is the only surface.

S5. **The relaunch target is wrong for an externally repackaged AppImage** — `pkg/rancher-desktop/main/tray.ts:98` [Claude Opus 5]

A bare `relaunch()` reuses the current `argv`, whose `argv[0]` under an AppImage points into the ephemeral `/tmp/.mount_*` squashfs that the runtime unmounts on exit. The repo keeps three live AppImage branches (`background.ts:477`, `integrations/unixIntegrationManager.ts:105`, `config/settingsImpl.ts:129`), but `electron-builder.yml` targets `zip` only for Linux and nothing under `packaging/` or the workflows builds an AppImage, so this reaches only builds repackaged outside the repo. Passing `{ execPath: process.env['APPIMAGE'] }` when that variable is set costs one line and matches what the surrounding code already assumes.

S6. **Missing trailing comma trips the repo's `comma-dangle` rule** — `pkg/rancher-desktop/main/tray.ts:100` [Claude Opus 5]

```ts

```

`.eslintrc.js:47` sets `comma-dangle: ['warn', 'always-multiline']`. The severity is `warn` and `package.json:23` runs eslint without `--max-warnings`, so CI stays green; `yarn lint:fix` corrects it.

## Design Observations

**Concerns**

1. **One feature, two implementations that fail differently** *(in-scope)* [Claude Opus 5, Codex GPT 5.6 Sol]. The tray restarts in-process through Electron's relauncher; the CLI shuts down over HTTP, reaps lima, qemu, and the app externally (`pkg/shutdown/shutdown.go:53-99`), then launches. They share no code. The tray path never reaches the force-kill fallback (I2) and the CLI path never arms a relauncher, which is why I1 and I2 are the same bug wearing two faces. Whichever surfaces survive should drive one restart sequence.

2. **`rdctl start --restart` is a smaller surface than a new subcommand** *(future)* [Claude Opus 5]. `doStartOrSetCommand` already owns the is-it-running decision, and a flag would inherit `start`'s full option set, making I3 unreachable rather than fixed. It also deletes the `restart` → `doSetCommand` path in I4. This is close to the maintainer's own counter-proposal in the thread.

3. **The tray is the contested placement** *(in-scope)* [Gemini 3.1 Pro, Gemini 3.5 Flash]. Both Gemini reviewers independently argued for the Troubleshooting page over the tray, which is the position @rak-phillip and @jandubois took in the thread. Since they share a model family, treat that as one opinion.

4. **Pre-existing, found while tracing** [Claude Opus 5]: `waitForAppToDieOrKillIt` at `pkg/shutdown/shutdown.go:102` puts `s.waitForShutdown &&` in the `for` condition, so `rdctl shutdown --wait=false` skips the wait loop entirely and goes straight to `pkill -9`. This PR does not touch it and forces the flag true, but the `--wait=false` path is a hard kill rather than a fire-and-forget request.

**Strengths**

1. **Forcing `WaitForShutdown = true`** rather than exposing a `--wait` flag (`restart.go:39`) [Claude Opus 5, Codex GPT 5.6 Sol]. A restart that does not wait would race the new instance against the single-instance lock.
2. **`app.quit()` rather than `app.exit()`** in the final tray implementation [Claude Opus 5, Codex GPT 5.6 Sol]. `exit()` would skip `before-quit` entirely, leaving the VM running and the integration symlinks in place.
3. **Reusing `doShutdown` and `commonShutdownSettings`** instead of duplicating the platform-specific shutdown logic [Codex GPT 5.6 Sol, Gemini 3.5 Flash].

## Review Process Notes

**Skill improvements**

- When a finding predicts damage from duplicate or concurrent processes (two app instances, two writers, a handler that fires twice), first check whether the program admits the second actor at all. Startup locks, PID files, and idempotency guards routinely reduce a predicted conflict to a wasted spawn, and the severity depends entirely on which of the two it is.
- When an agent reports a probe, reproduction, or test it wrote, make it state whether the probe exercised the code under review or a reconstruction of its call shape. A reconstruction is inspection, and it carries none of the extra weight an executed result earns. Check it against the tree before promoting a finding on its strength.
- Before reporting that an error path aborts a command, read to the end of the calling function. A discarded error followed by a fallback is common, and it inverts the user-visible symptom: the command succeeds silently instead of failing loudly. Say which of the two the code produces.

**Repo context updates**

- [repo] `src/go/rdctl/pkg/options/generated/` is gitignored and written by `yarn postinstall`, so `go build` and `go test` under `src/go/rdctl` fail in a fresh checkout or a review worktree until it is generated. Expect that failure and do not report it as a defect in the change under review.
- [repo] The Electron main process exits with code 201 when it cannot take the single-instance lock at startup. Any finding that predicts conflicts between concurrent Rancher Desktop instances has to account for the second one exiting immediately.
- [repo] `rdctl`'s shared `doShutdown` helper returns success without running its force-kill fallback when the app's HTTP command server is unreachable. When reviewing a command that composes it, check which error paths return before the fallback, because the caller inherits a silent no-op in exactly the hung-app case.

No stale context entries surfaced. The review SHA predates the current default branch by roughly three years, so nothing this tree shows can be used to retire an entry describing today's code.

**I4. Tray restart cannot relaunch the Linux AppImage build** — `pkg/rancher-desktop/main/tray.ts:98` *(important, regression)*

```ts
        Electron.app.relaunch();
```

#### Important Issues

##### I1. Race condition treats `restart` as a `set` command, aborting restart — `src/go/rdctl/cmd/restart.go:48`

```go
		return doStartOrSetCommand(cmd)
```

At `src/go/rdctl/cmd/restart.go:48`, the command calls `doStartOrSetCommand(cmd)` to boot up the application. In `src/go/rdctl/cmd/start.go:61`, `doStartOrSetCommand` checks if the application is running by calling `getListSettings()`. 

If Rancher Desktop is in the process of shutting down but the API port has not yet fully closed (a typical timing race window), `getListSettings()` will succeed. The command then treats the restart action as an in-place settings update, delegating to `doSetCommand(cmd)` at `src/go/rdctl/cmd/start.go:71`. Since the `restart` command does not define or carry any setting-change flags, `doSetCommand` fails with `"restart command: no settings to change were given"` at `src/go/rdctl/cmd/set.go:52`. The command exits with an error and never launches a new instance, leaving the application terminated.

Fix: Call `doStartCommand(cmd)` directly in `restartCmd` instead of `doStartOrSetCommand(cmd)`. A restart should always boot a fresh instance, never update an existing one's settings.

```diff
diff --git src/go/rdctl/cmd/restart.go src/go/rdctl/cmd/restart.go
index d1c3e1101..f3d3e34a1 100644
--- src/go/rdctl/cmd/restart.go
+++ src/go/rdctl/cmd/restart.go
@@ -45,7 +45,7 @@ var restartCmd = &cobra.Command{
 		if result != nil {
 			fmt.Println(string(result))
 		}
-		return doStartOrSetCommand(cmd)
+		return doStartCommand(cmd)
 	},
 }
```

##### I2. Duplicate tray clicks schedule multiple conflicting relaunches — `pkg/rancher-desktop/main/tray.ts:97-100`

```typescript
      click() {
        Electron.app.relaunch();
        Electron.app.quit();
      }
```

When clicking "Restart Rancher Desktop", `app.relaunch()` is scheduled immediately, and `app.quit()` is called. Since quitting is asynchronous (performing VM and Kubernetes cleanup inside `background.ts:456`), the tray menu remains responsive for several seconds. 

If a user clicks "Restart Rancher Desktop" again during this shutdown delay, `app.relaunch()` is invoked multiple times. According to Electron's documentation, if `relaunch()` is called multiple times, multiple instances of the application will launch upon exit. Having multiple instances of Rancher Desktop running concurrently results in severe WSL/Lima and port conflicts, corrupting or crashing the newly launched instances.

Fix: Guard against duplicate clicks by keeping track of whether a restart is already initiated.

### Design Observations

#### Concerns

1. **In-Tray Restart Button vs. Troubleshooting Page** `(in-scope)`
   Placing the restart button directly in the tray menu clutters the interface and can confuse average users, as noted in comments by `@rak-phillip` and `@jandubois`. Keeping the tray focused on essential options and placing the Restart facility on the Troubleshooting tab under the UI would offer a clean rescue mechanism for frozen stacks without cluttering the tray.

#### Strengths

1. **Reusing Common Shutdown Settings**
   The refactoring in `d7ae54f41` to reuse `commonShutdownSettings` from `cmd/shutdown.go` is an excellent design choice. It avoids code duplication and maintains unified structures across different shutdown and reset commands.
