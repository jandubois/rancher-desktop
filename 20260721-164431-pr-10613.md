## Executive Summary

The suite drives the updater end-to-end against a local stand-in for the
Upgrade Responder and the GitHub API. The server is faithful to what the
updater consumes: asset names, checksum format, and the block-map 404
all match. But two platforms cannot pass it. On Linux `AppImageUpdater`
refuses to download without `$APPIMAGE`; on Windows the suite runs
inside WSL while the app runs on Win32.

All four reviewers ran. Findings are ordered by severity. The two
Critical items share one root cause: the new directory auto-enrolls in
the CI matrix on platforms nobody verified.

## Critical Issues

C1. **`AppImageUpdater` throws before transferring a byte, so the download test cannot pass on Linux** — `bats/tests/updater/upgrade.bats:69` [Claude Opus 4.8]

```bash
@test 'the updater downloads the release' {
    # A bundling mistake breaks exactly here: the download throws before it
    # transfers a byte, so the update is never offered for install.
    try assert_update_log_contains 'New version v9.9.9 has been downloaded'
}
```

`update/index.ts:121` builds an `AppImageUpdater` on Linux. Its download
task throws `newError("APPIMAGE env is not defined", ...)` as its first
statement when `process.env.APPIMAGE` is unset. `forceDevUpdateConfig`
bypasses the `isUpdaterActive()` check, but it does not gate this one.
CI installs Linux from a zip into `/opt/rancher-desktop`
(`scripts/install-latest-ci.sh:216-221`, `RD_LOCATION: system`), so
`APPIMAGE` is never set. `Found version v9.9.9` still passes, so the
failure reads as a download bug rather than an unsupported platform.

Fix: skip the file where the updater cannot download.

```diff
 local_setup() {
+    if is_linux; then
+        skip 'AppImageUpdater refuses to download unless $APPIMAGE is set'
+    fi
     UPDATE_SERVER_SCRIPT="$BATS_TEST_DIRNAME/update-server.mjs"
```

C2. **On Windows the suite runs inside WSL, so it serves the wrong asset and its exports never reach the app** — `bats/tests/updater/update-server.mjs:25` [Claude Opus 4.8, Codex GPT 5.6 Sol]

```javascript
function assetName() {
  switch (process.platform) {
  case 'darwin':
    return `Rancher.Desktop-${ version }-mac.${ process.arch === 'arm64' ? 'aarch64' : 'x86_64' }.zip`;
  case 'linux':
    return `rancher-desktop-linux-${ version }.AppImage`;
```

`bats.yaml` runs the Windows suite as `wsl.exe --distribution openSUSE
--exec`, while Rancher Desktop runs on the Win32 host. Three independent
blockers follow. `process.platform` is `linux` inside WSL, so the server
offers an AppImage while `LonghornProvider.ts:424` filters for `.msi`
and throws `ERR_UPDATER_ASSET_NOT_FOUND`. The WSL image installs only
`curl` and `util-linux`, so `node` is absent. No existing bats test
needs it, since `yarn dev` is `fatal` on Windows. And the exports at
`upgrade.bats:55-57` are not in `WSLENV`, so `rdctl.exe` never sees them.

Fix: add `skip_on_windows` to `local_setup` beside C1's guard. Covering
Windows properly means keying `assetName()` off `$OS` passed from the
`.bats` file, adding the three variables to `WSLENV`, and installing
Node in the distro.

## Important Issues

I1. **`delete_pending_update` cleans the dev-mode path; packaged builds stage somewhere else** — `bats/tests/helpers/vm.bash:154` [Claude Opus 4.8, Gemini 3.1 Pro]

```bash
delete_pending_update() {
    rm -rf "$PATH_CACHE/updater-longhorn.json" "$PATH_CACHE/pending"
}
```

electron-updater stages into `<baseCache>/<updaterCacheDirName>/pending`.
`app-builder-lib`'s `appInfo.js:126` computes that name as
`sanitizedName.toLowerCase() + "-updater"`, so a packaged build stages
into `rancher-desktop-updater/pending`. That directory sits beside
`$PATH_CACHE`, not inside it. Only `dev-app-update.yml` spells the name
`rancher-desktop`, which is the one case line 154 matches. CI runs
packaged. On Windows
`installer-win32.tsx:153` yields `$PATH_APP_HOME/pending`, also missed.
A surviving cache makes `validateDownloadedPath` short-circuit, skipping
the very log line C1's test asserts.

Fix: target the sibling directory and the Windows location, without
taking `$PATH_CACHE` itself (it holds k3s downloads).

```diff
-    rm -rf "$PATH_CACHE/updater-longhorn.json" "$PATH_CACHE/pending"
+    rm -rf "$PATH_CACHE/updater-longhorn.json" "$PATH_CACHE/pending" \
+        "${PATH_CACHE}-updater" "$PATH_APP_HOME/pending"
```

I2. **Nothing confirms the application launched, so every failure surfaces as the same two-minute timeout** — `bats/tests/updater/upgrade.bats:63` [Claude Opus 4.8]

```bash
@test 'the updater offers the simulated release' {
    try assert_update_log_contains 'Found version v9.9.9'
}
```

`launch_the_application` (`vm.bash:276-297`) backgrounds `rdctl start`
and returns without checking anything. A failed launch, a missing update
config, and an unreachable server all present identically. In each case
`try` exhausts 24 × 5 s and reports that `update.log` lacks `Found
version v9.9.9`. The `Checking for update` assertion that separates them
already exists but sits at line 78, after both timeouts have burned.
This is the case the repo's own "prefer informative failures" convention
exists to prevent.

Fix: assert the updater ran before asserting what it found, matching the
budget a sibling suite uses (`preferences/surface-invalid-args.bats:18`).

```diff
 @test 'the updater offers the simulated release' {
+    try --max 36 --delay 5 assert_update_log_contains 'Checking for update'
     try assert_update_log_contains 'Found version v9.9.9'
 }
```

## Suggestions

S1. **`RD_GITHUB_API_URL` is honoured in shipped builds and moves the integrity anchor** — `pkg/rancher-desktop/main/update/LonghornProvider.ts:408` [Claude Opus 4.8]

```typescript
    const apiURL = process.env.RD_GITHUB_API_URL || 'https://api.github.com';
```

The precedent this follows, `RD_UPGRADE_RESPONDER_URL`, only selects
which GitHub tag to look up; the release JSON and checksum still come
from `api.github.com`. This hook moves the asset URL and the sha512
checksum together onto an attacker-chosen host, with no dev-only gate.
The checksum comes from `checksumAsset.browser_download_url`, which that
same server supplies, so it anchors nothing. Exploiting this requires
already controlling the process environment, which is why I rate it a
suggestion. The guard is still one line.

Fix:

```diff
-    const apiURL = process.env.RD_GITHUB_API_URL || 'https://api.github.com';
+    // Test-only override: the checksum comes from the same host, so the
+    // release must stay on api.github.com in a shipped build.
+    const apiURL = (process.env.RD_FORCE_UPDATES_ENABLED && process.env.RD_GITHUB_API_URL) || 'https://api.github.com';
```

S2. **The bundled-dependency test is subsumed by the download test** — `bats/tests/updater/upgrade.bats:79` [Claude Opus 4.8]

```bash
    assert_output --partial 'Checking for update'
    refute_output --partial 'is not a function'
```

If line 69 matched, electron-updater necessarily resolved its imports,
so the bundling regression cannot reach that log line. What remains
unique here is an unanchored `refute_output`, which fires on any
unrelated `TypeError` that ever lands in `update.log`. I would keep the
test anyway, since a guard against the class of bug that actually
shipped earns its place even when redundant, but anchor it to the
symptom the comment names.

Fix: `refute_output --partial 'o.readFile) is not a function'`, and move
the `Checking for update` assertion to where it does work (see I2).

S3. **The update server records nothing about what the updater asked for** — `bats/tests/updater/update-server.mjs:12` [Claude Opus 4.8]

The header states "Prints nothing". When C1's or C2's assertion fails in
CI, the artifacts show only that `update.log` lacks a string. They say
nothing about whether the app reached the server, which paths it
requested, or whether it fell into the 404 branch. The server is
backgrounded from a bats test, so stdout is the wrong sink. A file works.

Fix: append one line per request to a file passed as `process.argv[3]`,
and have `local_teardown_file` cat it on failure.

S4. **Teardown re-spells the PID path with nothing explaining why** — `bats/tests/updater/upgrade.bats:21` [Claude Opus 4.8]

```bash
local_teardown_file() {
    if [ -s "$BATS_FILE_TMPDIR/update-server-pid" ]; then
        kill "$(cat "$BATS_FILE_TMPDIR/update-server-pid")" || true
    fi
```

`UPDATE_SERVER_PID_FILE` is assigned in `local_setup`, which runs in the
per-test context; the file-teardown context never sees it. The literal
is correct, and the obvious "cleanup" to `$UPDATE_SERVER_PID_FILE` would
break teardown under `set -o nounset`. Nothing records that.

Fix: add a one-line comment, or hoist the path assignments into
`local_setup_file` so both contexts share them.

## Design Observations

### Concerns

**Factory reset never removes the packaged updater cache on macOS or Linux** *(future)* [Claude Opus 4.8]. This is the root cause behind I1. `delete_data_darwin.go:36-40` builds the path from `os.UserConfigDir()`, but Go returns `$HOME/Library/Application Support` there, so the code targets `~/Library/Application Support/Caches/rancher-desktop-updater`, a directory that never exists. The real one is `~/Library/Caches/rancher-desktop-updater`. `delete_data_linux.go` has no updater-cache entry at all; only the Windows path is right. `git blame` dates the darwin line to 2023, so this predates the PR. Fixing it there would let `delete_pending_update` shrink back to its `updater-longhorn.json` line, and it is the more durable fix for the leak this PR guards against.

**The suite adds six CI jobs to assert three log lines** *(future)* [Claude Opus 4.8]. `get-tests.py` expands every top-level directory under `bats/tests/` across `{containerd, moby}` and all three platforms, so the new `updater` directory costs six full Rancher Desktop installs. Nothing in the suite touches a container engine. There is no mechanism today for declaring a suite engine-independent, so this is worth raising separately rather than blocking here.

### Strengths

- Serving a 33-byte asset with a real sha512 is the right economy: it exercises `getSha512Sum`'s 128-hex-character validation, the size check, and the whole download path without moving hundreds of megabytes. [Claude Opus 4.8]
- Asserting against `update.log` keeps the test coupled to the updater's own record of what it did, which is what makes the bundling regression observable at all. [Claude Opus 4.8]
- The 404 fallback and its comment correctly anticipate the differential-download block-map probe, a request that is easy to miss. [Claude Opus 4.8, Gemini 3.1 Pro]
- Binding to an ephemeral port on `127.0.0.1` avoids fixed-port collisions between concurrent runs. [Codex GPT 5.6 Sol]
- `RD_GITHUB_API_URL` keeps the production default when unset, so the seam stays narrow. [Codex GPT 5.6 Sol]
- The server uses only Node core modules, so it needs no install step before it runs. [Gemini 3.5 Flash]

## Testing Assessment

The change is itself a test, so the question is what it covers. Ranked by risk:

1. **Installing the staged update.** The suite stops at "downloaded" by design, so `quitAndInstall` and the cached-update branch of `doInitialUpdateCheck` stay uncovered. That is the code that actually stranded users in 1.23.x.
2. **A second consecutive run on one machine.** Because of I1 the electron-updater cache survives, `validateDownloadedPath` short-circuits, and the asserted log line never reappears. A developer running the file twice locally is the first to notice.
3. **macOS behaviour after the download.** `MacUpdater` hands the 33-byte "zip" to Squirrel.Mac, which will fail. The test neither asserts nor tolerates that error, so a future change in how errors reach `update.log` could go unnoticed.
4. **The `https://api.github.com` default.** No test covers the fallback branch, so a typo in that string would surface only in production.
5. **Checksum mismatch and missing-asset paths.** The server always answers correctly, so `ERR_UPDATER_CHECKSUM_INVALID` and `ERR_UPDATER_ASSET_NOT_FOUND` stay unexercised even though this harness could produce both cheaply.

## Review Process Notes

### Skill improvements

- Before reporting that a newly added construct is unsafe, deadlocks, or hangs the test harness, grep the repository for the same construct in existing code. When established code does the same thing and passes, the burden shifts to explaining why this instance differs; absent that explanation, drop the finding. An existence proof in the repo falsifies a mechanism argument faster than any amount of reasoning about the primitive in isolation.

- When a claim about a harness rests on a runtime behaviour, reproduce it in that harness. Demonstrating the underlying primitive in a bare shell, or citing documented behaviour of the language or library, does not establish that the harness behaves the same way, because harnesses routinely install their own handling for exactly these cases. Report a claim you could not reproduce as unverified, with the attempt described.

- When a finding turns on what a third-party dependency does internally, read the installed copy in the vendor directory rather than inferring from its public API, its README, or its typical behaviour. The repository runs one pinned version, and the guard clauses that decide whether a code path works are often several layers below the call site. Defects that live in a dependency's internals are invisible to diff-reading and are systematically missed by reviewers who never open it.

- When a change adds a test file or a test directory, read how the runner discovers and schedules suites before assessing coverage. Discovery is frequently implicit (a glob over a directory tree) and multiplies across a platform and configuration matrix, so a new suite can be scheduled on platforms its author never ran. Verify the new tests can pass everywhere the matrix schedules them, or that they skip explicitly, and treat a suite that cannot pass on a scheduled platform as a defect rather than a gap.

### Repo context updates

- `[repo]` The bats suites are discovered by globbing top-level directories under `bats/tests/` (`.github/workflows/bats/get-tests.py`) and are expanded across three platforms and two container engines. A new test directory therefore adds six CI jobs, each provisioning a full Rancher Desktop install, and runs on platforms the author may never have exercised. A new suite must either pass on all three platforms or skip explicitly with `is_linux` / `skip_on_windows` from `bats/tests/helpers/os.bash`.

- `[repo]` On Windows the bats suite runs inside a WSL openSUSE distro (`BATS_COMMAND: wsl.exe --distribution openSUSE --exec`) while Rancher Desktop itself runs on the Win32 host. Three consequences for any test that starts a helper process: the distro is provisioned with only `curl` and `util-linux`, so interpreters such as `node` are absent; `process.platform` inside the helper reports `linux` even though the application under test is Windows; and variables exported in the test shell reach the Win32 process only when listed in `WSLENV`.

- `[repo]` Backgrounding a long-lived process from a bats test with a bare `&` is established practice here (`launch_the_application` in `bats/tests/helpers/vm.bash` does it for both `yarn dev` and `rdctl start`) and does not hang bats. The `3>&-` in `bats/tests/preferences/verify-paths.bats` addresses `bash -l -c` specifically, not backgrounding in general.

- `[repo]` electron-updater stages a downloaded update into `<userCache>/<updaterCacheDirName>/pending`. Packaged builds get `rancher-desktop-updater` from `app-builder-lib` (`sanitizedName.toLowerCase() + "-updater"`); dev builds get `rancher-desktop` from `dev-app-update.yml`; Windows gets `rancher-desktop` from `scripts/lib/installer-win32.tsx`. A cleanup path that assumes one spelling silently misses the others, and CI runs packaged.

- `[repo]` `rdctl reset --factory` does not remove the packaged updater cache on macOS or Linux. `delete_data_darwin.go` builds the path from Go's `os.UserConfigDir()`, which returns `~/Library/Application Support` rather than `~/Library/Caches`, and `delete_data_linux.go` has no updater-cache entry at all. Treat "factory reset cleans this up" as true only on Windows until that is fixed.

### Important Issues

**I1. `delete_pending_update` removes a directory no packaged install uses, and its comment's rationale does not hold** — `bats/tests/helpers/vm.bash:149-155` *(important, regression)*

```bash
# An update that finished downloading is staged, and the next launch installs it.
# Factory reset deletes the directory a packaged application stages into, but a
# dev build stages inside the Rancher Desktop cache, which factory reset keeps.
# A leak would install itself in whichever test runs next.
delete_pending_update() {
    rm -rf "$PATH_CACHE/updater-longhorn.json" "$PATH_CACHE/pending"
}
```

electron-updater stages into `<baseCache>/<updaterCacheDirName>/pending`. The change is itself a test, so the question is what the new test does and does not cover. Untested scenarios, highest risk first:

### Follow-up raised during execution

Verification surfaced three items beyond the review's findings; all were decided and applied.

1. **The cache carried a redirected release across the gate.** `checkForUpdates` returned a cached `updater-longhorn.json` without re-consulting the environment, so a release fetched from a test server stayed installable on a later flag-free launch, when the install suppressions are off. The cache now records the servers an entry came from, and every reader discards entries from other sources.
2. **`RD_UPGRADE_RESPONDER_URL` was still ungated.** It now requires `RD_FORCE_UPDATES_ENABLED` like its sibling, and forms part of the cache key. This changes pre-existing behaviour: a setup that sets the responder override alone will find it stops taking effect.
3. **A stale comment in `bats/tests/containers/factory-reset.bats`** named the macOS staged-update directory as `~/Library/Application Support/Caches/rancher-desktop-updater`, mirroring a path bug in `delete_data_darwin.go`. Corrected to `~/Library/Caches/rancher-desktop-updater`.

`checkupgrade` was added to the spelling expect list. It exists on main only inside full URLs, which `patterns.txt` matches; this PR introduces it as a bare path, which check-spelling would have failed in CI. No review agent caught it.

The rdctl bug behind item 3 is untouched and still open: `delete_data_darwin.go` builds the updater cache path from Go's `os.UserConfigDir()`, which returns `~/Library/Application Support` rather than `~/Library/Caches`, and `delete_data_linux.go` has no updater-cache entry at all.
