## Executive Summary

The PR moves the Windows certificate path from the subprocess `exit` event to `close`, serializes emissions through one promise chain, and skips the empty tail; a new regression test covers the `data`/`exit`/`data`/`close` sequence. The core fix is correct for production, and the test passes (verified, 4.7 s). The one substantive gap: the test omits the slow-consumer path that originally hung, leaving a latent, pre-existing `AsyncCallbackIterator.end()` race uncovered.

All three reviewers converged on that end-of-stream race. The orchestrator reproduced it directly (a synchronous consumer terminates; a consumer that awaits per certificate hangs) and confirmed against the merge-base that the race pre-dates this PR and that every current production consumer is synchronous — so it is latent, not active. One reviewer rated it critical and another labeled it a regression; both are reconciled below. The remaining findings are pre-existing robustness gaps and unaddressed review-comment requests, all at suggestion severity.

## Important Issues

I1. **Slow-consumer path that originally hung is untested; the underlying iterator end-race is latent and unfixed** — `pkg/rancher-desktop/main/networking/__tests__/win-ca.spec.ts:42-67` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]

```ts
emissions = emissions.then(async() => {
  if (buffer) {
    await iterator.emit(buffer);
  }
  iterator.end();
}, async(ex) => { await iterator.error(ex); });
```

`iterator.end()` (`utils/iterator.ts:88-90`) resolves `doneSentinel` without awaiting `#pending`. When the consumer lags the producer — any `await` in the `for await` body — `emit()` resolves `#next` with the last cert before the consumer pulls it; `next()` then installs a fresh `#next`, and `end()` resolves the already-settled promise, dropping the sentinel. Iteration hangs. I reproduced this: a synchronous consumer terminates with all certs, a consumer awaiting per cert hangs after the last one. The race pre-dates this PR (the old `exit` handler used the same `emit(buffer)`→`end()` shape) and stays latent only because every production consumer (`main/networking/index.ts:26,70,93`) pushes synchronously. The new test asserts the fix using a synchronous consumer, so the scenario that caused the original timeout stays uncovered.

Fix: add a regression case whose loop body awaits once per cert and assert it still terminates; remove the root cause by making `end()` await `#pending` like `emit()`.

```ts
// utils/iterator.ts
async end() {
  await this.#pending;
  this.#resolve(doneSentinel);
}
```

## Suggestions

S1. **Single-microtask-tick listener attachment is fragile** — `pkg/rancher-desktop/main/networking/__tests__/win-ca.spec.ts:58-65` [Claude Opus 4.8, Codex GPT 5.5]

```ts
// one microtask tick lets it resume and attach them.
await Promise.resolve();
proc.stdout.emit('data', cert1);
```

The test attaches listeners by awaiting exactly one microtask before emitting. This works only because `logMock.fdStream` is `Promise.resolve(2)`, already settled, so the generator resumes past `await Logging['networking-ca'].fdStream` (`win-ca.ts:37`) in one tick. Add an `await` before listener registration and the four `emit()`s fire into the void — half of the original timeout. The test passes today; the coupling is the risk.

Fix: gate emission on `spawnMock` having been called — resolve a promise from inside `spawnMock` and await it before emitting.

S2. **Add a comment marking the exit-before-close ordering under test** — `win-ca.spec.ts:62-65` [Claude Opus 4.8]

The `proc.emit('exit', …)` at line 63 is intentionally a no-op: `win-ca.ts:78` listens only on `close`. Without a comment, a future edit could reorder or drop the `exit`/`data`/`close` sequence and silently stop testing the regression. @mook-as requested this comment (discussion_r3337617404); it is unaddressed.

Fix: add `// exit fires before close, with a cert chunk arriving in between; we must wait for close.`

S3. **Use the repo's `mockModules` helper** — `win-ca.spec.ts:20-37` [Claude Opus 4.8]

The repo provides `pkg/rancher-desktop/utils/testUtils/mockModules.ts`, which wraps `jest.unstable_mockModule` with typing and returns handles for `mockReturnValue`. The hand-rolled mocks duplicate that machinery. @mook-as pointed to the helper (discussion_r3337591885). Stylistic; the current form works and reads clearly.

Fix: adopt `mockModules({ '@pkg/utils/childProcess': { spawn: jest.fn() }, … })` and drive `spawn` through the returned handle.

S4. **No `error` handler on the spawned process** — `pkg/rancher-desktop/main/networking/win-ca.ts:36-39` [Gemini 3.1 Pro]

```ts
const proc = childProcess.spawn(executable('wsl-helper'), ['certificates'], {
  stdio:       ['ignore', 'pipe', await Logging['networking-ca'].fdStream],
  windowsHide: true,
});
```

If `wsl-helper` cannot be spawned (missing binary, AV block), `ChildProcess` emits `error` with no listener, which throws and crashes the main process. Pre-existing — the old code had no handler either — and rare for a bundled binary, but the fix is one line and matches this PR's hardening of the same path.

Fix: `proc.on('error', queueError);`

S5. **Double-error path can leak an unhandled rejection** — `win-ca.ts:51-56` [Gemini 3.1 Pro, Claude Opus 4.8]

`queueError` chains `iterator.error(reason)` onto `emissions` with no terminal handler. `iterator.error()` throws once `#done` is set (`utils/iterator.ts:73-74`). A `data`-handler parse error followed by a clean `close(0)` runs the success branch, `emit(buffer)` throws on the done iterator, and nothing catches the rejection. The `data` handler does only string work, so the catch is near-unreachable; the defect is pre-existing.

Fix: add a terminal `.catch()` on the `emissions` chain in the `close` handler.

S6. **Early loop-break leaves the subprocess running** — `win-ca.ts:93-95` [Claude Opus 4.8]

`AsyncCallbackIterator` implements no `return()`, so a consumer that breaks the `for await` early (`main/networking/index.ts:70-76` returns on the first matching cert) abandons `proc` and its listeners without stopping it. Pre-existing; `wsl-helper` dumps a finite list and exits on its own. This is the backpressure concern @mook-as raised (discussion_r3337577214), still unanswered in code or reply.

Fix: add a comment at the `yield * iterator` site noting that an early break does not cancel the subprocess.

## Design Observations

**Concerns**

- **`AsyncCallbackIterator.end()` is not backpressure-aware** (future) [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro] — the root cause behind I1. `end()` resolves `doneSentinel` without awaiting `#pending`, so any caller whose consumer lags the producer loses the end signal and hangs. This PR routes win-ca around the defect for synchronous consumers rather than removing it. Every other `Latch()`/iterator caller (`protocols.ts`, `k3sHelper.ts`, `credentials.ts`, `windowsIntegrationManager.ts`) shares the exposure. A follow-up that makes `end()` await `#pending` would close the class.
- **Per-certificate promise chaining** (in-scope) [Gemini 3.1 Pro] — `emissions = emissions.then(...)` allocates a promise and a closure per chunk. Acceptable for the small, finite certificate list; an explicit async queue would be sturdier but is not warranted at this scale.

**Strengths**

- Switching from `exit` to `close` is the right primitive (in-scope) [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro] — `close` fires only after stdout drains, so the last chunk can no longer arrive after termination is signaled.
- Serializing emits through one ordered chain (in-scope) [Claude Opus 4.8, Codex GPT 5.5] — guarantees certificate ordering across interleaved `data`/`close` events.
- The `if (cert)` and `if (buffer)` guards (in-scope) [Claude Opus 4.8, Gemini 3.1 Pro] — suppress the empty tail without special-casing the close path.

## Review Process Notes

**Skill improvements**

- When a finding claims that an async iterator, generator, or promise chain hangs, deadlocks, or drops a completion or termination signal in a single-threaded async runtime (the JavaScript/TypeScript event loop, Python asyncio), settle it by writing and running a minimal faithful reproduction: translate the primitive and its caller into a standalone script and execute both the working consumer shape and the alleged-failing one. Hand-tracing microtask and promise-resolution order is unreliable and yields confident errors in both directions, and several agents can share the same wrong conclusion — so agreement among them is not verification. Record the reproduction's result in the finding.

**Repo context updates**

- [repo] `AsyncCallbackIterator.end()` (`pkg/rancher-desktop/utils/iterator.ts`) is not backpressure-aware: it resolves the done sentinel without awaiting `#pending`, so it drops the sentinel and hangs when a consumer awaits between iterations. Every current production consumer of `getSystemCertificates`/`getWinCertificates` pushes synchronously, so the bug is latent. When reviewing `iterator.ts`, a new `AsyncCallbackIterator` consumer, or any `for await` over one, check whether the loop body awaits per item — if it does, the stream can hang at end-of-stream.

### Design Observations

**Concerns**

- **The serialized-emission queue compensates for an iterator that cannot signal end-of-stream under backpressure** (future). The root cause of the original test hang lives in `utils/iterator.ts`: `end()` (lines 88-90) blindly calls `#resolve(doneSentinel)`, but if the previous `emit` already resolved `#next` with a value not yet pulled by `next()`, the sentinel resolution is discarded and the stream never ends. `win-ca.ts` works around this by chaining `emit`/`end` so `end()` only runs after the prior `emit`'s `#pending` latch has cycled — but every other `Latch()` caller (`protocols.ts`, `k3sHelper.ts`, `credentials.ts`, `windowsIntegrationManager.ts`) that emits faster than it consumes is exposed to the same lost-sentinel hang. A more robust fix would make `end()` enqueue the sentinel through the same `#pending` backpressure path as `emit()` (e.g., `await this.#pending` before resolving), eliminating the class of bug rather than routing one caller around it. Out of scope for this PR, but worth a follow-up issue.

- **Double-error path can produce an unhandled promise rejection** (future). `queueError` (`win-ca.ts:51-56`) chains `iterator.error(reason)` onto `emissions` with no terminal rejection handler. `iterator.error()` throws "Emitting result when end() has been called" if `#done` is already set (`utils/iterator.ts:73-74`). Two error conditions in sequence — a `data` parse error followed by a non-zero `close`, for instance — make the second `error()` reject, and nothing catches it. I reproduced this: it surfaces as `UnhandledPromiseRejection`. The old code had the same defect (the `data` listener's `await iterator.error(ex)` and the `exit` handler's unawaited `iterator.error(...)` both leak on a second error), so this is not a regression. Worth a `.catch(() => {})` on the terminal `emissions` chain if the iterator's double-settle contract is kept.

**Strengths**

- Decoupling the `data` listener from backpressure by making it synchronous and routing all emits through one ordered `emissions` chain is a clean way to guarantee cert ordering across interleaved `data`/`close` events.
- The `if (cert)` (line 45) and `if (buffer)` (line 83) guards correctly suppress the empty tail without special-casing the close path.
- Switching from `exit` to `close` is the right primitive: `close` fires only after stdout has drained, so the last chunk can no longer land after termination is signaled.

### Executive Summary

This PR fixes a bug where `win-ca` missed late-arriving certificate chunks by switching to the stream's `close` event and queuing emissions to maintain order. However, the fix exposes a critical race condition in `AsyncCallbackIterator` when consumers are slower than the stream, and a pre-existing missing error handler on the spawned child process remains a crash risk. 

### Findings

#### Critical Issues

C1. **Missing error handler on child process causes crash** — `pkg/rancher-desktop/main/networking/win-ca.ts:36-39`

```typescript
  const proc = childProcess.spawn(executable('wsl-helper'), ['certificates'], {
    stdio:       ['ignore', 'pipe', await Logging['networking-ca'].fdStream],
    windowsHide: true,
  });
```

Node.js `ChildProcess` emits an `'error'` event if the executable cannot be spawned (e.g., the binary is missing, or antivirus blocks execution). Because there is no `.on('error', ...)` handler attached to `proc`, this failure surfaces as an unhandled `'error'` event and crashes the entire Rancher Desktop main process.

Fix: Attach an error handler that delegates to `queueError`:
```diff
   const iterator = new AsyncCallbackIterator<string>();
   let emissions = Promise.resolve();
 
+  proc.on('error', queueError);
```
(critical, gap)

C2. **Iterator hangs on slow consumers due to race condition** — `pkg/rancher-desktop/main/networking/win-ca.ts:80`

```typescript
        if (buffer) {
          await iterator.emit(buffer);
        }
        iterator.end();
```

The PR sequences `iterator.end()` immediately after the final `await iterator.emit(buffer)`. However, `AsyncCallbackIterator.end()` resolves the *current* pending promise. If the consumer is asynchronous (e.g., has an `await` in its loop), it has not yet called `next()` to pull the final item and create the subsequent promise. Consequently, `iterator.end()` calls `this.#resolve(doneSentinel)` on the *already-resolved* promise, and the sentinel is lost. The consumer then calls `next()` and hangs forever waiting for an end signal that already fired. The PR author encountered this hang during testing but worked around it by removing `setTimeout` from the test loop instead of fixing the root cause.

Fix: Modify `AsyncCallbackIterator.end()` to wait for the consumer to pull the final item before resolving the sentinel. In `pkg/rancher-desktop/utils/iterator.ts`:
```diff
-  end() {
+  async end() {
+    await this.#pending;
     this.#resolve(doneSentinel);
   }
```
(critical, gap)

#### Important Issues

I1. **Error chain masking leads to unhandled promise rejections** — `pkg/rancher-desktop/main/networking/win-ca.ts:48-51`

```typescript
  function queueError(reason: any) {
    emissions = emissions.then(
      () => iterator.error(reason),
      () => iterator.error(reason),
    );
  }
```

If `queueError` is triggered, its `.then` handles any previous rejection in the chain and fulfills the new `emissions` promise. When `close` fires, its `.then` sees a *fulfilled* chain and executes the success branch (`await iterator.emit(buffer); iterator.end();`). However, `iterator.error` has already set `#done = true` internally, so `iterator.emit()` throws `"Emitting result when end() has been called"`. Because the `close` handler does not attach a `.catch()` to the end of the chain, this thrown error results in an unhandled promise rejection, crashing the Node process.

Fix: Add a terminal `.catch()` to safely consume framework errors after the stream is closed:
```diff
       emissions = emissions.then(async() => {
         if (buffer) {
           await iterator.emit(buffer);
         }
         iterator.end();
       }, async(ex) => {
         await iterator.error(ex);
-      });
+      }).catch(e => Logging['networking-ca'].error('win-ca iterator error', e));
```
(important, gap)

### Design Observations

**Concerns**
- **Dynamic Promise Chaining (in-scope):** The `emissions = emissions.then(...)` pattern creates a dynamic promise chain to provide a sequential queue. While functional for a small number of certificates, it allocates a new promise and closure per chunk. A simpler, more robust design would use an explicit asynchronous queue or channel (where producers push synchronously and consumers pull asynchronously) rather than dynamically chaining promises on an `EventEmitter`.
