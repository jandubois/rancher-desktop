Executive Summary ¶

The suite drives the updater end-to-end against a local stand-in for the Upgrade Responder and the GitHub API. The server is faithful to what the updater consumes: asset names, checksum format, and the block-map 404 all match. But two platforms cannot pass it. On Linux AppImageUpdater refuses to download without $APPIMAGE; on Windows the suite runs inside WSL while the app runs on Win32.

All four reviewers ran. Findings are ordered by severity. The two Critical items share one root cause: the new directory auto-enrolls in the CI matrix on platforms nobody verified.

Design Observations ¶

Concerns ¶

Factory reset never removes the packaged updater cache on macOS or Linux (future) Claude Opus 4.8. This is the root cause behind I1. delete_data_darwin.go:36-40 builds the path from os.UserConfigDir(), but Go returns $HOME/Library/Application Support there, so the code targets ~/Library/Application Support/Caches/rancher-desktop-updater, a directory that never exists. The real one is ~/Library/Caches/rancher-desktop-updater. delete_data_linux.go has no updater-cache entry at all; only the Windows path is right. git blame dates the darwin line to 2023, so this predates the PR. Fixing it there would let delete_pending_update shrink back to its updater-longhorn.json line, and it is the more durable fix for the leak this PR guards against.

The suite adds six CI jobs to assert three log lines (future) Claude Opus 4.8. get-tests.py expands every top-level directory under bats/tests/ across {containerd, moby} and all three platforms, so the new updater directory costs six full Rancher Desktop installs. Nothing in the suite touches a container engine. There is no mechanism today for declaring a suite engine-independent, so this is worth raising separately rather than blocking here.

Strengths ¶

  • Serving a 33-byte asset with a real sha512 is the right economy: it exercises getSha512Sum's 128-hex-character validation, the size check, and the whole download path without moving hundreds of megabytes. Claude Opus 4.8
  • Asserting against update.log keeps the test coupled to the updater's own record of what it did, which is what makes the bundling regression observable at all. Claude Opus 4.8
  • The 404 fallback and its comment correctly anticipate the differential-download block-map probe, a request that is easy to miss. Claude Opus 4.8 Gemini 3.1 Pro
  • Binding to an ephemeral port on 127.0.0.1 avoids fixed-port collisions between concurrent runs. Codex GPT 5.6 Sol
  • RD_GITHUB_API_URL keeps the production default when unset, so the seam stays narrow. Codex GPT 5.6 Sol
  • The server uses only Node core modules, so it needs no install step before it runs. Gemini 3.5 Flash

Testing Assessment ¶

The change is itself a test, so the question is what it covers. Ranked by risk:

  1. Installing the staged update. The suite stops at "downloaded" by design, so quitAndInstall and the cached-update branch of doInitialUpdateCheck stay uncovered. That is the code that actually stranded users in 1.23.x.
  2. A second consecutive run on one machine. Because of I1 the electron-updater cache survives, validateDownloadedPath short-circuits, and the asserted log line never reappears. A developer running the file twice locally is the first to notice.
  3. macOS behaviour after the download. MacUpdater hands the 33-byte "zip" to Squirrel.Mac, which will fail. The test neither asserts nor tolerates that error, so a future change in how errors reach update.log could go unnoticed.
  4. The https://api.github.com default. No test covers the fallback branch, so a typo in that string would surface only in production.
  5. Checksum mismatch and missing-asset paths. The server always answers correctly, so ERR_UPDATER_CHECKSUM_INVALID and ERR_UPDATER_ASSET_NOT_FOUND stay unexercised even though this harness could produce both cheaply.

Documentation Assessment ¶

docs/development/env.md documents RD_GITHUB_API_URL accurately, in the file's existing order, and ties it to RD_UPGRADE_RESPONDER_URL. One gap: the entry does not say the variable is honoured in packaged builds, which is the fact S1 turns on. If S1 is declined, say so in the doc.

Review Process Notes ¶

Skill improvements ¶

  • Before reporting that a newly added construct is unsafe, deadlocks, or hangs the test harness, grep the repository for the same construct in existing code. When established code does the same thing and passes, the burden shifts to explaining why this instance differs; absent that explanation, drop the finding. An existence proof in the repo falsifies a mechanism argument faster than any amount of reasoning about the primitive in isolation.
  • When a claim about a harness rests on a runtime behaviour, reproduce it in that harness. Demonstrating the underlying primitive in a bare shell, or citing documented behaviour of the language or library, does not establish that the harness behaves the same way, because harnesses routinely install their own handling for exactly these cases. Report a claim you could not reproduce as unverified, with the attempt described.
  • When a finding turns on what a third-party dependency does internally, read the installed copy in the vendor directory rather than inferring from its public API, its README, or its typical behaviour. The repository runs one pinned version, and the guard clauses that decide whether a code path works are often several layers below the call site. Defects that live in a dependency's internals are invisible to diff-reading and are systematically missed by reviewers who never open it.
  • When a change adds a test file or a test directory, read how the runner discovers and schedules suites before assessing coverage. Discovery is frequently implicit (a glob over a directory tree) and multiplies across a platform and configuration matrix, so a new suite can be scheduled on platforms its author never ran. Verify the new tests can pass everywhere the matrix schedules them, or that they skip explicitly, and treat a suite that cannot pass on a scheduled platform as a defect rather than a gap.

Repo context updates ¶

  • [repo] The bats suites are discovered by globbing top-level directories under bats/tests/ (.github/workflows/bats/get-tests.py) and are expanded across three platforms and two container engines. A new test directory therefore adds six CI jobs, each provisioning a full Rancher Desktop install, and runs on platforms the author may never have exercised. A new suite must either pass on all three platforms or skip explicitly with is_linux / skip_on_windows from bats/tests/helpers/os.bash.
  • [repo] On Windows the bats suite runs inside a WSL openSUSE distro (BATS_COMMAND: wsl.exe --distribution openSUSE --exec) while Rancher Desktop itself runs on the Win32 host. Three consequences for any test that starts a helper process: the distro is provisioned with only curl and util-linux, so interpreters such as node are absent; process.platform inside the helper reports linux even though the application under test is Windows; and variables exported in the test shell reach the Win32 process only when listed in WSLENV.
  • [repo] Backgrounding a long-lived process from a bats test with a bare & is established practice here (launch_the_application in bats/tests/helpers/vm.bash does it for both yarn dev and rdctl start) and does not hang bats. The 3>&- in bats/tests/preferences/verify-paths.bats addresses bash -l -c specifically, not backgrounding in general.
  • [repo] electron-updater stages a downloaded update into <userCache>/<updaterCacheDirName>/pending. Packaged builds get rancher-desktop-updater from app-builder-lib (sanitizedName.toLowerCase() + "-updater"); dev builds get rancher-desktop from dev-app-update.yml; Windows gets rancher-desktop from scripts/lib/installer-win32.tsx. A cleanup path that assumes one spelling silently misses the others, and CI runs packaged.
  • [repo] rdctl reset --factory does not remove the packaged updater cache on macOS or Linux. delete_data_darwin.go builds the path from Go's os.UserConfigDir(), which returns ~/Library/Application Support rather than ~/Library/Caches, and delete_data_linux.go has no updater-cache entry at all. Treat "factory reset cleans this up" as true only on Windows until that is fixed.
