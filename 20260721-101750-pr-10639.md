## Important Issues

I1. **A stale `@reason` survives a value overwrite and satisfies the identity check** — `src/go/i18n-report/report_validate.go:135` [Claude Opus 4.8]

```go
		if e.override || commentHasReason(e.comment) {
			continue
		}
```

`@reason` predates this check. The README defines it as "Why a particular translation was chosen", and 526 keys across the eight locales carry one on a value that is not identical to its source. All are exempt from day one.

The exemption is reachable. `merge` hands the input comment to `nodeSetLeaf`, which keeps the existing head comment when the input carries none and strips only `@override` (`yaml.go:356-361`), then refreshes `@source` to the new English. Merging the English verbatim over a translated key left `volume.title: Volumes` with a stale `@reason` about the German it replaced, and `validate` passed.

`yaml.go:359` already states this for the sibling marker, where a retained `@override` "would falsely claim it is still hand-tuned". A retained `@reason` claims deliberateness just as falsely.

Fix: strip `@reason` alongside `@override` when the value changes. A narrower variant strips only when the new value equals the English source.

```diff
 				} else if valNode.Value != value {
-					// The value is machine-replaced; a retained @override
-					// marker would falsely claim it is still hand-tuned.
-					current.Content[keyIdx].HeadComment = stripOverrideMarker(current.Content[keyIdx].HeadComment)
+					// The value is machine-replaced; a retained @override or
+					// @reason would falsely claim the new text is deliberate.
+					current.Content[keyIdx].HeadComment = stripMarkers(current.Content[keyIdx].HeadComment)
 				}
```

## Design Observations

**Concerns**

- **`check` reports a count, not the failing keys** *(future)* [Claude Opus 4.8]. The gate surfaces the new category as `validate passes: FAIL  N validation errors`, so a CI consumer must re-run `validate --locale=X` to learn which keys failed. That indirection is pre-existing, but `identical` is the first check likely to fire during routine translation work rather than on structural breakage, so it will be hit far more often.
- **README step 6 does not verify step 3** *(in-scope)* [Claude Opus 4.8]. Step 3 asks for a `locale.{code}` display name in every other locale file. Step 6's `check --locale=all` runs `reportCheckRegistration`, which asserts the key exists in `en-us.yaml` only (`report_check.go:211-215`); missing sibling display names surface only under `--strict`. A parenthetical would stop an author reading step 6 as confirmation of step 3.

**Strengths**

- The identity check layers cleanly against the existing categories *(in-scope)* [Claude Opus 4.8]. `!inEn` defers to the stale check, `!hasSource` defers to the `catSource` check directly above it, and the empty-value exemption is narrow, so every key lands in exactly one category with no double-reporting.
- Deferring the identity check on drifted keys makes developers resolve source drift before being asked for a `@reason` *(in-scope)* [Gemini 3.5 Flash, Claude Opus 4.8].
- The test uses `secret.types."kubernetes.io/basic-auth"` *(in-scope)* [Claude Opus 4.8], the repo's canonical quoted-dotted-segment stress key and the highest-risk path for the flat-key representation.
- The `settingsValidator` fix reuses the `fqname` already computed at line 255 instead of adding a conditional, so the root and nested paths cannot diverge again *(in-scope)* [Claude Opus 4.8, Gemini 3.5 Flash].
- `plural` centralizes count wording and leaves JSON output untouched, bounding the compatibility surface *(in-scope)* [Codex GPT 5.6 Sol]. Its docstring states plainly that it handles regular `+s` plurals only, which should stop the next contributor reaching for it on an irregular noun.

## Review Process Notes

**Skill improvements**

- When a change adds a validation gate that exempts entries carrying a particular annotation, comment marker, or flag, check whether that marker predates the gate and already carries a different meaning. Count how many entries already carry it and are therefore exempt the moment the gate ships, then trace every write path that can preserve the marker across a value change. A marker serving two purposes exempts everything annotated for the older purpose, and the gate still reports green.
- Before reporting a test suite as failing or unavailable, run it through the project's own documented command (the `package.json` script, Makefile target, or task-runner entry) rather than invoking the test runner binary directly. Projects routinely set module, transform, or experimental-flag options inside that wrapper, so a direct invocation can surface type or syntax errors the real suite never produces. Report a failure only after the documented command reproduces it.

**Repo context updates**

- [repo] REMOVE the note that the `check` and `drift` subcommands "remain in flight on the `i18n-workflow-v2` integration tree", and REMOVE the bullet directing reviewers to validate i18n-report gate changes inside an `i18n-workflow-v2` worktree. Both subcommands and the registration surfaces they check are on the default branch, and `check --locale=all` runs clean from an ordinary branch worktree.
- [repo] UPDATE the testing-environment note on repo-wide jest `TS1378` failures to name the working invocation. The suite runs under `node --experimental-vm-modules node_modules/jest/bin/jest.js` (the `test:unit:jest` script); invoking `node_modules/.bin/jest` directly reproduces `TS1378` on top-level `await import` and a spurious `Locale` type error even when the suite is healthy.
- [repo] To exercise i18n-report against a fixture, create `<root>/pkg/rancher-desktop/assets/translations/en-us.yaml` plus the locale file, then run the built binary with `--locale=<code>` from `<root>`. The text-input parser for `merge` requires dotted keys of at least two segments, since `isValidDottedKey` rejects single-segment keys, so a single-level fixture key fails to parse with only a warning.
