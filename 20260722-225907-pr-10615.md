## Important Issues

I1. **A cancelled quit leaves `installStarted` stuck, wedging every later check** — `pkg/rancher-desktop/main/update/index.ts:83` [Gemini 3.5 Flash, Gemini 3.1 Pro, Codex GPT 5.6 Sol, Claude Opus 4.8]

```ts
  installStarted = true;
  autoUpdater.quitAndInstall();
```

`installStarted` gates every future check at `index.ts:383` and is cleared only by the updater's `error` event at `index.ts:161`. `quitAndInstall()` triggers `app.quit()`, whose `before-quit` handler (`background.ts:644-669`) tears down services and re-quits; the second quit closes windows, and a dirty Preferences window aborts it via `event.preventDefault()` (`preferences.ts:129`). No `error` fires, so the latch sticks. Every later check is skipped, and the renderer holds "Applying…" (cleared only on error, `UpdateStatus.vue:139`). Codex reproduced `appStillRunning:true` after two `before-quit` events. The harm is masked today, because that same teardown already forces a restart; it becomes a live dead-end once the zombie-app behavior is fixed.

Fix: clear `installStarted` (and the renderer's `applying`) when a quit is cancelled, and set the latch only once the quit is irrevocable.

I2. **An unrelated in-flight check error releases the latch, re-enabling a second install** — `pkg/rancher-desktop/main/update/index.ts:161` [Codex GPT 5.6 Sol]

```ts
    // Installing may be what failed, and the application is still running to
    // report it, so let the user ask again.
    installStarted = false;
```

The `error` handler clears the latch for any updater error, not only an install error. A periodic check can already be awaiting `checkForUpdates()` (`index.ts:385`) when Apply sets the latch; if that check rejects during shutdown, this handler clears `installStarted`, and the watcher re-enables Apply (`UpdateStatus.vue:139`). A second `quitAndInstall()` then becomes possible. Codex reproduced two `quitAndInstall()` calls with a focused spec. This defeats the one-installer invariant the latch was added for in Round 1, and platform updaters may duplicate work or silently reject the second call. The window is narrow: the in-flight check must error while Apply is pending.

Fix: scope the clear to install-originated errors, or track the in-flight check so its failure does not release install state.

I3. **Retrying a failed download can hide the card and its own Retry button** — `pkg/rancher-desktop/main/update/index.ts:170` [Gemini 3.5 Flash, Claude Opus 4.8]

```ts
    updateState.downloaded = !!stagedVersion && updateState.info?.version === stagedVersion;
    if (updateState.downloaded) {
```

The `error` handler restores `available` only when a staged update survives (the line 171 gate). `checking-for-update` clears `available` (`index.ts:184`); when the user clicks Retry after a download that never staged (`downloaded` is false), a check that errors before `update-available` leaves `available` false. `UpdateStatus.vue` gates the card on `available`, so the card and the Retry button inside it unmount. A scratch test confirmed `available === false` after `checking-for-update` + `error` following a download failure. The affordance the PR adds thus removes itself on a flaky network. It self-heals on the next successful check (≤10 min, via the catch arm at `index.ts:407`). This is the unstaged mirror of Round-1 I1, whose fix covered the staged case only.

Fix: let `update-available`/`update-not-available` own `available`, and drop the `available = false` in `checking-for-update`, so a first offline check stays hidden while a download-failed → retry-fails sequence keeps the prior `true`.

## Suggestions

S1. **The restored queued flag adds a writer to the un-serialized cache race** — `pkg/rancher-desktop/main/update/index.ts:176` [Gemini 3.5 Flash, Gemini 3.1 Pro, Codex GPT 5.6 Sol, Claude Opus 4.8]

```ts
      updateState.available = true;
      setHasQueuedUpdate(true);
```

`setHasQueuedUpdate` does an un-awaited, non-serialized read-modify-write on `updater-longhorn.json`, a known pre-existing race. This PR adds a write on the `error` path, which can interleave with the `setHasQueuedUpdate(false)` that `checking-for-update` starts at `index.ts:189`. The UI stays correct, but the on-disk flag can lose the race, so the next launch re-checks the staged update instead of installing it directly. The impact is low and self-corrects; it is flagged only because the change adds the call, since the standing rule treats this file's writes as pre-existing otherwise. Codex reproduced `isInstallable:false` from a controlled read-modify-write.

Fix: serialize the queued-flag writes, or clear the flag only on `update-not-available` or a confirmed newer offer rather than on every check start.

S2. **A component test pins a state the main process cannot produce** — `pkg/rancher-desktop/components/__tests__/UpdateStatus.spec.ts:150` [Codex GPT 5.6 Sol, Claude Opus 4.8]

```ts
      const wrapper = wrap({
        enabled:     true,
        updateState: { available: true } as UpdateState,
      });
```

The main process never broadcasts `available: true` without `info`. `update-available` sets both, and the error restore requires `info.version === stagedVersion`. After the `errorChecking` removal, this fixture asserts empty text for a state production cannot produce, so it adds no real coverage. The nearby `offers to retry a download that failed` test sets `available: true` after a failed retry, the same assumption I3 shows the main process does not hold, so it gives false confidence there too.

Fix: drop the impossible-state fixture; the "no updates available" test already covers the hidden card.

## Review Process Notes

### Skill improvements

- Before dropping a finding as fabricated because a cited file "does not exist," confirm the file's absence across the whole repository, not the subtree you assumed it lived in. A `grep` or `find` scoped to one directory that returns nothing is absence of evidence, not evidence the file is absent; entry points and lifecycle handlers often sit at the repo root, outside the main source tree. The "quoted snippet absent from the cited file" heuristic applies only after you have opened a file that exists and found the snippet missing, never to a file a narrow search failed to locate.
- When a finding turns on a project's main-process entry point or application-lifecycle handling, resolve the entry from the build manifest (`package.json` `main`, `Cargo.toml`, and so on) before reasoning about where handlers live. An overview doc or a directory guess can point at a relocated or dead file; the manifest is authoritative.

### Repo context updates

- [repo] The Electron main-process entry point is the repo-root `background.ts` (`package.json` `main` → `dist/app/background.js`), not `pkg/rancher-desktop/index.ts`, which is fully commented out, a Nuxt-removal relic. The app-lifecycle handlers live in `background.ts`. `before-quit` tears down services (`k8smanager.stop()`, server shutdowns, integration teardown) and sets a module `gone` flag before re-quitting; `window-all-closed` hides the dock. When a finding cites a main-process entry or a quit/lifecycle handler, look there, not under `pkg/`.
- [repo] A quit in Rancher Desktop is cancellable, so `app.quit()` and `autoUpdater.quitAndInstall()` are not guaranteed to terminate the app. The Preferences window's `close` handler (`window/preferences.ts`) calls `event.preventDefault()` when the form is dirty and the user cancels the discard dialog, which aborts the quit; `before-quit` has already torn down services by then, leaving a running-but-degraded app. Any code that latches state before or during a quit or install (for example an install-in-progress flag that gates future work) needs a recovery path for a cancelled quit, since no updater `error` fires on cancellation.

### Critical Issues

None.

### Important Issues

I1. **Cancelled quit permanently wedges the update latch** — `pkg/rancher-desktop/main/update/index.ts:77-83` (important, regression)

```typescript
  if (installStarted) {
    // The button that sends this disables itself, but it forgets that when the
    // user navigates away and back, and a second quitAndInstall() hands the
    // same update to a second installer process.
    return;
  }
  installStarted = true;
```

The new `installStarted` latch is cleared only when the updater emits an `error` event. If `autoUpdater.quitAndInstall()` initiates a quit but the quit is aborted (e.g., the user clicks "Cancel" in the Preferences window's "unsaved changes" dialog, which calls `event.preventDefault()` on the `close` event), the app does not quit and no `error` is emitted. The latch remains `true` permanently.

This wedges the feature's state machine: the UI leaves the "Restart Now" button stuck at "Applying update...", and `triggerUpdateCheck()` silently skips all future update checks. Although Rancher Desktop currently requires a force-restart when a quit is cancelled (a pre-existing zombie-app issue), this latch ensures the update mechanism remains broken even if the zombie-app behavior is fixed later.

Fix: Clear the latch if the quit is aborted. Listen for the cancellation (e.g., via a custom `quit-cancelled` event emitted by the `before-quit` or window `close` handlers that call `preventDefault()`) to reset `installStarted = false` and restore the UI.

I2. **Un-awaited write exacerbates latent race on update cache** — `pkg/rancher-desktop/main/update/index.ts:175-178` (important, regression)

```typescript
    if (updateState.downloaded) {
      // checking-for-update cleared both of these on the way in. A check that
      // failed never got as far as retracting the offer the last one made, and
      // without `available` the renderer hides the card the button lives in.
      updateState.available = true;
      setHasQueuedUpdate(true);
    }
```

The newly added call to `setHasQueuedUpdate(true)` continues a pre-existing pattern of un-awaited, non-serialized read-modify-writes to `updater-longhorn.json`. Because `setHasQueuedUpdate` asynchronously reads the file, mutates it, and writes it back, calling it without `await` allows concurrent update events to interleave their reads and writes. If an `error` event fires closely with another update state transition, it can corrupt the cache file or silently lose the queued flag.

Fix: `await` the call to `setHasQueuedUpdate(true)` (wrapping the contents of the event handler in an async IIFE if necessary), and ensure `LonghornProvider.ts` internally serializes access to the cache file (e.g., via a promise queue or mutex) so that concurrent un-awaited calls resolve safely.
