+`RD_FORCE_UPDATES_ENABLED` is also set, because the responder chooses which

I2. **Nothing tests that the cache records its provenance at all** — `pkg/rancher-desktop/main/update/LonghornProvider.ts:493` [Claude Opus 4.8]

```typescript
    const cache: LonghornCache = {
      nextUpdateTime: nextRequestTime.getTime(),
      ...sources,
      unsupportedUpdateAvailable,
```

Every new test hand-writes its cache fixture and asserts on the read side. No
test reads back a cache that `checkForUpdates` produced, so deleting
`...sources` here leaves the whole suite green. That deletion would make every
`fromCurrentSources` comparison fail against `undefined`, so the cache would
never be reused and every launch would re-query the Upgrade Responder. The
class docstring at line 370 names avoiding double-counted stats as the reason
the cache exists, so the regression is live rather than hypothetical.

Fix: add a round-trip test that calls `checkForUpdates` twice and asserts the
second call issues no fetch, plus a pair covering the `testing &&` gate on
`RD_UPGRADE_RESPONDER_URL` at line 182.

I3. **Provenance records the environment overrides, not the configuration the request actually used** — `pkg/rancher-desktop/main/update/LonghornProvider.ts:177-183` [Codex GPT 5.6 Sol]

```typescript
function updateSources(): Pick<LonghornCache, 'apiURL' | 'upgradeServer'> {
  const testing = process.env.RD_FORCE_UPDATES_ENABLED;

  return {
    apiURL:        (testing && process.env.RD_GITHUB_API_URL) || 'https://api.github.com',
    upgradeServer: (testing && process.env.RD_UPGRADE_RESPONDER_URL) || '',
  };
}
```

The fetch uses `this.configuration.upgradeServer` (line 437) and `owner`/`repo`
(line 450), but the recorded identity ignores all three. A build whose
`app-update.yml` names a fork therefore writes the same provenance an official
build computes, so the official build accepts its cached release. That is the
workflow `scripts/populate-update-server.ts:271-277` documents. This is a gap
rather than a regression: before this PR the cache carried no provenance and
was accepted unconditionally.

Fix: build the identity from the resolved configuration and thread it from
`getUpdater()` into `hasQueuedUpdate()`, so both paths compare what the run
actually used.

## Design Observations

### Concerns

**The gating decision lives in two files and stays consistent by convention** *(future)* [Claude Opus 4.8, Codex GPT 5.6 Sol]. `getUpdater` decides whether the responder override applies (`index.ts:109`) and stores the result in `options.upgradeServer`; `updateSources` (`LonghornProvider.ts:177-184`) re-derives the same decision from the environment so it can record provenance. They agree today, and nothing enforces it. Change the gate in one file and the cache records a responder the run never queried, which makes every later `fromCurrentSources` check wrong in a way no test catches. The obstacle to a single source of truth is that `hasQueuedUpdate` is a module-level function with no provider instance. Threading the resolved sources from `getUpdater` into both paths would make them agree by construction and would also close I3.

**A rejected cache leaves its payload on disk** *(future)* [Claude Opus 4.8, Codex GPT 5.6 Sol]. When `hasQueuedUpdate` discards a foreign entry (line 204), the staged archive under `pending/` stays. Nothing can install it, since `doInitialUpdateCheck` (`index.ts:284`) is the only install path and `autoInstallOnAppQuit` is false. It is normally reclaimed when the next real download finds a sha512 mismatch, but if the real server answers `update-not-available`, nothing removes it. `delete_pending_update` covers test machines; a developer who ran the overrides by hand keeps the stub indefinitely.

### Strengths

- Recording provenance inside the cache entry, rather than keying the file name on the sources, means a stale entry gets actively rejected and rewritten instead of silently orphaned. [Claude Opus 4.8]
- Putting the check in `fromCurrentSources` and calling it from both readers makes the "every reader must agree" invariant structural rather than a rule two call sites must remember. [Claude Opus 4.8]
- Gating both environment overrides behind the existing test flag is a sound safety boundary, and the cache key follows from it. [Codex GPT 5.6 Sol]
- The request trace and the explicit launch check materially improve failure diagnosis, which is what Round 1 asked for. [Codex GPT 5.6 Sol]
- Serving a 33-byte asset and asserting on the updater's own log lines covers a bundling failure no unit test can reach. [Claude Opus 4.8, Gemini 3.5 Flash]
- The mock server binds an ephemeral port on `127.0.0.1` and uses only Node core modules, so it needs no install step and cannot collide. [Gemini 3.5 Flash, Gemini 3.1 Pro]

## Review Process Notes

### Skill improvements

- When a change introduces an invariant that later code depends on (a
  provenance field, a version stamp, a capability flag written at one site and
  read at several), identify the single line whose removal would break it and
  ask whether any test would fail. Test suites that build their fixtures by
  hand exercise only the read side of such an invariant, so the write side can
  be deleted silently. Report an untested write path as a finding in its own
  right, at the severity the broken invariant would carry, rather than as a
  general coverage note.

- Before proposing that a change accept older records by defaulting a newly
  added field, establish what those older records could contain. When the new
  field records provenance, trust, or origin, the old records predate the rule
  that field enforces and may be exactly the ones it exists to reject, so a
  compatibility default reintroduces the hole the change closes. Check whether
  rejecting the old record is self-healing before treating the rejection as a
  defect: a value the code refetches and rewrites costs one extra round trip,
  not a broken install.

### Repo context updates

- `[repo]` The bats matrix pins macOS to `macos-15-intel`
  (`.github/workflows/bats/get-tests.py`), so any code path selected by host
  architecture runs only its x86_64 branch in CI. An arm64 branch is exercised
  only by developers running the suite locally on Apple Silicon. Treat
  arch-conditional logic in test fixtures as CI-unverified.

- `[repo]` `clearLoggingDirectory()` in `pkg/rancher-desktop/utils/logging.ts`
  deletes every `*.log` file in `paths.logs` whose basename is not a registered
  logging topic, and `background.ts` calls it at module load on every app
  start. A test that writes a diagnostic file into `$PATH_LOGS` with a `.log`
  extension will have it deleted by the next application launch. Use another
  extension; `capture_logs` collects the whole tree regardless.

- `[repo]` bats suites normally start the app through `start_container_engine`
  (`bats/tests/helpers/vm.bash`), which passes `--application.debug`,
  `--application.updater.enabled=false`, and `--kubernetes.enabled=false`.
  Calling `launch_the_application` directly with no arguments after a factory
  reset starts the app with default settings, which means a full Kubernetes
  cluster. A suite that does not need Kubernetes should disable it explicitly.

**Concerns**

- **The gating decision lives in two files and is kept consistent by convention** *(future)*. `getUpdater` decides whether the responder override applies (`index.ts:109`) and stores the result in `options.upgradeServer`; `updateSources` (`LonghornProvider.ts:177-184`) independently re-derives the same decision from the environment so that provenance can be recorded. If an existing installation has a previously downloaded update waiting to install, its legacy `updater-longhorn.json` cache lacks the `apiURL` and `upgradeServer` keys (they are `undefined`). During a standard production run, `sources.apiURL` is `'https://api.github.com'` and `sources.upgradeServer` is `''`. Comparing `undefined` to `'https://api.github.com'` evaluates to `false`. This causes `hasQueuedUpdate()` (line 204) to ignore the legacy cache and return `false`, preventing the staged update from being installed.

**Fix:**

Default `undefined` cache keys to their production fallback values to preserve compatibility with legacy cache files:

```diff
function fromCurrentSources(cache: LonghornCache): boolean {
  const sources = updateSources();
+ const cacheApiURL = cache.apiURL ?? 'https://api.github.com';
+ const cacheUpgradeServer = cache.upgradeServer ?? '';

- return cache.apiURL === sources.apiURL && cache.upgradeServer === sources.upgradeServer;
+ return cacheApiURL === sources.apiURL && cacheUpgradeServer === sources.upgradeServer;
}
```

### Raised during execution

Verification surfaced four items beyond the review's findings; all were decided and applied.

1. **`getUpdater`'s gate had no unit coverage.** The review's I2 named two uncovered gates, and only the `updateSources` half was closed initially. `index.spec.ts` now asserts that `options.upgradeServer` picks up the override when updates are forced and stays untouched when they are not. Removing the `RD_FORCE_UPDATES_ENABLED` half of the gate fails exactly that test.

2. **The sibling spec had the same env-poisoning bug S3 fixed.** `index.spec.ts`'s state-machine block never cleared `RD_FORCE_UPDATES_ENABLED`, and `doInitialUpdateCheck` gates the queued-install path on it, so a developer exporting the documented variable got two unrelated failures. Reproduced, then fixed.

3. **`LonghornCache.apiURL` and `upgradeServer` were declared required** while no cache on any existing installation carries them. They are now optional, with `updateSources` returning `Required<Pick<…>>` so it still promises both. With `strict: true`, an unguarded dereference now fails type-checking.

4. **The comment on `fromCurrentSources` initially overclaimed.** It said every reader discards a provenance-less entry, but `setHasQueuedUpdate` reads the cache and writes it back without checking. It now names the two readers that do discard. No behavioural bug: that third reader only flips `isInstallable`, and the entry fails the next provenance check anyway.

The suite passes identically with a clean environment and with all three override variables exported to poison values. Two mutation checks confirm the new tests bite: removing the cache's provenance spread fails three tests, and removing half the responder gate fails one.

The branch row in this review and in Round 1's was wrong, naming `fix-updater-bundled-electron-updater` (which is PR 10614). Both now read `test-updater-simulated-upgrade`. The setup helper populated it, so the same error will recur until that is looked at.
