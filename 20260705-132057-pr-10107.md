## Executive Summary

This PR adds `i18n-report`, a self-contained Go CLI that scans Vue/TS/JS source and `en-us.yaml` to report unused, undefined, stale, referenced, and dynamic translation keys. It is the recut first slice of a ten-PR stack — only the scanner and read-only reports — cleanly scoped and fully tested. One output bug matters: `references --format=json` emits keys absent from `en-us.yaml`, diverging from text mode. The rest are documentation and scope cleanups.

The three reviewers converged. Claude and Gemini independently caught the JSON leak; Codex and Claude flagged package comments that name subcommands (`check`, `drift`, `merge`, `translate`) and helpers (`loadMetadata`) absent from this slice; Gemini and Claude noted override/merge machinery in `yaml.go` carried from later slices and dead here. No critical issues surfaced. Running every report against the live tree confirmed the heuristic scanner produces zero false positives today — the `undefined` gate finds exactly seven genuine missing keys — so the several "this heuristic could false-positive" concerns are future hardening, not current bugs.

## Important Issues

I1. **`references --format=json` emits keys absent from `en-us.yaml`** — `report_references.go:36-51` [Claude Opus 4.8, Gemini 3.1 Pro]

```go
if format == formatJSON {
    enc := json.NewEncoder(os.Stdout)
    enc.SetIndent("", "  ")
    return enc.Encode(refs)          // refs holds keys not in en-us.yaml
}
for _, k := range sortedKeys(keys) { // text mode: en-us keys only
```

`findKeyReferences` returns `refs`, and `addDirect` (`scan.go:198-201`) writes every direct reference into `refs` — including references to keys missing from `en-us.yaml`. JSON mode encodes that map verbatim; text mode iterates `sortedKeys(keys)` and omits them. Verified on the live tree: `references --format=json` contains `"generic.and"` (an undefined key) while text output does not. The command documents itself as "where each `en-us.yaml` key is used," so the JSON form breaks its own contract — and JSON is the interface downstream tooling consumes. Both agents raised this independently; my run confirmed it.

Fix: filter to en-us keys before encoding, matching text mode.

```diff
 if format == formatJSON {
+    filtered := make(map[string][]keyReference, len(keys))
+    for k := range keys {
+        if locs := refs[k]; len(locs) > 0 {
+            filtered[k] = locs
+        }
+    }
-    return enc.Encode(refs)
+    return enc.Encode(filtered)
 }
```

## Suggestions

S1. **Unreadable source files warn-and-continue, contradicting the documented exit-2 contract** — `scan.go:203-207` [Codex GPT 5.5]

```go
data, err := os.ReadFile(file)
if err != nil {
    fmt.Fprintf(os.Stderr, "Warning: cannot read %s: %v\n", file, err)
    continue
}
```

The README's exit-codes section promises exit `2` for "an unreadable file," and the primary inputs honor it — a `loadYAMLFlat(enPath)` failure returns an error and exits 2. Source-file read errors are the exception: they downgrade to a warning, so `undefined` can exit 0 while an unreadable file hides a missing key. Source files are always readable in CI, so this never fires today. Reconcile the two — return the error for a strict gate, or scope the README's exit-2 promise to the inputs it covers.

S2. **`dynamic --format=json` emits `null` for empty results** — `report_dynamic.go:60-68` [Codex GPT 5.5, Gemini 3.1 Pro]

`reportDynamic` declares `var entries []dynamicReportEntry` and `var matches []string`, then JSON-encodes them directly, bypassing the nil-slice normalization `outputStrings` applies (`output.go:15-16`). With no dynamic patterns — or a pattern matching nothing — the JSON field serializes as `null`, not `[]`, forcing consumers to handle two shapes. Initialize both to empty slices.

S3. **Unsupported `--format` values silently render as text** — `report_unused.go:8-13` [Codex GPT 5.5]

Every report accepts `--format` but compares only against `"json"`, so any other value — including a typo like `--format=jsoon` — renders as text and exits 0. A shared validator returning an operational error (exit 2) for values other than `text` or `json` would catch the mistake. The pattern repeats in `report_dynamic.go`, `report_references.go`, `report_stale.go`, and `report_undefined.go`.

S8. **`indirectKeyPattern` misses double-quoted object property names** — `scan.go:55` [Gemini 3.1 Pro]

This affects `unused` precision only (not the `undefined` gate), and no such construct exists in the tree today. Add `"[^"]+"` to the property-name alternation.

The loop skips a template that lacks `${`, but `dynamicKeyLiteral` already requires `\$\{[^}]+\}` to match, so the guard can never fire. Drop it.

S10. **Line-based comment filter misses block comments without leading asterisks** — `scan.go:48` [Gemini 3.1 Pro]

A stateful `inBlockComment` flag in the line loop would close the gap. Theoretical today — the scan produces no false positives on the current tree.

## Design Observations

### Concerns

- **(future) The `undefined` gate's heuristics can false-positive once wired to CI** — `scan.go` [Claude Opus 4.8, Gemini 3.1 Pro]. `keyAttrPattern` captures any `*-key="literal"` attribute; the `keyPropLine`→`dottedKeyLiteral` path captures every dotted lowercase literal on a line containing `titleKey`/`labelKey`/`descriptionKey`; `multilineKeyPattern` and trailing/block comments bypass the line-based comment filter. All feed `directRefs`, which drives the exit-1 gate. Today the tree is clean — exactly seven real undefined keys, no false positives. But a future attribute like `sort-key="metadata.name"`, or an unrelated dotted literal on a `labelKey` line, would be reported as undefined and, once a later slice wires the gate into CI, fail the build on non-translation code. Constrain `keyAttrPattern`'s value to the key shape, or gate `undefined` on a curated attribute allowlist. (Gemini raised the `keyPropLine` and `multilineKeyPattern` cases as important findings; the zero-false-positive result recalibrates them to this forward concern.)

- **(in-scope) `unused` folds dynamic matches into "used," under-reporting truly dead keys** — `scan.go:256-263` [Codex GPT 5.5]. A broad pattern like `snapshots.dialog.{}.info` marks `snapshots.dialog.delete.info` used even though only the `restore` branch calls it (`SnapshotCard.vue:139`). For a deletion tool this is the safe direction — treating a dynamically-matchable key as used avoids proposing deletion of a live key. A "possibly used" tier (or listing dynamic matches separately) would surface those keys without that risk. Assessment: the current behavior is correct by default; the tier is a precision enhancement, not a fix.

- **(future) Regex-heuristic scanning versus a Vue/TS parser** — `scan.go` [Claude Opus 4.8]. Roughly eleven regexes over raw lines: fast (<1s over the tree) and conservative. Residual noise shows in `dynamic`, which reports a JS object-access literal `WSL.integrations["{}"]` with zero matches. If the heuristic set keeps growing across the stack, a lightweight parse would remove the trailing-comment and object-access corners wholesale.

### Strengths

- **(in-scope) The `refs`/`directRefs` split** — `scan.go:151-161` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]. `unused` uses the permissive set (indirect and dynamic) to avoid false deletions; `undefined` uses the strict set to avoid false alarms. The rationale is documented at the point of use.
- **(in-scope) Exit-code discipline** — `main.go:49-55` [Claude Opus 4.8, Codex GPT 5.5]. `errFindings` maps to exit 1 for findings and 2 for operational errors — the right primitive for CI gating, explained in both code and README.
- **(in-scope) Complete integration touches** [Claude Opus 4.8]. A single dependency (`yaml.v3`), the module wired into `go.work`, a `package.json` test target, `.gitignore`, and spelling excludes all land together and correctly.

## Review Process Notes

### Skill improvements

- When the change adds or modifies a source scanner, linter, code generator, or CI gate, run it against the real repository before rating any finding that alleges a false positive or false negative. Base severity on the observed output: a heuristic that could misfire in theory but produces none on the current tree is a hardening suggestion, not a correctness bug. State the command run and its result in the finding. Reviewers that reason about the regex in isolation systematically inflate the severity of edge cases the real input never hits.

- When a round-N PR has been recut rather than incrementally updated — the current diff no longer contains the files a prior round's findings referenced — state this in the prompt and skip injecting prior findings whose code is gone. Re-verify only the prior findings whose files survive the recut. Asking agents to re-check findings against deleted code wastes tokens and invites confusion between the old and new scope.

### Repo context updates

- [repo] `src/go/i18n-report` is a heuristic scanner and CI-gate tool built as a ten-PR stack. When reviewing any slice, run the affected reports against the real repo (`cd src/go/i18n-report && go run . undefined | unused | references | stale --locale=<x> | dynamic`) and calibrate severity on the output. The scanner is a stack of line-based regexes; on the current tree the `undefined` gate reports exactly seven genuine missing keys with zero false positives, so a "this pattern could false-positive" claim is a forward-looking hardening note unless the run reproduces it.

I2. **JSON output in `references` includes undefined keys** — `src/go/i18n-report/report_references.go:33-37`

The text output for `references` iterates over `keys` (the keys present in `en-us.yaml`), correctly fulfilling its documented purpose to "Show where each en-us.yaml key is used". I3. **`indirectKeyPattern` misses double-quoted object properties** — `src/go/i18n-report/scan.go:53`

```go
	indirectKeyPattern = regexp.MustCompile(`(?:\b\w+|'[^']+'):\s+['"]([a-z][a-zA-Z0-9]*(?:\.[a-z][a-zA-Z0-9]*)+)['"]`)
```
The regex only matches object property names if they are bare words (`\b\w+`) or single-quoted strings (`'[^']+'`). If the codebase uses valid JSON-style double-quoted keys (e.g., `"my-property": 'foo.bar'`), the scanner will miss the indirect reference, leading to false positives in the `unused` report.

Fix: Allow double-quoted strings in the property-name group:
```diff
-	indirectKeyPattern = regexp.MustCompile(`(?:\b\w+|'[^']+'):\s+['"]([a-z][a-zA-Z0-9]*(?:\.[a-z][a-zA-Z0-9]*)+)['"]`)
+	indirectKeyPattern = regexp.MustCompile(`(?:\b\w+|'[^']+'|"[^"]+"):\s+['"]([a-z][a-zA-Z0-9]*(?:\.[a-z][a-zA-Z0-9]*)+)['"]`)
```
`(important, gap)`

I4. **`keyPropLine` causes false positive `undefined` findings for unrelated strings** — `src/go/i18n-report/scan.go:210-214`

```go
			if keyPropLine.MatchString(line) {
				for _, m := range dottedKeyLiteral.FindAllStringSubmatch(line, -1) {
					addDirect(m[1], ref)
				}
			}
```
If a line matches `keyPropLine` (e.g., contains `titleKey:`), the scanner blindly extracts *every* dotted string literal on that line. If the object declares another property on the same line with a dotted string that isn't a translation key (e.g., `titleKey: condition ? 'page.title' : 'app.default', icon: 'icon.png'`), `'icon.png'` is added to `directRefs`. Because it is missing from `en-us.yaml`, the `undefined` command will fail the CI build.

Fix: Use a regex that specifically targets the values assigned to the key properties, or document this as a known limitation that requires placing unrelated dotted strings on separate lines.
`(important, regression)`

I5. **`multilineKeyPattern` bypasses comment filters, causing false positives** — `src/go/i18n-report/scan.go:222-226`

```go
		// Multi-line t( calls span lines, so match against the whole file.
		for _, m := range multilineKeyPattern.FindAllStringSubmatchIndex(content, -1) {
```
Because `multilineKeyPattern` searches the raw file `content`, it completely bypasses the `commentLinePattern` check applied in the line-by-line loop. If a developer comments out a multi-line `t(...)` block and deletes the key from `en-us.yaml`, the scanner will still parse it and the `undefined` gate command will break the build.

Fix: Remove `multilineKeyPattern` and track multi-line `t(` state in the primary line-by-line loop, or document that multi-line calls cannot be safely commented out.
`(important, regression)`

S1. **Block comments without leading asterisks bypass the filter** — `src/go/i18n-report/scan.go:44`

`commentLinePattern` only matches lines starting with `//`, `*`, `/*`, or `<!--`. In a block comment where inner lines lack leading asterisks (or HTML comments spanning multiple lines), the inner lines are treated as active code, potentially triggering false positives. Consider adding a stateful boolean (`inBlockComment`) to the line-by-line loop.
`(suggestion, gap)`

S2. **Defensive code that cannot fire in dynamic pattern extraction** — `src/go/i18n-report/scan.go:104-106`

The `yaml.go` file contains extensive logic to parse and preserve YAML comments (`@reason`, `@override`), storing them in `mergeEntry`.
